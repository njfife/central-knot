# Central Knot product brief

Source: the user's request and walkthrough confirmations, November 4 and 5, 2026. This is a faithful working summary, not an approved specification. The rules are in [SPEC.md](SPEC.md).

Statements here are the user's confirmed choices unless marked. **(Constraint)** marks a technical fact or evidence limit those choices must meet. **(Proposed)** marks a mechanism or default this draft suggests, which the user has not confirmed and can change; it never reduces confirmed scope. A marker covers its own sentence, or the whole paragraph when it opens one. Six latest confirmations are choices, not proposals: marketplace automation independent of sync ownership, partial native Disable, automatic resolution of unknown action order, the explicit Start fresh recovery, best-effort organization update delivery, and opening CK once after normal installation.

## Product

Build a simple cross-platform desktop configuration manager named Central Knot (Death Stranding reference), probably Electron. First deliver a detailed formal requirements specification, not application code. Prioritize a polished, very simple UI later. No overbuilding: minimal local architecture, no new platform. Explicitly state what is out of scope, prune complexity before asking the user questions, and separate proposed defaults from confirmed requirements.

**Central Knot is a configuration mover, not a secret manager or security product. Managing secrets is the user's responsibility.** Do not look for secrets in MCP configurations, skills, agent definitions, instructions or any other managed content. No secret detection or classification, scanning, redaction, filtering, omission, secret-specific warnings or approvals, vault integration or content policing. Move content and values as-is through supported translation, local storage, history and restoration, whether or not they contain secrets. Repository and build authentication do not authorize inspecting or filtering synced content. Ordinary correct file handling is still necessary.

Every delegated task, across research, specification, implementation, build, testing and review, must include the root `AGENTS.md` paragraph on this boundary directly in its brief; inherited context is not enough. Reviewers must not treat the absence of secret-management features as a defect.

## Priorities and scope

- **Two core features:** Claude and GitHub Copilot desktop and CLI support, and optional bundled marketplace distribution for custom internal builds.
- **Highest priority surfaces:** the actual GitHub Copilot desktop app and Copilot CLI, Claude Desktop (Cowork and Code journeys) and Claude Code CLI, and Codex CLI with the ChatGPT desktop app's Codex (added November 8, 2026). Pi and OpenCode stay in scope at lower priority. All five families remain supported. Investigate CLI and desktop surfaces of each, and distinguish actual products from nonexistent surfaces, including the user's references to GitHub Desktop and GitHub CLI. Do not silently narrow support or assert unsupported capabilities.
- **No substitutes:** GitHub Desktop and the VS Code extension are not the Copilot app. A CLI does not satisfy required desktop support.
- **Restricted access:** some users have Cowork only and engineers have Claude Code only. Both journeys are required independently. Never require switching to, installing or using the other product or CLI, and never count one surface's success as proof for the other. Detect and manage only available or selected surfaces, respecting organization access restrictions, with no CK user roles. **(Constraint)** An installed Claude app does not show which modes an account can use, so CK says what it cannot tell and invents no signal; an ordinary user-wide write where access is unknown grants nothing and claims no access. A private Claude Code copy is never a Cowork route or an exception to an organization restriction (PLG-04). **(Proposed)** Ticking a mode whose access is unknown, and an explicit I don't have this mode: D-28c, D-28d.
- **Platforms:** macOS launches first, followed by Windows and Linux. Preserve all three in the architecture from the outset: prefer cross-platform technologies, avoid macOS-only dependencies where practical, and isolate necessary native integrations behind platform adapters. No later-platform dates or launch-parity commitments are selected.
- **User-wide configuration only.** Workspace, project and repository configuration is out of scope, including instructions, agents, skills, MCP and plugin settings. Do not synchronize or write it, or use project overrides to work around missing user-wide controls.

## Recipient experience

Installing CK must be enough to enable integration with already-installed, authorized harnesses. For v1, opening CK once after normal installation is acceptable: marketplace setup then happens automatically, with no terminal commands or extra harness setup, no installer auto-launch is required, and the later Iru end state does not change. User choices stay inside CK, and CK handles native marketplace registration, selected-plugin installation and updates. Recipients do not register marketplaces, upload plugins, clone repositories, use a terminal, edit settings, install an alternate harness or CLI, or hold repository membership for bundled content. Organization publishing and hosting are separate. These are required outcomes even where current routes lack proof: manual Cowork upload is not an accepted substitute, and unproven automation stays reported as unmet. Use whichever route is simplest and most seamless; a local server, Git service or UI automation is not mandatory.

**(Constraint)** Evidence stays honest. A locally hosted Git source is user-reported, with transport, build, steps, load and update not captured, so it is a lead rather than an independently reproduced pass. Third-party-provider host provisioning documentation is a candidate, not universal evidence for ordinary Enterprise accounts. Do not substitute Code results for Cowork. The user's screenshot shows the Varo Claude account labelled Enterprise; organization permissions, enabled plugin features and private GitLab reachability remain unverified, and organization sync does not replace optional bundled distribution.

**Iru (formerly Kandji)** managed rollout is the end state, not v1: Iru deploys the internal build, and CK makes the marketplace appear natively. V1 proves normal CK install and first open, then native marketplace registration, then a selected plugin installing and loading, with no Iru integration or tenant access. Other confirmed requirements are not deferred by this. Research supported provisioning mechanisms; do not assume an integration or APIs exist.

## Marketplaces and plugins

- **Work marketplace:** a private GitLab marketplace with many plugins, remotely hosted in the organization's GitLab environment and reached by remote URL. No prepared local clone. Access needs the company network or VPN, which CK does not configure. The first release must browse it and install a selected plugin into both Cowork and Claude Code with no terminal or manual clone. GitLab deployment type and authentication are organization facts, still unspecified. **(Proposed)** Direct-source installs assume Git credentials already on the machine; onboarding someone without them stays unresolved, neither a confirmed no-terminal solution nor a blocker for bundled recipients (PLG-01).
- **Coworkers cannot figure out installing a plugin from a private Git repository** into Claude Desktop or Claude Code. Make supported installation easy without CLI knowledge.
- **Browsing:** users browse marketplaces and their catalogs. The marketplaces Codex and Claude Code provide by default are added automatically, not a curated list. Adding a marketplace never installs a plugin. **(Constraint)** Each default applies to the surfaces reading its provider's configuration and implies no route elsewhere. **(Proposed)** Native removal of CK's registration, removal from CK's own list, and a same-name registration from another source, which is never silently overwritten: D-16.
- **Destinations:** Install defaults to all compatible managed harnesses, with per-plugin include and exclude controls. A plugin left on that default also installs into newly detected compatible harnesses with no further approval. Settings can change the default or turn off expansion, without overwriting per-plugin choices. No version pinning, profiles or policy engine. **(Proposed)** These defaults read this build's own selections, not standalone selections transferred with sync; Install shows its plugin-specific default and can explicitly include such a harness, widening no existing plugin (D-31). **(Proposed)** How a plugin's policy behaves as Settings change or while Disabled everywhere, and adopting one installed natively before CK: D-16. **(Proposed)** Deselecting a harness leaves plugins installed there updating and drops it from later Install defaults: D-18. **(Proposed)** A waiting selection where a feasible route only awaits a named proof, shown Not known yet and never as installed: D-28b. A destination that is definitely not available is not ticked.
- **Uninstall** is explicit and records an exclusion until the user chooses Install again. Destination-specific uninstall excludes that destination; uninstall everywhere also covers future destinations. Updates, expansion and catalog presence never reinstall. **(Proposed)** Unticking an installed destination is its clearly named Uninstall (PLG-02). **(Constraint)** Where surfaces read one plugin store (OWN-04), a write for one can reach the other: CK discloses that, claims no exclusion or removal for one reader without a validated filter, and still reports each surface's own result.
- **General plugin support:** Claude plugins should install on at least Codex and appropriate Copilot surfaces as supported. Whole-plugin compatibility is not assumed; explain incompatible features in the UI.

## Organization builds

- **Optional and reusable.** Anyone can build an internal app from a GitLab or GitHub marketplace by adding an optional argument to the normal build, locally or in CI, with no application-source edits or in-app build screen. Omitting every optional custom input gives the standard build, which has no private marketplace, plugin content or feed, and still offers browsing and the default marketplaces. Any optional input gives a custom build, and one with a marketplace input is a bundled build. App branding with no marketplace gives an unbundled custom build with its own identity. **(Constraint)** So does an app-update location with no marketplace, because a custom update route cannot belong to the standard app's identity.
- **Contents.** The whole catalog and all installable plugin content from a recorded snapshot. Bundling is not installation. Recipients browse and install with no source-repository membership, credentials or runtime source connection. Build credentials are never distributed: this covers the build's own source access and checkout metadata, while configured URLs and supplied content copy as-is. **(Constraint)** No source access does not prove no Git dependency: whether a native route needs system Git on a recipient's machine is unproven, and any such dependency means installing CK alone is not proved there.
- **Branding.** Optional independent name and logo for the application and for the bundled marketplace. Omitted inputs keep standard branding. **(Proposed)** Marketplace branding with no marketplace input stops the build with a clear input error. **(Proposed)** A native registration's identity is fixed per build: changing it needs an application build, and a content refresh never renames it (D-16).
- **Separate installations.** Custom builds install beside the standard app with separate settings and identity, and updates keep them separate.
- **One background sync owner** across builds for standalone sharing and instruction synchronization. If another build is syncing, offer Take over syncing, transferring those jobs with no overlap and leaving the previous app running but not syncing. Each build still registers its own marketplace and runs plugin automation without takeover, with no conflicting writes to a shared file. This is an uncommon case, mainly in development, with no multi-instance system. **(Constraint)** Changing owner reopens no confirmed choice: the established sync state, history and choices carry over, changes made meanwhile reconcile under the normal rules, and only genuinely new or unrelated items are collisions. If that state cannot be read, no sharing write runs under an invented baseline, and marketplace automation continues. What a build finding another recorded owner shows and still does: ORG-08. **(Proposed)** All mechanics: how stores are arranged, sync state carried and shared-file writes coordinated, a fresh build with no recorded owner becoming owner, how transferred history ages, and a transfer adding no plugin destination (D-31). **(Proposed)** Registering on a surface installed later, inferred from the no-setup outcome: D-16.
- **Recovery when sync state is permanently lost.** If sync metadata is permanently lost and no previous owner remains, offer an explicit Start fresh from current files. Explain that lost exclusions, conversion choices and history cannot be recovered, and show the first-time setup preview before beginning. Current harness files become new setup inputs; never infer historical deletions or claim the old relationships were restored. This is an explicit recovery action, not an automatic reset during ordinary takeover or handback. **(Constraint)** It is not offered while a prior owner runs or overlap cannot be ruled out, and plugin selections and marketplace automation continue unaffected (ORG-08). **(Proposed)** How permanent loss is recognized: D-31.
- **Independent content releases.** Marketplace content publishes and updates through a configurable organization feed, independently of application binaries and with no app rebuild per plugin release. **The final organization-specific update delivery is best effort for v1:** HTTPS is not required, local HTTP is acceptable, no exclusive transport, hosting arrangement or authentication method is selected, and organization-internal agents may complete or adapt that step later. CK supplies the client; hosting, reachability and access are the organization's, unknown here and not release-blocking. Gaps stay explicit, never claimed proven, and this relaxes no unrelated requirement, native install or load journey, or proof gate. **(Constraint)** Because recipients have no source access, each applied release must leave them the whole catalog and all installable plugin content, including externally referenced plugins, with packaging failures named and plugin bytes moved as-is. An application update never rolls content back to an older embedded snapshot, and code, app-branding and installation-identity changes need an application release. **(Proposed)** The mechanism, including full archives, an HTTP-capable client, a feed needing a marketplace input, snapshot-only bundles and a newer embedded snapshot counting as a release: D-35.
- **Automatic organization application updates** stay required for bundled distribution, separate from content, and never replace a custom build's identity. **(Constraint)** A custom build never uses the standard app's update channel, because updates must keep the builds separate. **(Proposed)** Holding a branding-only build to the same obligation, and what a build with no location or no proven route reports: D-19, ORG-06.
- **Installed plugins** update automatically at their existing destinations, preserving selections, disabled states and exclusions, and installing nothing unselected. Refreshing the catalog alone is not enough. Native update and reload routes need validation per destination.
- **Catalog removal,** on every source route, shows Deprecated, explains why, and keeps the installed copy usable and unchanged, with its enabled or disabled state. Only explicit uninstall removes it. No silent cleanup of content still in use, and a failed or incomplete refresh proves nothing.

## Configuration sharing

The user switches harnesses, including through T3 Code, and wants the same base configuration wherever possible.

- **Detect and browse.** Detect installed harnesses and discover existing skills, MCP servers, agents and instruction configuration automatically. Browse by harness in one UI, turn supported items on and off, and customize instructions.
- **Store.** Import existing configuration into a central app-managed store, track changes and sync compatible configuration rapidly behind the scenes, with per-item and per-destination control available without complicating ordinary use.
- **Automatic sharing.** After the user selects harnesses, standalone skills, MCP configurations and agents already present, and those added later, synchronize with no CK approval prompts, including supportable best-effort conversions with limits shown non-blockingly. Entirely unsupported features are skipped with an explanation. Examples: install a skill in Claude and have it appear in Codex, Pi, OpenCode; add an MCP server in Codex and have it appear in Claude Code. MCP stays two-way, including deletion. **(Constraint)** A destination that cannot hold an MCP field speaks only for the fields it can hold (MCP-01).
- **First-setup collisions.** Different standalone skills or MCP entries under one name stay separate and unchanged, and are shown during first setup, where the user shares one version or leaves them separate. Never an automatic overwrite. Unrelated items proceed. **(Constraint)** Two capable MCP copies that disagree on a field a third, limited copy cannot hold are still a collision (SYN-06).
- **Newest action wins.** For an already-synced item, concurrent edit/edit and delete/edit resolve to the newest action, with recoverable history and a non-blocking notice linked to history and Undo, and no dialog. **Where order genuinely cannot be established,** CK still resolves automatically: an edit beats a deletion, competing edits are chosen deterministically, the notice says order was unknown and the alternatives stay recoverable. This is an accepted degraded outcome, not proof of which came last. **(Proposed)** The exact tie-break. **(Constraint)** State real detection limits honestly: no invented deletion times, and notification arrival, scan or read order and modification times are never proof of action order (CON-04).
- **Deletion and history.** Deleting a synced skill or MCP entry in one harness deletes it from its other destinations, with Restore. An unavailable harness is not a deletion, and a stale replica never recreates the item. Deleted items and previous versions are kept 30 days by default, configurable.
- **Disable and Delete.** Settings holds the default turn-off action, initially Disable; Delete is separate and explicit; new installs start enabled, and updates preserve disabled states. Disable is native, only where kind, surface, version and user-wide scope support it. If only some destinations support it, disable there and clearly identify where the item remains enabled. Where unsupported, leave the destination unchanged and show Disable unavailable, never removing or relocating content or using a project override. Build only the capability handling supported adapters need. Blocking automatic invocation alone is not disabling. **(Constraint)** With Delete chosen as the default, turning off a shared skill or MCP entry is that explicit Delete, naming its scope with no new approval; native Disable stays local (ENB-05). **(Constraint)** On a build outside the verified record no new Disable is offered; an existing disabled state stays, and Enable is a plain reversal that claims no support. **(Proposed)** An item Disabled at every current destination waits for an explicit Include or Enable before reaching a newly selected harness (D-12).
- **Plugin-owned skills** cannot be deleted individually. Disable applies only where the harness has an effective override that does not edit plugin contents, and whole-plugin disable stays visibly distinct.
- **Agents.** Prefer native sharing. **(Proposed)** A translated agent's direction by a local check: D-26. **(Constraint)** That check is structural: whether a translated agent behaves the same at runtime stays unproven. Where a destination has no compatible native agent support, offer optional, user-initiated Convert to skill, never an automatic setup or background fallback. Disclose true losses and invocation modes, and do not conflate workspace instructions, primary agents and subagents. A converted skill excludes the originating harness, even through automatic sharing and discovery, until explicitly requested there, which offers Keep agent and skill or Skill only. Skill only replaces the source-harness agent recoverably and prevents its recreation, without deleting other native-agent destinations. Skill edits never write back to agents. Plugin ownership and collision rules still apply.
- **Instructions.** Sync is optional and off by default, with its own control. When on, one shared base edited once across selected harnesses, plus optional per-harness additions, in personal paths only. When off, nothing moves, and inspection and editing still work. Built-in system prompts are not rewritten. **(Constraint)** Surfaces reading one physical file are one destination, with one composed output and one set of additions, every reader disclosed and no new filter required. **(Proposed)** Instruction sync's own selection list and a file deleted outside CK (D-29); instruction-group Delete stays open.

## App lifecycle

CK starts automatically at sign-in by default, configurable in Settings, so sync and updates work without opening the UI. Closing the main window keeps it running in the tray or menu bar. An explicit Quit stops the app and its background work.
