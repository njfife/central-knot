## 1. Central Knot in ordinary use

Central Knot (CK) is a simple local desktop app that moves configuration. It keeps skills, MCP servers and agents shared across the AI coding tools ("harnesses") on one computer, and installs marketplace plugins into them without a terminal. This section is the required experience, not current capability; sections 5 and 8 say what is unproven. Unmarked statements are confirmed outcomes (section 2) or the technical limits they must meet; *(proposed)* marks a default from section 7 that the user has not confirmed.

**First setup.** CK lists the harnesses it found and what each holds, with no standalone sharing writes yet; a bundled build's native marketplace registration is separate (ORG-03). The user selects the harnesses to manage, and the standalone skills, MCP servers and agents already in them share with no approval prompts. Different items under one name stay separate and appear right there in setup, where the user shares one version or leaves them separate. New items then share by themselves. CK starts at sign-in and keeps working from the tray or menu bar after its window closes; **Quit** stops it.

**A switcher.** A skill installed in Claude is written rapidly where Codex, Pi and OpenCode read it. An MCP server added in Codex reaches Claude Code, once V-09 shows that write is safe. An agent shares natively where the destination supports it *(direction proposed, D-26)*. A destination with no compatible native agents stays unwritten and offers an optional **Convert to skill**. If an item is edited differently in two harnesses, or edited in one and deleted in another, the newest action wins. Where CK genuinely cannot establish the order, it still resolves automatically and says so: an edit beats a deletion, and a fixed rule *(proposed)* picks between competing edits, with no claim that it was newest. A non-blocking notice links to history and Undo, and the alternatives stay recoverable. Deleting a synced skill or MCP entry in one harness removes it from the others, with **Restore**. **Disable** is the default way to turn something off: it applies at each destination with a real native switch and names where the item stays enabled, and those destinations stay unchanged and say **Disable unavailable**.

**Installing from a private marketplace.** On the company network or VPN, the user pastes the GitLab URL once in **Marketplaces**. They pick a plugin and see, per destination, what will work. **Install** defaults to all compatible managed harnesses, and CK does the native registration, install and later updates itself. Cowork-only and Code-only users each get their own complete journey. Having the Claude app does not show which modes an account can use, so CK says when it cannot tell and, *(proposed)*, a mode Install would otherwise tick stays ticked with that label.

**An organization build.** One optional argument to the normal build bundles a GitLab or GitHub marketplace, with optional independent names and logos for the app and the marketplace. The result installs beside the standard app and carries every plugin, so recipients open it once, then browse and install with no source access, and the marketplace also appears in their Copilot and Claude Code browsers. Later releases arrive through an organization feed with no app rebuild, updating installed plugins in place, and the app updates itself separately without rolling that content back. A plugin dropped from the catalog shows **Deprecated** and keeps working until uninstalled. If another build owns background sync, this build still registers its marketplace and keeps its plugins updated; **Take over syncing** concerns only standalone sharing and instruction sync, and carries their established state and choices across rather than starting over. Only if that state is permanently lost and no previous owner remains does CK offer an explicit **Start fresh from current files**.

**Day to day.** **Harnesses** shows each harness's actual items, managed or not, each with a name, a switch and one plain status; details sit one click down. Instructions can always be read and edited. Instruction sync, off by default, keeps one common base plus each harness's own additions, in personal instruction files only.

## 3. How to read this

A requirement's bracket shows its basis.

| Layer | Marker | Meaning |
| --- | --- | --- |
| Confirmed intent | `I-nn`, UD | Stated by the user |
| Technical constraint | **E** | Follows from evidence or correct file handling |
| Proposed default | `D-nn` | A choice this draft makes, unconfirmed. Implementation proceeds on it unless the user changes it (section 7) |
| Proof gate | `V-nn` | A technical fact not yet established (section 8) |

`AT-nn` is a specified acceptance test and `T-nn` a proposed numeric target.

| Evidence word | Meaning |
| --- | --- |
| **Documented** | Stated by the vendor; not run |
| **Exercised** | Run in a test here, for that OS, version and fixture only. Sub-labels Real, Stub, Stand-in and Listing: [CD §1] |
| **User-reported** | The user says it happened. Recorded as stated, not independently reproduced, never a pass |
| **Unproven** | None of the above, including anything Blocked. Unknown does not mean unsupported, and nothing here turns it into a promise |

**A required outcome stays required while its proof is open.** It is reported Unmet, naming the proof (REL-01), and a guided or interim route never passes a test that requires automation.

**Limits.** **The test fixture was a private GitHub repository, so no validation exercised GitLab.** Still unverified [VF §5]: the real Code tab on Windows and Linux (the most important gap); private HTTPS through a real credential helper; Copilot app and VS Code chat turns; Chat and Cowork by interaction; fresh machines.

CK **never** silently installs or removes a harness (a private CK-internal copy is allowed only where a validated REC-02 route needs it; PLG-04 is the current candidate, within its access conditions), launches harness apps with redirected homes or test drivers, uses internal scheduled-task formats, debug switches or trust-state edits, or collects harness logs. [E]

## 4. Core model and labels

- **Surface:** a product or mode. **Location:** a physical path or config key. **Reader:** a surface that reads a location. **Destination:** the harness or group of surfaces an item or plugin is written for at one location; a write or native switch reaches every reader of that location (OWN-04).
- **Harness:** a surface in section 5.1's two tiers. *(Proposed, D-18)* Surfaces recorded as reading the identical set of write targets (Appendix A) are one group, selected together for sharing, though each reports its own plugin results (REC-03); this is placement, not proof of reading (V-05, V-06). A partial reader such as VS Code joins and chains no group: OWN-04 discloses it, claiming no isolating filter.
- **Shared store:** one plugin install location, physical or account-held, that more than one surface may read, such as the Code tab and Claude Code CLI, the Copilot app and Copilot CLI, or a chosen Cowork route held in account state that Code sessions also load (seen on the macOS Code tab; elsewhere V-04) [CD §7]. A native operation there can act on one install unit for all its readers, so per-reader control needs a validated filter (OWN-04).
- **Item:** a skill, MCP server, agent, instruction file or plugin. A **standalone** item is not owned by a plugin.
- **Managed harness:** one the user selected. Automatic standalone writes reach only managed harnesses, and explicit actions may write to any detected harness. The only other automatic writes are plugin automation (ORG-03, PLG-06, PLG-09) and instruction sync, which has its own control and selection (INS-03). Neither enrols a harness for sharing. *(Proposed, D-31)* Plugin defaults read this build's own selection, not standalone selections transferred with sync (PLG-06).
- **Shared item:** a standalone skill, MCP server or agent kept in step across its **destinations**. A change at any destination spreads, except at a one-way native-agent destination (TRN-02).
- **Not shared:** discovered, imported or excluded, and not being shared. No automatic write reaches it.
- **Plugin:** a native record per surface, installed and updated as a unit. Never a shared item.

**Can this reach that destination?** These four labels are the only route answers. Item detail shows the specifics.

| Label | Meaning |
| --- | --- |
| **Automatic** | Written with no prompt; its class records nothing behaviour-affecting lost |
| **With limits** | Written with no prompt; a best-effort conversion's loss is named permanently, including "Has wider access than the original" |
| **Not available here** | Unsupported, none documented, or below a version floor. Skipped, with the reason and source |
| **Not known yet** | A proof the route depends on is open, or a result is unconfirmed; says what is unproven. Never worded as unsupported |

A "Why" may mention steps the harness itself offers, as information. They are not a CK route and never count as installed.

**Class, route and evidence are separate questions.** The class says what the destination's format can hold (TRN-01). The route says whether CK can write there with no proof outstanding. Those two set the label. Evidence is what has been run: a note in Item detail, never a fifth label, and never a reason to treat an already classified field as lost. A structural check is not runtime proof, which stays Unmet by name (REL-01).

**How far did it get?** Never merged into "synced". **Written:** store updated and the file or key on disk matches, as asserted by CK only. **Installed:** a plugin passed PLG-03's file check or its route-specific account-backed installation observation; not proof an app loaded it. Item detail may add evidence, never a row status: **Files found** and **Listed by _harness_**. A listing alone is never success. Listed is not Loaded, and Loaded is not Executed. **Appears in** is a Compatibility claim (REL-01), never a row status: it needs recorded session use per kind, surface and OS (V-05, V-06), and a signed-out run or a listing alone never proves it. There is no "Active" status, and no plugin is labelled simply "compatible" [AU §7]. Row statuses: UX-04.

## 6. Requirements

### 6.1 Platform and app lifecycle

- **PLT-01 Platforms.** macOS launches first, then Windows and Linux: a release sequence, not a scope reduction. The shared core uses portable technology and avoids macOS-only dependencies where practical; necessary native integration (sign-in start, tray, file events, packaging) sits behind platform adapters. Later dates and launch parity are not specified. Minimum OS, CPU and package formats are validated (V-10). [I-02]
- **PLT-02 Updates and removal.** Never tell a user to bypass an OS warning or disable a trust check. Bundled organization builds update automatically with no recipient action, through a route that keeps their identity; where none is configured or proven, ORG-06 reports it Unmet (unbundled custom builds: D-19). An update or uninstall preserves the store and settings; a failed update leaves the previous version usable and reports it. Removing the app leaves harness files in place. OS signing and packaging limits are per-OS evidence (V-10), not a product policy or a blanket reason a local build cannot run. [I-17, D-19, E]
- **PLT-02a Standard Mac self-update.** The standard build knows the release tag it was made from and checks the project's GitHub releases (no token, nothing about the person sent) shortly after launch and every few hours, also with the window closed. A newer release with the Mac zip (previews and finals for a preview build, finals only for a final build) turns the status bar's version into an Update button; one click downloads it with progress and restarts into it, unless something typed or waiting for Apply all would be lost, when the button asks instead, and never during a write. The new app must be signed by the same Developer ID team before it replaces the running one; a failed or interrupted update leaves the installed app as it was and says so. The next launch says once that it is on the new version, with the release notes. Settings has the version, Check now and the last result; a copy that can't update itself (not in an Applications folder, unsigned, untagged or a development build) says why and offers the release page. Not on Windows or Linux until they have releases. Organization builds: ORG-06. [I-17, D-19]
- **PLT-03 Automatic start.** CK starts at sign-in, so sync and updates work without opening it. On by default; Settings can turn it off. [I-30]
- **PLT-04 Window and Quit.** Closing the main window leaves CK running in the tray or menu bar with sync and updates continuing, and background work never needs the window reopened. An explicit **Quit** stops the app and all its background work. [I-30]

### 6.2 Detection and discovery

- **DET-01** Detect each section 5.1 surface separately, with version and channel where readable. States: Installed, Config found but app not detected, Not found, Version unknown. A config folder proves prior use only. For automatic-write eligibility, detected means Installed or Version unknown with installation established, never config alone. **An installed Claude app proves access to neither Cowork nor Code,** and CK assumes no sign-in or organization right. Each mode shows its access as known, available or not, only where a safe read-only signal establishes it (V-01, V-15), and otherwise **Access unknown**, stated as uncertainty; no such signal is established yet. An explicit **I don't have this mode** (UX-05) is the user's reversible statement, not a detection: a **marked mode** gets no plugin automation write on its behalf and reports no failure (D-28d). Neither unticking a mode for one plugin (PLG-06) nor deselecting a harness for sharing (D-18) is this statement. Identifiers are probed [CD §3]. [I-03, I-04, I-18, D-28c, D-28d, E]
- **DET-02** Probes have timeouts and start no session, service, MCP server or sign-in. Resolve executables as a GUI app must and honour documented root overrides [CD §3]. An unknown root is labelled unknown, never replaced by the default. Background rechecks: T-07. [E]
- **DET-03 One version rule.** Capability data records, per feature, family and OS, any documented floor and the tested range. Below a floor: **Not available here**. Outside the tested range: a documented route continues with a "not yet verified on this build" note; an undocumented route shows **Not known yet**. **Native Disable is best effort:** outside V-20's record, or where the build can't be read, Disable is still offered with a quiet "not checked on this version; it may not take effect" note (ENB-01). A build change never deletes a deployment, reruns a native operation or clears a Disabled state. Capability data ships with app updates. [E]
- **DIS-01** Discover items at user scope automatically, with no home-wide crawl and no workspace or project management. **Discovery changes nothing:** no config write, data initialization, or service or server start. Project paths in the research describe harness behaviour, not locations CK manages. [I-04, I-31, E]
- **DIS-02 Harness view, in the default UI:** for each detected surface, its actual skills, MCP, agents, instructions and installed plugins, managed or not, with applicable controls and status; instruction files offer editing, not a turn-off switch (INS-02). [I-05, I-08]
- **DIS-03** Read-only with a reason [CD §3]: plugin-provided items (apart from ENB-06's native Disable), reserved folders, administrator layers, commands, rules, hooks, prompts, themes, extensions, inline agents and host-bound entries. Account-backed state shows "Managed in your Claude account" with a link, never an empty state. [I-03, D-15]
- **DIS-04** Empty list, failed command, policy restriction, malformed file and missing binary are different results. On disk never implies active. [E]
- **DIS-05 Discovery reads files.** It runs no native command that writes, starts servers or runs code; the commands in [CD §3] with side effects never run for it. Native operations are allowed for explicit actions and plugin automation, with a timeout. [E, VF §1]

### 6.3 Store and history

- **STO-01** A local app-managed store in an ordinary folder needs no system Git, cloud or running harness. It is not a vault, and has no remote of its own (STO-05 adds an optional git repo). Separate settings per installation are confirmed (ORG-07); one content store per installation is proposed (D-31). Form: D-08. [I-06, I-11, D-31]
- **STO-02** Track each change (item, source, when CK observed it, diff), with item history and restore. Before editing a shared native file, keep the prior value of the touched keys; before replacing a file, keep the whole file. [I-06, E]
- **STO-03 Import copies portable configuration only.** Skill: the directory, byte-exact with file modes (SKL-01), without nested `.git` or reserved folders. MCP: the native entry alone, all values verbatim including embedded credentials. Agent: the original file or entry. Instruction file: bytes, path and scope. Plugin: a record only (source, marketplace, version, enabled state, scope, components). External caches, session stores, auth databases, keychains and logs are not configuration entries and are not imported. *(Proposed, D-01)* Import starts with a selected harness's setup or an explicit Share (D-34); discovery at an unselected harness imports and adopts nothing. [I-06, I-11, D-01, E]
- **STO-05 A git repo for the Managed set (user feedback, November 9, 2026).** Optionally, one git repo on any host (GitHub, GitLab, a server of the user's own; HTTPS or SSH) holds the Managed set: `skills/<folder>/` byte for byte, `mcp/<name>.json` in Claude Code's shape, `agents/<name>.md` in Claude Code's format, and `instructions/base.md` for the base instructions (the store's `instructions/base.md`; a pulled base also goes to the tools that get the base, except a copy edited in a tool's file; a base deleted in the repo empties the base and takes it out of those tools, in History with an Undo that puts both back). Other files in the repo stay as they are. CK keeps its own clone in the store and runs the machine's git with its existing sign-in; it never asks for, stores or handles credentials. Nothing moves until the user clicks **Pull** (the repo's changes since the last pull or push go into the tools through ordinary sync, each in History with Undo or Restore) or **Push** (one commit of the Managed set as it is here, only when this computer has every commit the repo has). When both sides changed one item, Pull takes the repo's version and History keeps this computer's; an edit always beats a deletion, on either side. An item that can't come in (a link, a SKILL.md no tool can read, no tool to hold it) is shown with why and stays as the repo has it. The page shows the repo, branch, the commit in use here, the repo's latest commit, when it last pulled, pushed and checked, and what differs each way. One repo; no merging of several. STO-01's local store still needs no Git: without a connected repo nothing changes. [Feedback item 9]
- **STO-04 Retention.** Deleted items and previous versions stay recoverable for 30 days by default, configurable in Settings; indefinite retention is not promised. Expiry removes recoverable content but keeps a small deletion record, so a stale replica returning later cannot revive the item. It never touches a current revision or content a retained install still uses. [I-22, E]

### 6.4 Automatic sharing

- **SYN-01 First setup.** Sharing writes nothing before the user selects harnesses. CK then shares the standalone skills, MCP entries and agents already in them under this section's rules, with no further approval (D-01); a build that finds another recorded owner waits for Take over syncing, which is not first setup, while one with none proceeds and may become owner (D-31); only the explicit Start fresh recovery re-enters setup (ORG-08). Collisions show during setup (CON-03), and setup discloses once which other readers will see shared items (OWN-04). It selects no other harness, installs no catalog plugin, extracts no plugin component, moves no instructions and touches no project. [I-07, I-26, I-29]
- **SYN-02 After setup.** A new or changed user-scope skill, MCP server or agent at any managed location spreads with no prompt to the other managed harnesses, per TRN-01 and TRN-02. The only remaining prompts are a platform's own consent (ACT-03) and the MCP-02 interim. Instructions follow INS-03, plugins PLG-05. [I-07]
- **SYN-03 Sync switch.** Normal use is one visible **Sync on/off** switch, with no required per-item setup. Off stops background standalone writes and shows a banner; CK keeps watching, so changes stay recorded and apply when it turns on. **Explicit user actions run regardless** and write exactly what they show (a non-owner offers only those in ORG-08). It does not control instruction sync or plugin automation. [I-08, D-01, D-16]
- **SYN-04 Watching.** Native file events, a polling fallback (proposed interval, T-08) and a settle window, so atomic saves are not read as deletions. An event or poll only prompts a read (CON-04). Provide **Sync now**. [I-07, E]
- **SYN-05 Reconcile** against a recorded baseline, which moves with ownership (ORG-08). A one-sided change is adopted; a two-sided one follows CON-01. Echo suppression is hash-based and crash-surviving: **a second pass makes zero content writes and repeats no native install.** [E]
- **SYN-06 Identity.** Same kind, name and content is one item, and an identical file is taken over with zero writes. MCP entries and agents compare after format normalization, so a TOML-versus-JSON difference alone is no collision. **MCP entries compare only the fields both readers can hold (MCP-01),** at first setup, at a later selection and after a handoff. Compare the whole set of copies, not one pair: they are one item only if all copies able to hold a field agree on it, and a capable copy holding a retained field then supplies it, with no write wiping it. A real difference in a field both can hold, like other different content, follows CON-03, even where a third, limited copy matches each side. **If a chosen limited copy cannot hold a field on which capable copies disagree,** such as two different tool allow lists, that same CON-03 choice has the user select which capable copy supplies the retained fields: no inferred union of their values, no removal because the chosen copy cannot represent them, and no extra prompt in ordinary sync. After sharing starts, identity is the location, respecting case-insensitive filesystems. A rename is one deletion and one addition, both of which spread, and History says so. [I-29, E]
- **SYN-07 New harness.** A newly detected harness gets no shared skill, MCP or agent until the user selects it, though it may already read shared folders. Detecting one raises one notice, and selecting it runs SYN-01 for that harness, apart from an item Disabled at every current destination, which waits for an explicit Include or Enable (proposed, D-12). Plugin expansion is separate (PLG-06), and deselecting a harness follows D-18. [I-07, I-19, D-12, D-18]
- **SYN-08 Exclusion.** Item detail has one switch per destination, and **Don't share** covers all of them. Exclusion stops CK writing there; any existing copy stays as it is and becomes Not shared, and later edits there enrol nothing (D-34). Including it again treats a differing copy as CON-03; **Share** on a Not shared item: D-34. Deleting follows DEL-02. [I-08, D-34]

### 6.5 Ownership and file handling

- **OWN-01** Automatic sharing writes reach shared items' destinations only; instruction sync follows INS-04. One location has one owner: a second, different item reaching it is CON-03. Bytes, fields and comments outside a shared item are preserved. A collision is never an overwrite. [E]
- **OWN-02** Never edit caches or tool-managed registries [CD §3], or administrator layers. Never replace a user's symlink, and create none (D-13). [E, VF §4]
- **OWN-03** Sync plans **physical locations**: resolve real paths, write once per destination, know every reader. Placement (D-05) honours selected destinations and exclusions. No fixed set of folders is claimed to cover all surfaces until V-06 passes. [E]
- **OWN-04 Report overlap the harnesses cause on their own.** Some harnesses read others' folders, so an item can reach a reader the user did not select. Item detail names that reader [CD §4]. Excluding it uses a validated native filter (Appendix B); otherwise the exclusion switch is unavailable, with the reason. **Plugins in a shared store (section 4) follow the same rule:** per-reader exclude, Disable or uninstall stays unavailable unless a per-reader filter is validated (PLG-02, PLG-07), and a selected sibling's write is disclosed, naming every reader it reaches, including a marked mode (DET-01). **This covers an account route:** if the chosen Cowork route reaches Code sessions, neither a Cowork-only exclude or uninstall nor marking a mode is promised to stop effects on those sessions without a validated filter (V-06). Never fake an exclusion, claim an isolated removal or write trust state to resolve one. [E]
- **FIL-01** Recheck, stage beside the target, verify, rename atomically where supported. Failure leaves the last good state. Report per-destination results with retry. Commands use argument arrays and **a timeout on anything that runs Git**. Logs omit file contents. [E]
- **FIL-02** Edit targeted keys only, preserving everything else byte for byte. A file that cannot be edited faithfully becomes read-only with a report. Reread before writing. **Never use a native command as the write path where a preserving edit exists** [CD §3]; one run by the user counts as an outside edit. [E, VF §1]
- **FIL-03 Native plugin exception.** Where no preserving route exists, a native plugin or marketplace-registration operation may change what its command changes. A user-requested action discloses known effects first; an automatic registration, update, expansion or eligible waiting-selection install does not prompt. History shows a text diff after either. Nothing else gets this exception. [E, D-16, D-28b]

### 6.6 Conflicts and deletion

- **CON-01 Newest action wins.** Only for an item already syncing. When it changes differently at two locations before sync completes, the newest action wins at every destination, automatically and whole, never merged. A revision from a destination that cannot hold a field is the fields it can hold over the prior neutral record (MCP-01): that is adapter translation, not a merge, and competing revisions still win or lose whole. For a synced skill or MCP entry, a later deletion propagates removal and a later edit keeps and spreads the edited version. Where the order cannot be established, CON-04's accepted fallback decides instead. Agents follow this at destinations sharing both ways (D-32); a change at a one-way destination never competes (TRN-02). Identical revisions converge. No conflict dialog, per-item pause or approval. [I-21, D-32]
- **CON-02 Notice and undo.** Competing and earlier content enters recoverable history before the winner applies, including when deletion wins. Every automatic edit/edit or delete/edit resolution shows a non-blocking notice naming the item, the winning action and its location, saying whether the order was proved (CON-04), and linking to History and Undo or Restore. A resolution while the main window is closed sets a non-blocking unseen indicator on the tray or menu bar icon (D-36). The note is retained until seen, and the resolution stays in History's activity under retention (STO-04). None of this needs an OS-notification permission or an approval. Undo applies the losing side as a new action, which spreads normally. Identical convergence shows no notice. [I-21, I-22, I-30, D-36]
- **CON-03 Same-name collisions are not concurrent edits.** Different standalone skills or MCP entries under one name are unrelated items, so newest-wins never applies; MCP entries differ only in a field both readers can hold (SYN-06). First setup identifies them across the selected harnesses before writing to them, keeps every copy separate and unchanged, and shows the collision during setup with a diff. The user chooses **Share this version**, which replaces the other copies only after that diff, with replaced bytes in history and, where a limited MCP copy is chosen, the selected capable copy supplying retained fields (SYN-06), or **Leave separate**, which leaves each copy Not shared and can be revisited. Until then only that name's relationship is withheld: neither version spreads, the rows show **Needs a decision**, and unrelated items sync. The same protection covers a later harness selection, a later unrelated name or location collision and a Restore that meets a different item. A change of sync owner is not one of these (ORG-08); **Start fresh from current files** is first setup, so the full protection applies there. Agents follow the same rule (D-32). [I-26, I-29, E]
- **CON-04 Ordering evidence and its limits.** With two or more competing revisions, first discard every revision proved older than another; choose the sole remaining revision, or apply the unknown-order fallback only among those not proved older. This preserves established order in three-way and larger conflicts. CK sees files, not actions, so "newest" can only mean the newest its evidence proves (mechanics: D-04). Each change at a location has a conservative **observation interval**: from the last read that verified that location's baseline to the first read that verified the changed state. The action happened somewhere inside it, however CK came to look. The interval is ordinary sync state beside the baseline, with no new journal or platform.

  - **Order proved:** the intervals do not overlap, because CK verified one change and only afterwards read the other location still at its baseline. Adapter evidence can also prove order, but only where V-10 records that it establishes action order for that OS, file system and pair of locations; none is recorded yet. Newest wins.
  - **Order unknown:** everything else, including delayed or reversed event delivery, two changes before either was read or within one polling interval, and two changes made while CK was off. CK still resolves automatically and does not pause sync. **This is the user's accepted degraded outcome (I-21), not proved chronology:** the notice says CK could not tell which came first, nothing claims the winner was newest, and the alternatives stay recoverable. Delete versus edit keeps and spreads the edit, because a wrong keep removes nothing, and offers **Delete everywhere** (D-04). Edit versus edit takes a deterministic choice; the exact tie-break is proposed (D-04) and is not chronology.

  **Never evidence of action order:** a notification's arrival or position, which only prompts a read; scan, read or destination order; a modification time, because tools can preserve or set it and, in a shared file, it can come from an unrelated entry; and a missing file, which has no time. CK compares a shared file entry by entry against its last snapshot, so an edit to one entry neither changes nor dates another.

  CK starts at sign-in, runs with its window closed and keeps watching under Sync off, so gaps come mainly from Quit or automatic start turned off. Order that was never observed is not recoverable, and CK does not claim it. Reliability per OS: V-10. [E, I-21, D-04]
- **DEL-01 What counts as a deletion.** Distinguish a missing item from a disabled item, unmounted volume, unreadable root, malformed file, or a failed or transient listing. **A deletion is inferred only from a file read of a reachable root after the settle window, never from a missing harness, incomplete scan or native listing.** [I-22, E]
- **DEL-02 Propagation.** Deleting a shared skill or MCP entry in any harness, including at a With limits destination, or with **Delete** in CK, deletes it from its other synchronized destinations with no prompt, apart from the MCP-02 interim. It is a tracked change: content and destination state go to recoverable history, and a stale replica (proposed reading, D-37) never recreates the item. A destination unreachable at the time is deleted when it returns, unless it then holds an edit, which follows CON-01. An excluded destination's copy stays, and an observed-only `claude_desktop_config.json` copy follows D-11. Agents follow the same rule (D-32), except that a deletion at a one-way destination stays local and cannot delete the origin (TRN-02). Plugin uninstall follows PLG-07. [I-22, D-32]
- **DEL-03 Restore.** **Restore**, in History, restores recorded per-destination Disabled state without automatic re-enablement and returns the item to its selected, compatible destinations within retention and respects exclusions. It is a new revision that spreads normally, apart from AGT-03's local Restore of an agent replaced by Skill only and a Not shared item's Restore, which returns it only to its recorded location without enrolment. Meeting a different item follows CON-03. **On a build outside V-20's record** (ENB-01), a recorded Disabled state returns through its recorded switch, with the unverified-effect note; if that form no longer applies there, the destination stays unrestored with the reason and is never returned enabled. [I-22, E]

### 6.7 Disable and Delete

- **ENB-01 Disable is native or unavailable.** A destination offers Disable only where capability data records an effective, user-wide native switch for that kind and surface (Appendix B, V-20). Disable is best effort across builds: the tool's version (older than V-20's record, unreadable, or no CLI found) never withholds it; it is only noted next to the switch. A real blocker does (a settings file that can't be read or written, a switch that would also turn off other items, or a route whose command can't run). Elsewhere the destination stays unchanged and the control reads **Disable unavailable**, with a one-sentence reason. Never remove or relocate content to imitate disabling, use a project-level override, or fall back silently to Delete. Blocking only automatic model invocation is not Disable, and `hidden` is never called disabled. Build only the handling supported adapters need, not a fallback subsystem. [I-05, I-28, E]
  - **Partial Disable.** An item-level Disable applies at each destination that supports it, explicitly names every destination where the item remains enabled and shows those Disable unavailable with the reason, with no workaround there.
  - **After a build change** outside V-20's record (DET-03), Disable and Enable both stay on offer with a quiet note that their effect on this build isn't checked; each is confirmed by re-reading. A Disabled state already observed there stays, and nothing re-enables it. If the recorded form no longer reads as CK recorded it, Enable is unavailable with the reason and the destination stays unchanged. Neither case is reported as supported. Restore there: DEL-03.
  - **Shared location.** A native switch there acts for every reader and names them; per-reader Disable follows OWN-04 rather than pretending the sibling stays enabled.
- **ENB-02 What Disable preserves.** The item and its configuration stay. Disable does not propagate as a deletion, and nothing re-enables it automatically. It is destination state, not item content: content updates still arrive with the switch preserved, and **Enable** clears it. [I-28]
- **ENB-03 A native toggle inside a harness** shows as Disabled there and does not spread (D-12); an item already natively disabled when discovered, or Disabled at every current destination, follows the same proposal. [I-28, D-12, E]
- **ENB-04 A switch on a Not shared item or installed plugin** is an explicit targeted edit of that one key or native toggle, confirmed by re-reading, with Sync on or off. It creates no sharing relationship, and Enable reverses a native Disable. If the configured default is Delete (ENB-05), the switch on a Not shared standalone skill or MCP entry invokes the explicit Delete action at that location, with recoverable History; returning it uses Restore, not Enable. A plugin switch stays Disable/Enable, with Uninstall separate (PLG-05, PLG-07); instruction files have no turn-off switch (INS-02). [I-05, I-08, E]
- **ENB-05 Default action.** Settings holds the default action for turning off a skill or MCP server: **Disable** initially, or Delete if selected there. It does not reach agents, plugins or instruction files, or affect how new items install. **Delete** is otherwise a separate, explicit action that follows DEL-02. **With Delete selected, the switch on a shared skill or MCP entry is that explicit Delete** (owner only, ORG-08): the control names DEL-02's scope and adds no approval, and History's Restore recovers it (DEL-03). Native Disable stays local to its destination or reader group (ENB-01, D-18). [I-28]
- **ENB-06 Plugin-owned skills.** A skill belonging to an installed plugin is never deleted individually, whatever the default action. Its individual action is Disable, only where the harness has an effective override that leaves the plugin's contents unmodified; otherwise Disable unavailable, as a compatibility limit. Whole-plugin Disable is a visibly different action. Install and destination choices operate on the plugin as a unit, never extracting or separately deploying its children. [I-28]
- **ENB-07 New installs start enabled** at their selected, supported destinations, including an explicit Include under D-12. Automatic updates preserve a disabled state or exclusion and never treat an update as a new install. Enabled intent is not proof that a session loaded the item. [I-28, I-17, D-12]

### 6.8 Conversion: skills, MCP and agents

- **TRN-01 Every skill key, MCP field and agent field falls into one class per destination [CD §5], and the class decides the conversion. No class asks for approval.** **Representable** or source-only: Automatic. **Best-effort with a loss:** With limits, the field dropped or copied as-is, the loss named, and "Has wider access than the original" where a restriction is lost. **Unsupported:** skipped as Not available here with the reason, never an invented equivalent or a content scan. Route feasibility and evidence are separate questions (section 4). [I-07, I-11, E]
- **TRN-02 Direction.** A With limits item does not behave the same, and its limits stay in Item detail and show in the row. A byte-identical With limits skill spreads normally, and so does a structurally translated MCP entry, both ways and including deletion (MCP-01). **An agent translated with every field intact is ordinary two-way sharing (proposed, D-26):** where every field of the revision is Representable or source-only at that destination and a local translate-back check reproduces it [CD §5], an edit there spreads, concurrent changes follow CON-01 and deletion follows DEL-02. **A native-agent destination that loses a field is one-way (D-26):** it receives the origin's changes, but an outside edit or deletion there stays local. CK stops writing to that destination, shows why, spreads nothing and cannot change or delete the origin (any location holding every field) or another destination, and the destination then behaves as excluded (SYN-08). The test applies per item, destination and revision, and does not wait for V-07. It is structural: it never implies the pair behaves the same at runtime, which stays Unmet under V-07. Convert to skill is a separate snapshot (AGT-02). [I-07, D-26, E]
- **SKL-01** Copy the whole directory except nested `.git` byte-exact, preserving file modes where the OS supports them. **CK never rewrites a skill.** A byte copy is not a claim of equivalent behaviour. [I-11, E]
- **SKL-02 Metadata tolerance is per version** [CD §4]. A destination that would not load the skill as it stands is **skipped**, naming the missing field; others continue. Where a destination tolerates the gap, the bytes deploy with a limit noted. [E, D-25]
- **SKL-03 Loading is not no-loss.** Capability data records the effect of a finite key list [CD §4]. A documented or recorded loss of a listed key marks that reader's destination With limits, naming it, and keeps that class, with an evidence note, on an untested OS or build (DET-03). An untested effect is no loss: the route label stands, Item detail notes "effect not tested", and nothing claims equivalent behaviour (SKL-01). [E]
- **MCP-01** Translate structurally through a neutral record into each destination's shape [CD §5], in both directions. All configuration values copy verbatim, including embedded secrets, tokens, headers, URLs and environment values, with no scanning, redaction, omission or secret-specific warning or approval. **A destination that cannot hold a field speaks only for the fields it can hold,** when first met (SYN-06) and on every later edit, and such a field is never read as a change or removal. The neutral record and capable destinations keep the rest: if a destination with no tool allow list edits the URL, the URL spreads and the allow list stays, and if its copy is selected or shared first, or chosen under Share this version, the allow list at a capable destination is not wiped. Capable copies that disagree when first met: SYN-06. This is adapter translation, not a content conflict merge (CON-01), and MCP stays two-way, including deletion (DEL-02). External OAuth or login stores are not transferred, so a remote server may need sign-in: a next step, not a loss. [I-07, I-11, E]
- **MCP-02 `~/.claude.json` until V-09 passes.** The app and CLI rewrite this file, so a background write is not yet shown to be safe. This is a missing write proof, not an approval prompt. Until then, a Claude Code MCP destination shows **Not known yet** with **Write now**: "Close Claude first", then a hash-checked edit of that entry alone. A deletion reaching this file also waits for Write now. A server shared *from* this file spreads normally. The Codex-to-Claude-Code example stays Unmet until then. [E, I-07]
- **AGT-01 Native first.** Agents share automatically, native to native, where the destination supports the relevant mode [CD §5]. TRN-01 decides each field and TRN-02 the direction. Item detail shows each destination's real invocation modes and true losses, keeping personal instruction files, primary agents and subagents distinct. A translated agent keeps its route label (section 4), and Item detail adds an evidence note naming V-07 until that pair's runtime equivalence is proved; the note is not a label, and that outcome stays Unmet. [I-07, I-09, E]
- **AGT-02 Convert to skill.** An optional, explicit action for a destination without compatible native agent support, such as researched Pi 1.5.0. Setup, background sharing, discovery and new harnesses never create it. Until chosen, that destination stays unwritten with an explanation, and compatible native destinations proceed. The result is an ordinary standalone skill with recorded provenance (original agent, originating harness), shared normally minus the originating harness; the action shows those destinations, and any can be excluded. It is With limits and names true losses in isolated context, tool restrictions, model selection and invocation, never saying "agent installed" or claiming equivalent behaviour. It is a one-time snapshot (D-33), and **skill edits never write to any agent.** Apply DET-03 to build eligibility. Where the source agent format or destination skill route cannot be established, show Not known yet and perform no guessed conversion. [I-09, E]
- **AGT-03 Source-harness exclusion and explicit return.** A converted skill never deploys to its originating harness automatically, including through default-all selection, later harness selection or discovery. Placement avoids any root that harness reads; where a destination's only root is read by it and no validated filter exists, that destination is skipped with the reason. Only an explicit request deploys it there, offering **Keep agent and skill** (both stay) or **Skill only**: the skill replaces the source-harness agent, the original goes to recoverable history, and the choice is recorded so background sharing cannot recreate that agent. This is a local representation choice: it deletes nothing at other native-agent destinations and does not propagate as DEL-02. **Restore** of that original in History is the explicit reversal: CK lifts the recorded suppression, restores the native original at the source harness alone and leaves the converted skill there, the same state as Keep agent and skill. Like Skill only, it does not cascade: it spreads nothing and removes nothing, and the suppression and restored baseline are recorded together, so background sharing neither recreates nor re-removes either item. If another native-agent destination now differs, that difference follows CON-03. A plugin-owned original makes Skill only unavailable (ENB-06), and name collisions follow CON-03. [I-09, D-33]

### 6.9 Instructions

- **INS-01 Browse and customize.** View and edit instruction files in a plain editor at user scope, in each harness's view. A save shows the diff and rechecks the file hash. With instruction sync off, a save is a user edit; with it on, INS-03 applies. Each version stays recoverable. Whether the Copilot app reads its personal instruction file shows **Not known yet** under V-05, an open proof and not an unsupported feature. Its UI-set instructions are probably in `data.db`, which is not a write target, so for those the view points to the app. [I-05]
- **INS-02** The editor says **who reads this file and what happens next** [CD §6]. Instruction files have no Disable and are never deleted or emptied to simulate one. There is no universal system-prompt control. [I-05, E]
- **INS-03 Shared base.** Optional, off by default, with its own control, independent of Sync and of skill, MCP, agent and plugin sharing. Only the installation owning sync runs it (ORG-08). When on, the user edits one common base once, and it applies to every harness selected for it (selection list proposed, D-29). Each harness may have its own additions, kept separately, which reach no other harness's file. **Surfaces reading one physical file are one destination here too (OWN-03, OWN-04):** one selection entry, one composed output and one set of additions, naming every reader, with no new reader filter required. The UI makes clear what is common and what is harness-specific, and both are editable. [I-23, D-29]
- **INS-04 What must be true, however it is built.** No file layout, marker format, symlink scheme or editor is required. The personal instruction file each selected harness actually reads [CD §6] gives it the common base plus its own additions, a common edit leaves every addition intact, and no file outside the selection is written; any other reader of a selected file still reads it, and the editor names it (INS-02). Turning it on discards nothing: existing text stays in history, and before the first write the user sees what will be common and what stays harness-specific. Writes follow FIL-01. A direct edit in a destination's file is never silently lost (D-29). **A destination whose file is not shown to hold the composed result safely gets no composed write** and shows Not known yet (V-19), or Not available here where it has no writable file. Platform-supplied system prompts are never rewritten, replacement prompts stay out [CD §6], and no workspace or project file is read or written for this. [I-23, I-31, E]
- **INS-05 When off,** no instruction content moves between harnesses, and INS-01 and INS-02 work as usual. Turning it off deletes and empties nothing: each file stays as last written, and the common base and additions stay recoverable. [I-23, E]

### 6.10 Recipient setup, marketplaces and plugins

A Git repository, marketplace, installed bundle and running plugin are four different things, and a clone is not an install.

- **REC-01 Installing CK is enough.** For already-installed, authorized harnesses, normal choices stay in CK, and CK performs native marketplace registration, selected-plugin install and updates. **For v1, opening CK once after normal installation is acceptable (confirmed):** marketplace setup then runs automatically, with no terminal command or extra harness setup. No installer auto-launch is required and the later Iru end state is unchanged (ORG-09). Throughout, a normal install includes that first open, which is no recipient step. The recipient never registers a marketplace, uploads a plugin, clones, opens a terminal, edits configuration or installs another harness or CLI, and bundled content needs no repository membership (direct-source access: PLG-01). Organization publishing and hosting are separate. This holds even where a route lacks proof: with no validated automatic route the outcome is Unmet, and guided or manual steps never satisfy it. [I-24, I-17]
- **REC-02 Route choice.** Per destination, use the simplest reliable route that meets REC-01, respects user-wide scope and organization access policy, and works with bundled and downloaded content. No mechanism is mandated: a local server, Git service or UI automation appears only if the chosen route needs it. Nothing undocumented is promised before its proof passes. Candidates: [CD §7]. [I-24, E]
- **REC-03 Each surface and source route counts alone.** A Claude Code result never counts for Cowork or the reverse; a CLI result never counts for its desktop app; VS Code or GitHub Desktop never counts for the Copilot app; a direct-GitLab result never counts for an organization bundle or the reverse. A route requiring another product is no solution for someone restricted from it. CK detects every surface under DET-01 and manages only available or selected ones, never changing organization access policy, with no user roles or permission system. Treating a mode whose access is unknown as eligible is proposed, not confirmed (D-28c); an ordinary user-wide write there grants and bypasses nothing, claims no access and reports only its own evidence, with a shared reader's effects disclosed (OWN-04) and the private copy held (PLG-04). [I-01, I-16, I-18, D-28c]
- **MKT-01 Add by remote URL.** **Marketplaces works without completing first setup.** The user pastes the URL and optional ref; no prepared clone is required, and any internal fetch or cache is an implementation detail. The catalog comes from a read-only fetch that runs no repository content. A repository with no marketplace gets a plain message. An immovable ref, such as a tag or commit, is disclosed: it brings no automatic new source revisions, which is no version-pinning feature, and content updates arriving independently still apply. [I-01, I-14, E]
- **MKT-02 Browse.** One list per marketplace and, for a selected plugin, its components and their outcome per destination (Appendix D), with no single yes or no. [I-14, I-10]
- **MKT-03 Default marketplaces.** CK adds to its catalog the marketplaces each detected Codex and Claude Code provide, read from their configuration for that version, with no list of its own. ### 6.11 Organization builds

- **ORG-01 Build input and snapshot.** The normal build accepts an optional argument naming a GitLab or GitHub marketplace, documented for local and CI use, with no source edits or in-app build screen and nothing hard-coded to an employer or repository. **Standard build:** no optional input. **Custom (organization) build:** any optional input, with its own identity (ORG-07). **Bundled build,** or bundle: a custom build with a marketplace input. **The result follows from all optional inputs together,** not from that argument alone (feed, update location and branding: ORG-06).

  | Optional inputs given | Result |
  | --- | --- |
  | None | **Standard build:** no custom marketplace, private plugin content or feed; still browses marketplaces and adds the defaults |
  | App branding or an app-update location, no marketplace | **Unbundled custom build;** still browses marketplaces and adds the defaults |
  | Marketplace, no feed | **Snapshot-only bundle** (minimum behaviour proposed, D-35): builds and retains its embedded snapshot, with no feed requests |
  | Marketplace and feed | **Bundle with independent content releases** (ORG-05) |
  | A feed or marketplace branding with no marketplace, whatever else is given | **No build** (proposed dependency, D-35): stops with a plain input error that it needs a marketplace input (for a feed, one identifying its initial snapshot), rather than shipping a broken empty marketplace |

  A custom build's report and in-app Compatibility view state its app-update state (ORG-06), and a snapshot-only bundle's also state **Unmet: no content feed configured:** independent content and installed-plugin updates are not delivered (I-17). An authorized build environment packages a recorded snapshot of the catalog and installable content of **every marketplace plugin**, with no selection UI or policy engine, and external content referenced by entries is resolved during packaging. The build records an identifier naming the included marketplace and plugin release. A plugin that cannot be packaged is named in the build report as unmet. [I-16, I-17, I-25, D-35, E]
- **ORG-02 Build access stays out** of a build and a content release: the credentials the build environment used to fetch the source and its own checkout metadata, such as the fetch's `.git` directory and remotes. This concerns what packaging itself used, so nothing is inspected: configured catalog, feed and update URLs and supplied configuration and plugin content are never classified or omitted, and copy as-is. Recipients' independence from the source: ORG-03. [I-16, I-11]
- **ORG-03 Recipients.** The bundled marketplace appears in CK's Marketplaces, labelled with its snapshot, and after the first open (REC-01) CK automatically performs the applicable per-user native registration, with no sync ownership (ORG-08), so it appears in the native marketplace browsers of installed Copilot and Claude Code surfaces with no employee step. *(Proposed, inferred from I-24, D-16)* This also runs when an eligible surface is detected later (T-07), including one installed after CK's setup. Cowork follows COW-01. Registration writes to a detected destination whether or not it is managed for sharing, though never on behalf of a marked mode (DET-01), installs no plugin, changes no exclusion and enrols no standalone configuration. A registration the user removed natively is not remade until asked (proposed, D-16). No source membership, credentials, clone or runtime source connection is needed to browse and install; the private-network prerequisite applies only to the build environment and direct-source users. Whether a native route needs system Git stays V-17, with no bundled Git assumed, and any recipient dependency leaves installing CK alone unproved on that route. A plugin may have its own network dependencies, so this is no promise of offline execution. [I-16, I-24, I-26, D-16, E]
- **ORG-04 Install from a bundle** uses a native local-marketplace route where proven (V-17), from a location that survives app updates [CD §7]. Each destination stays Not known yet until V-17 records it. An existing same-name registration from a different source is never overwritten (report and next step proposed, D-16). [I-16, E, D-16]
- **ORG-05 Independent content releases.** A bundle can carry an organization feed URL (ORG-01). Later catalog and plugin-content releases have their own versions and update writable app-managed content, never the app binary, with no app rebuild per plugin release. Code, installation-identity and app-branding changes still need an application release; organization application updates are automatic and separate. Installed plugins follow PLG-09. [I-17, D-35, E]

  - **Self-contained result.** Recipients have no source access, so each applied release must leave them the whole catalog and every plugin's installable content (ORG-01, ORG-02), a technical inference; a full archive is one proposed way to package it (D-35). Any plugin that cannot be packaged is named in the publish report. A named failure is not a catalog removal (PLG-08): installed copies stay unchanged and that release offers no install of it.
  - **Activation (proposed, D-35).** The app stages a complete compatible release in writable app-managed storage and activates it without replacing its binary. A failed release, or one naming a newer minimum app version, leaves the last working content active and reports why. A release held for its minimum app version is re-evaluated after a compatible app update and applied with no recipient step.
  - **No rollback.** An application update never rolls content back: the newer of the active content and the build's embedded snapshot, by comparable ordering metadata (proposed, D-35), stays or becomes active, so newer feed content is never replaced by an older embedded catalog. *(Proposed, D-35)* A newer embedded snapshot becoming active counts as a release for PLG-08 and PLG-09: installed plugins update at their existing destinations, one no longer listed shows Deprecated, and disabled states and exclusions hold.
  - **Delivery is best effort for v1 (confirmed, I-17).** The final organization-specific update delivery need not use HTTPS, local HTTP is acceptable, and no exclusive transport, hosting arrangement or authentication method is selected. Organization-internal agents may complete or adapt it later, so deployment details are not release-blocking product requirements. **CK's part** is the client: reading the configured location, activating as above and reporting the result (D-35). **The organization's part** is hosting, reachability, access and publishing triggers, none known or prescribed here; the only constraint is that recipient access never requires source-repository membership. A gap stays explicit (REL-01), never claimed as delivered. Native install, load and update routes (REC-01) and every proof gate are unaffected.
- **ORG-06 Branding and update inputs.** Optional build inputs set the content-feed URL and an organization app-update location independently: the feed carries content, the location carries the application binary, and neither stands in for the other (combinations: ORG-01). Branding inputs set the application's display name and logo and, independently, the bundled marketplace's. An omitted input keeps standard branding: Central Knot's for the app and, *(proposed)*, the catalog's own name with no custom logo for the marketplace. A native registration's identity stays build-fixed (proposed, D-16). **Automatic application updates are confirmed for bundled distribution (I-17), so omitting the location there never waives them;** applying the same obligation and reports to an unbundled custom build is proposed (D-19). **Minimum behaviour (proposed, D-19):** a custom build with no location, or no identity-correct route proven on that OS, still builds as an ordinary internal or staging build and claims no automatic application update or met recipient requirement. Its build report and in-app Compatibility view keep the two apart: no location is **Unmet: no app-update location configured**, which a passed V-10 does not change; a configured location with no proven route is **Unmet: V-10**. The location's hosting and access follow ORG-05's best-effort delivery. [I-25, I-17, D-16, D-19]
- **ORG-07 Separate installations.** A custom build, including an unbundled one (ORG-01), has its own installation identity and settings, installs side by side with the standard app, and updates never replace one build with the other. It never uses the standard app's update channel, whatever its update state (ORG-06). A changed display name alone is not an identity. [I-25]
- **ORG-08 One background sync owner.** Separate settings do not isolate harness files, so only one installation, standard or custom, runs standalone sharing and instruction synchronization at a time for the same user's harness configuration. An uncommon safety case, mainly in development, with no multi-instance management system. All mechanics are proposed (D-31). [I-26, I-08, I-09, I-22, D-31, E]

  - **Not covered.** Each build registers its own marketplace and runs its own plugin automation (ORG-03, PLG-06, PLG-09) with no Take over syncing, preserving exclusions and Disabled states. Those operations and the owner's sharing writes can touch one file, so they must not race there: every build coordinates each CK write or native operation, bounded by a timeout, and rereads first (FIL-01, FIL-02); a blocked one retries and reports per destination. Unrelated apps stay outside this, and it proves no runtime safety (V-10).
  - **Take over syncing.** Offered when another build is syncing, it transfers ownership with no overlap and leaves the previous app running but not syncing. Ownership never moves by itself. *(Proposed, D-31)* If the last owner is not running, the app says standalone sharing and instruction sync are inactive and offers the same action.
  - **A non-owner,** meaning a build that finds another recorded owner (none recorded: D-31), names it and whether it is running. It keeps browsing, Item detail, marketplace and plugin work, and explicit targeted actions that change no sharing state: an instruction file save (INS-01, D-29) or a native Disable or Enable at one destination (ENB-03, ENB-04), which the owner treats as outside edits. It shows read-only, with that reason and Take over syncing: Share, Don't share, destination exclusions, Sync, Sync now, Write now, collision choices, Delete, Undo and Restore, Convert to skill, and instruction sync's switch, selection, base and additions. Its own harness selection starts no sharing. No row says Not shared for that reason alone (UX-04).
  - **Sync state carries over.** Taking over or handing back restarts and reopens nothing. The new owner continues from the last owner's authoritative sync state, never an older baseline of its own: item identity, destination bindings with baselines and revisions, standalone harness selections, the Sync switch, instruction sync's switch, selection, base and additions, deletion records, pending changes, effective Disabled states, exclusions and Don't share, Leave separate, one-way stops, conversion provenance and source exclusions, Skill only suppressions, and the history Undo, Restore and suppressions need within retention. Changes made meanwhile reconcile under SYN-05, CON-01, CON-04 and DEL-02 (a direct instruction edit: D-29): a real one-sided deletion propagates, and unknown-order edits take the accepted fallback automatically. No stale replica recreates anything, no setup choice reopens, and CON-03 applies only to a genuinely new or unrelated relationship. App preferences do not move and, *(proposed, D-31)*, neither do plugin selections, so a transfer adds no plugin destination or tick (PLG-06). An owner returning with no transfer keeps its own baseline (SYN-05).
  - **Blocked.** If that state cannot be read or overlap cannot be ruled out, ownership stays put, no sharing write runs under an invented baseline, and marketplace automation continues. The app gives the reason and Retry, and how to recover where that is possible, such as opening the last owner.
  - **Start fresh from current files (confirmed, I-26).** Only where sync metadata is permanently lost and no previous owner remains (test: D-31) does the app add this explicit action beside Retry: never while a prior owner runs or overlap cannot be ruled out, never by itself, and never as a shortcut for an ordinary takeover or handback. It first explains that lost exclusions, conversion choices and history cannot be recovered, then shows the first-setup preview (SYN-01, D-01); no sharing write runs until the user presses Start. Current harness files are then new setup inputs (SYN-01, SYN-06, CON-03) with no invented or stale baseline: an identical item is taken over with zero writes, different items under one name stay separate for a choice, a missing copy is no deletion, and a copy on disk is a current item, whatever the lost state recorded. Instruction sync stays off until turned on again. Nothing claims old relationships or choices were restored. Plugin selections, exclusions and marketplace automation are not part of this state and continue unaffected; only a harness this build newly manages counts under PLG-06.
- **ORG-09 V1 and end state.** Iru deployment and the fully managed rollout are the end state, not v1, and v1 builds no dedicated Iru integration. V1, the first release, proves with CK installed normally (REC-01) and without Iru or tenant access: native marketplace registration, then a selected plugin installing and loading. ### 7.1 D-16 (proposed): plugin policy and native registrations

Nothing here overrides an exclusion, an uninstall or a Disabled state: expansion writes only its new destination, enabled (ENB-07). Automatic plugin updates and expansion run independently of Sync; independence from sync ownership is confirmed (ORG-08). Native operations follow FIL-03.

- **Policy at Install.** A plugin keeps the policy recorded at Install. The all-compatible default records Default policy, which expands on PLG-06's triggers (later management and newly established compatibility are proposed here); unticking one destination keeps it, with that exclusion. Explicit Only these destinations sets Restricted policy, which never expands.
- **Changing the default** affects later Installs only, including Install again after uninstalling everywhere. An Install under a default narrowed below all compatible records Restricted policy.
- **Expansion switch.** One global switch. Off, no plugin expands, though a waiting selection still applies (D-28b). Turned back on, a compatible destination with no record and no exclusion counts as new, while an unmanaged one already known at Install still waits to be managed or included.
- **Disabled at every current destination.** A Default-policy plugin still expands, enabled at the new destination only, unlike D-12's standalone rule. The user has not decided this.
- **Installed natively before CK.** A user-scope plugin found installed from a marketplace in this build's list, with the same source (MKT-07), is adopted there with no native write: PLG-09 updates it and CK records Restricted policy, so nothing widens automatically. An explicit Install can change that. A plugin from any other marketplace gets no automatic update.
- **External uninstall.** Removing an installed destination is its uninstall. Only a complete successful read of a detected harness's reachable root, whose record or declaration no longer lists a CK-installed or adopted plugin, records that destination's external uninstall (on an account route, V-15's observation). No uninstall or exclusion is inferred from a missing root or harness, a failed or incomplete read, an unreadable location, or files purged behind a surviving record (PLG-03).
- **Excluding an installed destination.** PLG-02's named Uninstall is inferred from the uninstall rule, not a stated choice.
- **Relisted plugin.** A later complete listing clears Deprecated (PLG-08), and updates resume, keeping exclusions and Disabled states.
- **Later surface.** Registering on an eligible surface detected later (ORG-03) is inferred from the no-employee-setup outcome, not a stated choice.
- **External removal of CK's registration.** The same read test, with a registration CK made no longer declared, records an exclusion from re-registering there until an explicit request (**Register again**, or an Install there); a missing root or harness or a failed or incomplete read infers nothing. Installed copies stay, and each affected update reports that reason and next step.
- **Registration identity.** The identity a native registration uses is fixed per build: marketplace branding that changes it needs an application build, and a content refresh never silently renames a registration. A release can still change catalog display text.
- **Removing a self-added marketplace from CK's list** changes that list only: native registrations and installed copies stay (MKT-07), and Item detail says CK no longer updates them.
- **Same name, different source.** Nothing is overwritten or replaced (MKT-07). The destination reports Couldn't update, naming both sources, with informational next steps: remove the other registration with that harness's own controls where known, then **Retry**, or ask whoever publishes this build for a different marketplace name (ORG-06). Recipient-native cleanup and Retry do not satisfy REC-01: the original fixture's automated recipient outcome remains Unmet. A publisher-corrected build is a new fixture; a future CK-contained resolution must independently meet REC-01 through a validated route.

### 7.2 D-31 (proposed): sync ownership and transfer

Mechanics for ORG-08's outcomes, including owner-not-running handling, with no service, queue or multi-instance platform. Only separate installation identity and settings are confirmed (ORG-07); how stores are arranged is proposed and can change.

- **Stores and carried state.** Each installation keeps its own content store. The owner also keeps ORG-08's carried state, which is nearly all sync state and its history, current with each baseline change in a versioned per-user location other builds can read; they read no other installation's store. App settings and plugin selections stay outside it. A missing, incomplete or unreadable-format copy, or a running owner that cannot confirm it stopped, blocks the transfer.
- **Owner.** The last owner's installation identity persists across sign-in, so startup order never moves ownership, and a build that has seen an owner remembers it in its own store, so lost state never reads as no recorded owner. A fresh build with no recorded owner runs first setup normally, and the first to finish it becomes owner; waiting, the notice and read-only controls apply only on finding another recorded owner. After that only Take over syncing or Start fresh moves ownership, even if the previous owner is no longer installed.
- **Selections.** Standalone selections carried with sync and this build's plugin selections are separate lists: a draft policy, not a technical limit (PLG-06). A transfer changes only the first, this build's own deselection (D-18) also drops the harness from the second, and neither expands an existing plugin.
- **History age.** Transferred history keeps each record's original date and ages under the new owner's retention setting (STO-04), with no silent reset.
- **After a transfer.** A former owner runs no sync and, on handback, adopts the current carried state over its own baseline. A harness the new owner's own setup selected runs afterwards as a later selection (SYN-07). A non-owner's targeted actions are outside edits to the owner (FIL-02).
- **Permanent loss (Start fresh test).** The carried state is still unusable after Retry, no owner is running, overlap is ruled out, and the last owner's installation is gone or is this installation with its own state unreadable. A last owner still installed elsewhere is recoverable: opening it rewrites that state or offers Start fresh itself. Completing Start fresh writes new current state, so old state or an installation that returns later is stale and follows the former-owner rule.
- **Shared-file coordination.** A per-user lock held only around one CK write or native operation, whichever build runs it (ORG-08), with a timeout.

- **T-08** Polling fallback interval (SYN-04) ≤30 s.

## 10. Scope

**Excluded or not requested by the user [B, UD]:**

- Secret scanning, classification, redaction, filtering, omission, vaults, credential portability machinery, secret-specific warnings or approvals and policing skill content (I-11).
- Workspace, project and repository configuration of any kind, and project overrides as workarounds (I-31).
- A general public marketplace-hosting service or any new platform. A local Git/manifest service inside CK remains allowed only if REC-02's validated integration route needs it.
- Installing plugins the user never selected; plugin install on adding a marketplace; automatic agent-to-skill conversion; reverse skill-to-agent writes.
- Synchronizing instructions while their control is off; rewriting platform-supplied system prompts.
- Enrolling a harness for sharing without selection; treating an unmet proof as passed.
- Version pinning, profiles, a policy engine, user roles, a multi-instance management system; changing organization access policy; configuring or connecting a VPN.
- In v1: Iru integration, tenant access or a managed rollout. Application code at this stage.

**Proposed exclusions (unconfirmed):**

- Requiring an organization-operated marketplace server for content releases, which follows from the proposed manifest-and-archive mechanism (D-35). Feed hosting, authentication and network prerequisites are not excluded: they stay each organization's best-effort deployment details (section 12).
- Plugin-only repositories; a private clone wrapper; extracting components from a plugin into standalone items, apart from explicitly requested Convert to skill (AGT-02/03), which never modifies the plugin-owned original.
- Cross-machine sync, hosted services, store remotes, WSL deployment, and harness, model, permission and theme settings.
- Per-field per-destination overrides, symlink deployment, a rename manager, a general skill, MCP or agent editor.
- Hook and command sync or conversion; a universal plugin executor; rewriting a plugin's `.mcp.json` for Codex, without which a `${CLAUDE_PLUGIN_ROOT}` server has no route to Codex.
- IDEs beyond VS Code; GitHub Desktop as a destination; T3 integration; ChatGPT hosted plugins; cloud agents; rewriting scripts; installing skill dependencies.
- Plugin authoring; a general Git GUI; installing or upgrading harnesses, apart from PLG-04's private copy if proven; running-session detection; MCP connection tests; repairing harness data.

## 11. Minimal architecture (proposal, not a mandate)

One local app: one UI (Electron is a candidate), one sync engine, a read-only marketplace reader, six small harness adapters, thin platform adapters, a bundled capability data file keyed by version and OS, and one build and publish step. Rejected as avoidable: plugin framework, database server, separate daemon, rules language, profiles, marketplace service. Route helpers: REC-02.
