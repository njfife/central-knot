# Map of the code

Read this first. Each area says what it is for, its files (one entry each: what the file owns; every source file is under `src/`, every script under `scripts/`), where to start reading and where its worked examples are (tests); then the paths that cross areas, names that mean two things, and where the recipes for common changes are. `tests/map.test.ts` fails when a file is added, renamed or removed and this map is not.

**What the app is.** Central Knot is an Electron app (plain TypeScript and the DOM, no framework) that moves AI coding tools' configuration (skills, MCP servers, agents, instructions, plugins) between the tools in one home and keeps it in step: Claude Code, Copilot CLI, Codex, Pi, OpenCode and Antigravity (a "harness" in the code, `types.ts HarnessId`). `main.ts` is the main process, which runs the engines (files, the tools' CLIs) and the background pass; the window starts at `renderer.ts`; the two talk only through `preload.ts`. What it keeps about a home is in `.central-knot/` inside it; its own settings and log are in the app's data folder (README's "State").

**Two ideas to hold.**
1. *Items live in Central Knot's library and are applied to the managed tools.* A tool is where an item is applied, not where it lives, and every content is kept before anything is written over. The model is `library.ts`'s header.
2. *Skills, MCP servers and agents are all on the library.* The Library and a tool's tabs read all three through one shape (`itemrow.ts kindSource`). Putting a kind onto the library is the recipe in `librarypass.ts`'s header.

## Word search

- `main.ts` the main process: window, menu bar, the tray icon (`makeTray`: none on a Linux desktop without a system tray, where closing the window quits and a start at sign-in shows it), folder watching, the background pass, settings storage, every IPC channel (the Plugins page's handlers are `marketplaces.ts registerMarketplaces`) · `preload.ts` the page's calls into main (`types.ts DesktopApi`)
- `homepass.ts` what one pass does, in order, at start and at every look (`homePass`): a profiles file from before moved, plugin parts from before moved (`partsmigrate.ts migrateParts`), a plugins record that knew fewer tools brought forward (`pluginrecord.ts bringForward`), then with Sync on skills, MCP servers and agents; what it tells the page, every kind alike (`passTells`); and what a person would see of the home as it read it, as one value (`pageSees`)
- `signin.ts` Start at sign-in, and on Linux the desktop's files it keeps for itself (the autostart file, the launcher entry and its icon) · `machine.ts` how this computer, its home and keys are named, whether it writes a real home (`writesRealHome`), and the `/` path display rule (`displayPath`, `shownFromHome`) · `trayicon.ts` the Mac's menu bar icon (elsewhere the tray shows the colour app icon: `main.ts makeTray`) · `index.html` the window's frame
- `places.ts` owns the window’s list and cursor, records the drawn place (`fullPlace`) as a visit after `app.ts noteMove`, as Back to the visit before after a page's own Back control (`noteMove('back')`: `stepsBackTo`), or a repair otherwise, and opens it on Back or Forward; and each visit's scroll place, kept as the person leaves it and put back after each draw from Back or Forward until something else moves it (`putBack`, from `renderer.ts renderWindow`; on screen, `scripts/e2e.mjs backPlaceFlow`) · `visits.ts` has the pure operations for a visit, repair and traversal.
- `renderer.ts` the page's entry: sidebar, header, status bar, which page draws (`renderPage`); a redraw replaces a text field and its Undo, so the fade with nothing to clear and a Git repo read that changes nothing draw nothing, and the window's focus draws again except while an editor's text area has it (its header says where); a redraw puts every scrolled element with an id back where it was, a page's scroll area or a box in it, whose id names what it shows, so other content starts at its top, and a text field only while it holds the same text (`scrolledNow`); a result is drawn in one place: on a list page (`matrix.ts resultInHeader`) in the header's own two lines, whatever it holds, so it covers and moves nothing (`resultHere`, which says the rule: `matrix.ts listResult`, and `pluginspage.ts pluginsResult` on Plugins and a tool's Plugins tab under Harnesses), its sentence then its first reason, as a problem line (`matrix.ts problemLines`), each cut to its line, the whole of it on Show all (`matrix.ts wholeToggle`) as a card over the page, closed like a menu by Show less, ×, Escape or a press that begins outside it (`foldResult`), a newer result showing folded. Beside it, the list's sync notices in the same 48px (`matrix.ts headerNotices`): Notices, counting them, marked and filled while one is unseen; the newest in the two lines while no result has them, said as an automatic change, marked as it comes (`matrix.ts noticeLine`); every notice with its actions in the card Notices or that line opens (`matrix.ts noticesCard`), where an Undo or Turn it on says what it did in its notice's place (`matrix.ts noticeLines`), one card at a time (`app.ts state.shownWhole`). What wasn't done is said first (`words.ts notAllThrough`, `app.ts notDoneFirst`); after what went through, the tools still reading an Off skill another way and the items waiting for a choice of copy, one click's and a run's alike (`app.ts stillRead`, `libraryrow.ts stillReadWords`, `libraryrow.ts copiesDiffer`). A new result (a click's, a run's, an Undo's, Sync once's) keeps its own reasons and none older (`app.ts keepOwn`); with none on show, what the background passes could not do, a failed removal only while it is still owed (`matrix.ts backgroundProblems`). An open card stays, its scroll kept through a redraw (`scrolledNow`); a folded result with no problem goes by itself after 8 seconds (`app.ts FADE_MS`). On every other page in a band above it, each reason a line of its own (`matrix.ts outcomeBand`) · `app.ts` the page's state and most pages' actions (`applyClick`, `queueClick`, `restoreEvent`, `tell`; `profileEndedLine`, via `profilesBefore` and `profileplan.ts endedProfiles`, is the one helper that gives `words.ts profileLeftUse` when an act ends every profile in use, called by `withProfileEnded`, `pluginstate.ts act`, `pluginstate.ts runEnded` and `pluginstate.ts sayResult`, drawn by `matrix.ts profileSpan` in `matrix.ts listResult`, `matrix.ts resultLine` and `pluginspage.ts pluginsResult`)
- `settingspage.ts` Settings (standing row explanations in `dom.ts infoMark` cards; live counts, warnings, download estimates, faults and `role="status"` progress lines on the page), History's retention state, warning and save shared with History (`historyWindowControl`, `openHistoryWindow`), the open home's Synchronize everything row (switched by `everything.ts setSyncEverything` through `app.ts switchSyncEverything`, showing its result band with History's Undo via `app.ts restoreEvent`, counted by `setupcounts.ts whatYesDoes`), the log shown under its row (`showLog`, read by `main.ts readLog`; written by `main.ts log`), and the note at its top that the settings file couldn't be read at launch (`keptNote`; read and kept aside by `main.ts loadAppSettings`) · `style.css` every style · `dom.ts` the `h` element builder and small controls; the app's collapsible fold (`fold`), detail mark and top-layer card (`infoMark`, `infoCardId`, `cardPlace`, `closeInfoCard`, `syncInfoCard`, placed on open, scroll, resize and after redraws); a press and its release (the pointer's, or Space's on a button) as one click when a redraw replaced the control between them, and a press on a text as a click or a drag (`keepClicksAcrossRedraws`, `pressWasDrag`); what a redraw keeps of what is selected: a selection inside one text with an id, or the focused field's caret (`keepSelection`) · `icons.ts` the glyphs · `brand.ts` each tool's mark
- `types.ts` the shapes main and the page share · `words.ts` tools' and kinds' names, a command and its arguments as one line (`commandLine`), the on-screen names of the plugins' and sources' pages (`pageNames`), the switch's words from outside a row (`turnIt`: "Turn it on"), lists in words (`touchedTools`, `toolsPhrase`) · `model.ts` small helpers: times, counts, paced calls · `flags.ts` per-viewer flags
- `pagedata.ts` a page's own read, apart from the home's · `diff.ts` line and word diffs
- **Start:** `renderer.ts` for the window; `main.ts`'s handlers for what a call does. **Examples:** `tests/signin.test.ts`, `tests/settingspage.test.ts`, `tests/pathdisplay.test.ts`, `tests/words.test.ts`, `tests/model.test.ts`, `tests/pagedata.test.ts`, `tests/homepass.test.ts` (what a pass of the whole home says a person would see); every page opened in `scripts/e2e.mjs`, and a change made outside reaching the page without a Refresh in `scripts/e2e.mjs staleFlow`.

## The store and safe writes
What every engine stands on: `.central-knot/` and its record, the gates on writing, and writes that never lose a save made meanwhile (but for an unlocked save in Claude Code's file, replaced in place: `share.ts writeFileChecked` `inPlace`).
- `share.ts` the store: the home's record, which names a build and holds the tools left out and Synchronize everything (`readRecord`, `SyncRecord`; only `takeOverSync`, called from `main.ts takeOverHome`, rewrites the build it names), whether the record lets this build write (`syncGate`: its folder must allow writes and its generation must match when remembered; a wait for Resume this build holds in memory: `ShareContext.resumeFirst`), whether this window may write at all (`writeAccess`: never while held, `ShareContext.held`), the gate for library writes (`libraryGate`; its header says which writes ask it, and which don't; letting a write in, asked any way, it first lifts a format 2 record to the record's format, `FORMAT_VERSION`, at which an earlier build stops syncing the home; the Plugins page's writes ask the same lift: `liftFirst`), checked writes (`writeFileChecked`; on Windows a rename, link or removal another program holds up for a moment is tried again for about a second, `retryWhileHeld`), whether a folder can be written (`folderAccess`: on Windows the folder itself opened for writing, once a pass) and whether a refusal is a denial of permission (`denied`), a file of Central Knot's own that can't be read kept beside it (`keepUnreadable`), a skill's folder copied (`placeCopy`), one file's text for a file panel, at most 1 MB (`shownText`)
- `textedit.ts` one entry of a JSON or TOML file changed, every other byte kept, and read-only spans for cutting one out (`jsonStart`, `members`, `memberAt`) · `values.ts` untrusted values checked, with safe defaults
- **Start:** `share.ts`'s header, then its exports, by their comments; a skill's copy is written over by `skillfiles.ts swapFolder`. **Examples:** `tests/share-recovery.test.ts`, `tests/heldfile.test.ts` (on Windows, a file held open a moment, held for good, read-only, or saved while the write waits), `tests/textedit.test.ts`, `tests/skillsafety.test.ts`, `tests/librarygate.test.ts` (the gate for the clicks that write before their pass, and the record's format lifted; in a whole home an earlier build wrote, `tests/upgrade.test.ts`).

## Test and tour scripts
How each is run: `AGENTS.md` ("Checking a change") and README ("For developers"); the Mac run is `scripts/mac-run.mjs`, which `.github/workflows/mac.yml` runs (after `scripts/mac-guard.ts`, and with a last step that removes its temporary folder under /private/tmp, empties release/ and stops what it left running; and `.github/workflows/mac-hosted.yml` on a GitHub-hosted Mac, by hand, not yet the run that counts), the Linux run `.github/workflows/linux.yml`. Unit tests are `tests/*.test.ts`. Every script that opens the app names a stand-in for /Applications, the running apps and the Trash (`tests/macstandins.ts`, set as CK_TEST_APPS: `platform.ts macPlaces`), so none looks at or removes the real ones; off a Mac, where there are none, `scripts/e2e.mjs` names one only in its flows about another build.
- `scripts/e2e.mjs` the end-to-end checks on the real app in a throwaway home, every flow in one of its `groups`, a run being one copy of the script per group (`runGroups`) · `scripts/ui-tour.mjs` the screenshot tour · `scripts/cdp.mjs` the DevTools client the scripts drive the app with, the wait for an AppImage's mount to go (`mountsGone`), and the one way the scripts name an item list's row or its elements (`rowPart`) · `scripts/scratch.ts` a script's throwaway folder, removed with what it started however it ends but by SIGKILL (`scratchFolder`, `launched`), and an app's temporary places (`tempPlaces`)
- `scripts/fixture-market.mjs` a realistic marketplace · `scripts/git-http-fixture.mjs` Git repos served here · `scripts/update-fixture.mjs` a stand-in for GitHub's releases
- `scripts/mac-run.mjs` the Mac run: the unit tests, the packaging, the light tour, the bundled and alpha checks and the end-to-end checks, what runs beside what and why (`phases`) · `scripts/mac-guard.ts` the run's check before npm ci: it waits while the Mac is short of memory, swap or disk, then fails in one line (`LIMITS`, `roomToRun`)
- `scripts/update-proof.mjs` a real signed update, on a Mac · `scripts/alpha-check.mjs` the alpha beside the standard app · `scripts/bundled-check.mjs` a bundled build end to end
- `scripts/real-home-trial.ts` the two-way trial on a real home its owner opened for it
- `scripts/windows-check.mjs` the Windows CI helper (`.github/workflows/windows.yml`): packages the Windows preview for `--smoke` and runs its smoke test, then `tests/launch.test.ts` under the packaged app's own Node; and runs the advisory unit test files not on `tests/windows-strict.txt` (`--advisory`, streaming the log and combining the strict log into the summary via `parseUnitLog`) · `scripts/windows-check.d.mts` windows-check.mjs's types
- `tests/spawnlog.mjs` a record of every program the unit tests start or stop (the program, its arguments, every option, the environment it was given, the stops, the stand-ins' bytes) and every file they rename, link, unlink, rm or writeFile (the paths, the options, the error's code), loaded with NODE_OPTIONS on two trees and compared (`compare`): how a change proves macOS and Linux start and write what they did before; its worked examples are `tests/spawnlog.test.ts`

- **A plugin's other clicks** (Update, Update all, a skill's switch under Skills, and their Undo; the record doesn't change): the click → `pluginstate.ts applyPluginOps` → `pluginplan.ts runPlan` → the handlers in `marketplaces.ts registerMarketplaces` → `plugins.ts update`, `plugins.ts setSkill` or `marketplaces.ts items` (its items read again: `pluginlibrary.ts runItems`). Both routes set `pluginstate.ts market.lastRun`, which the header says with one Undo (`pluginstate.ts undoLast`).
- **An item list's switch for a plugin's item:** `app.ts runSwitches` (`pluginswitch.ts` works out the steps; a plugin's row's own switch waits its turn in the page's list: `app.ts queueClick`). Whole-plugin turns for listed plugins go through `plugins:turn` → `marketplaces.ts turn` and write the record (undoing via `marketplaces.ts undoTurn`), while per-item switches and unlisted plugins use each tool's own switch, with their Undo in the header's result.

## Names that mean two things
- **A kind:** `app.ts PageKind` is a page's name for it (agents), `library.ts ItemKind` the library's and a profile's (agent), `presence.ts HomeKind` every kind a home can hold, with a sidebar row (the Library's three share one) or a page (instructions, plugins); `librarypass.ts Kind` is what a kind implements.
- **A source:** `library.ts LibraryItem source` is the id of a source the home records (`sourcestore.ts SourceRecord`); a version's `from` is a `library.ts Origin` (`how: 'source'`: read at one). `library.ts SourceSeen` is one read of a source as its table reads it, `librarypass.ts SourceRead` the same of one kind, with each item's content and its kind's Merge, as the pass is given it, and `types.ts SourceFound` the same as the page shows it, every kind's lines together (`types.ts SourceName kind`). An item there that can't be read is "unreadable" (`library.ts AtSource`), never a harness's `unseen` copy; one read and not brought in by a rule is `leftOut` (`atlink.ts ItemThere`), which holds back no drop.
- **An item's key:** `library.ts itemKey` of its name (also exported by `share.ts`); a profile names an item by its kind and key, `skill:notes` (`profileplan.ts itemId`), and a plugin's item by `plugin:` before them, `plugin:skill:document-tools@team-tools/pdf` (`profileplan.ts pluginItemId`). A plugin's item's plan key, the same for each tool's copy installed and placed in Pi, OpenCode and Antigravity, is `profileplan.ts pluginItemKey`'s, `document-tools@team-tools/pdf` (a skill by its folder, or for a plugin that is one skill the plugin's name; an agent by its file; an MCP server by its name); the name a tool's switch takes is each copy's own `name` (`types.ts PluginItem`). The Library's rows of a plugin's items are grouped by name, not by it (`pluginrows.ts pageRows`).
- **A part:** a piece of a plugin installed whole, its skill, MCP server or agent (`types.ts PartKind`, `PartRef`, `partswitch.ts`, the steps `part-on` and `part-off`); in the library, the shared part of an item's content and each tool's own part (`library.ts`'s header, `kindstore.ts keepOwnPart`, `mcp.ts OwnPart`). The separate copies 0.6.0 alpha 1 wrote of a plugin's parts survive only as the record `partsmigrate.ts` moves.
- **A switch:** `skillswitch.ts` and `mcpswitch.ts` are a tool's own off-switch for a skill or a server (never the item's On/Off); `partswitch.ts` the same for one part of a plugin; `pluginswitch.ts` the item lists' switch for an item a plugin brings; `plugins.ts setSkill` one skill of a plugin.
- **On, Off and managed:** an item is On or Off and kept out of the harnesses in `except` (`library.ts LibraryItem`), and a click (`types.ts Change`), a row (`types.ts LibraryFacts`, `itemrow.ts ItemRow`) and History's Turn it on/off say it so. A tool's own switch that has it off there is `switchedOff` (`types.ts LibraryFacts`, `library.ts FoundCopy`, and the row as it is: `libraryrow.ts LibraryRow`, `itemrow.ts ItemRow`), worded by `libraryrow.ts`'s sentences. "Managed" is a tool Central Knot manages (`presence.ts managedTools`, its Manage switch). Where the old words stay, each is stored, shown or another area's: `off` in the records from before the library, which the migrations read (the tools an item was left out of), and plugins' `off` (`types.ts ThroughPlugin`, `plugins.ts ToolPlugin`: turned off in that tool); "managed" in History's `TookOver managedNow`, the Git repo's Managed set and `unmanaged` (an item in the tools, not in the library), the CSS classes `.unmanaged` and `.ov-managed`, and the page's sentences.
- **Found, own copy, deleted:** found is a key the library holds no live item for (`library.ts`'s FOUND table, the item lists' Found heading; History's cause and a version's `Origin` `found`: taken in from one). A copy Central Knot never applied, in a harness the item is Off or kept out of, is that harness's own copy (`library.ts Plan ownCopy`, `libraryrow.ts HarnessIs` and History's cause `own-copy`). Deleted is an item deleted from Central Knot (`LibraryItem deleted`, History's kind `deleted`); a copy deleted by hand in a tool is `deleted-by-hand` (`types.ts ItemNotice`, `libraryrow.ts HarnessIs`, History's cause), where the tool had it only through the shared folder, its copy there or its link to it (`sharedWay`, said by `words.ts deletedIn`).
- **History:** stored for every kind by `history.ts`; worded by `historypage.ts`, except skills', MCP servers' and agents' entries, which `historyactions.ts` words.
- **First setup:** `setSyncEverything` is the engine's (`everything.ts`) and the page's call to it (`types.ts DesktopApi`); the Settings row's action is `app.ts switchSyncEverything`, the question's `firstsetup.ts`. "Latest" is three: `library.ts latestCopy` (of found copies that differ: contents tied by their copies' times are told apart by their files' own times, `skillfiles.ts SkillCopy filesAt`; a tie by both is no latest), `library.ts latestEdit` inside `plan` (of edits to an item in the library: a tie goes to the first tool, and the plan says no time decided: `Plan orderProved`), and the take-in answer's `latest` field (latestCopy's answer, read by the copy question and the walkthrough; beside it `datedByFiles`, the files' times where they told it, which the copy question's lines say).
- **Sign-in:** `signin.ts` is Start at sign-in, the app starting when the person signs in to the computer; `mcpsignin.ts`, `mcpsigninrun.ts` and `mcpsigninpage.ts` are each MCP server's sign-in in each tool, as the tool reports it.
- **One name, two things:** `Outcome` (`app.ts Outcome` a result the page tells; `types.ts Outcome` a plugin component in a tool), `standing`, `toggle`, `updateButton`, `Waiting`, `CHECK_EVERY_MS` (`updateflow.ts`: the app's own updates; `pluginupdates.ts`: plugins'), `PassOptions`, `pluginTools`, and seen (`librarypass.ts Seen` a copy as its kind read it, `unseen` one not read for sure; `types.ts Change.seen` a source's content an item had taken; `main.ts unseen` news the window hasn't shown; `homepass.ts HomePass.seen` what a person would see of the home, `homepass.ts pageSees`): read each with its file.
