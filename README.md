# Central Knot

Central Knot is a desktop app that shows the skills, MCP servers, agents, instructions and plugins each AI coding tool on your computer has, and keeps the ones you choose the same across those tools. It works with Claude Code, GitHub Copilot CLI, Codex, Pi, OpenCode and Antigravity, through their CLIs or their desktop apps (Claude desktop, the GitHub Copilot app, ChatGPT desktop, OpenCode desktop, Antigravity's app and IDE), and it only reads and writes each tool's own user-wide files. For Antigravity it handles skills, MCP servers and its `AGENTS.md` so far; its agents, other instruction files, own plugins, hooks and history are not read yet.

## Getting it

Download the Mac disk image (Apple silicon), `Central-Knot-<version>-mac-arm64.dmg`, from the [GitHub releases](https://github.com/njfife/central-knot/releases). Open it, drag **Central Knot** onto the **Applications** folder beside it, then open Central Knot from Applications. It is signed with a Developer ID and notarized. Each release also has the same app as a zip.

**On Linux** (x86_64 desktops) there is no release yet: `npm run package:linux` builds `Central-Knot-<version>-linux-x86_64.AppImage` from the source (see Packaging and release), which runs from a file manager or a terminal (on a system that restricts user namespaces, Ubuntu 24.04 and later, start it with `--no-sandbox`). It writes your real home as the Mac app does. At each start it puts its launcher entry and icon in your desktop's launcher, pointing at wherever the AppImage is now, and at its first open it turns on Start at sign-in, as the Mac app does (see Settings). It doesn't yet update itself, and one more thing is in **Not here yet**.

A released build opens on **This Mac's home** (**This computer's home** on Linux): your real tools. Nothing is changed until you choose it. The sidebar's **Home** list also has **Another folder…**, for a backup or another account's home; Central Knot writes only inside that folder, and one that is or links into your real tool folders is read-only. The **Practice copy** (sample data in a throwaway folder, removed at Quit) is only in development builds: run `npm start` from the source to try things on sample files first.

Real-home writes happen on macOS and Linux; on Windows a real home is preview only. If something looks wrong, Settings → **Show log** shows Central Knot's own log (**Open log folder** opens its folder): each plugin change with what it came to and why, and each item a change couldn't reach.

## The pages

### Overview

The page the app opens on. First, what needs you, a line each with its way on: first setup's question, an update to install, why the home can't be written, what couldn't be read, found items whose copies differ, Automatic sync off, and each tool that came under management by itself (installed while the app was closed or open: "Central Knot now manages OpenCode. Copied 2 items.", or, until a sync has brought it into line, "Its items are copied there at the next sync."), with a link to its Manage switch, until you close it with its ×; nothing when none applies. Then one card each for skills, MCP servers and agents: how many, how many are On and whether every copy is in sync (or how many changes wait for sync), how many were used in the last 30 days, how many have no use seen (a link to that filter, where Turn these off is) and the three most used: each name opens its row on the Library, its file mark opens its file under the card, named, the Overview staying (the copy in each tool where they differ, or the version Central Knot holds; closed by its ×, by Escape, or by leaving the page), and **Most used** opens the Library sorted by most used for that visit, the Sort you keep left as it was. Under them, when usage was collected, with **Update usage statistics**; then a row per managed tool: its version, its skills, MCP servers, agents and plugins ("?" where what it keeps there couldn't all be read), and its sessions in the last 30 days. Opening it reads nothing more than the home itself. While another build of Central Knot is on this Mac, the window shows one screen instead of the Overview and every other page (see Updates, One build on a Mac).

### Harnesses

One card per tool found on this computer, with its skills, MCP servers, agents, instruction file, plugins and config folder. A tool counts as found when its CLI or its desktop app is there; when both are, their versions are shown separately. A settings folder with no CLI or app beside it (left behind by an uninstall, say) doesn't count, and a CLI is looked for wherever your terminal finds it, including folders that nvm, bun and the like add to your PATH, up to a fixed folder bound (40 folders on macOS and Linux; on Windows, up to 120 folders from `%USERPROFILE%\.local\bin`, `%APPDATA%\npm`, WinGet `Links`, Scoop `shims`, and PATH split on `;`, tried with the CLI command endings among `.exe`, `.cmd`, `.bat`, `.com` in `PATHEXT` order, always trying `.exe` before `.cmd`; `.cmd` shims are found there, though running them is not wired up yet). Each harness has its own page with tabs for Skills, MCP servers, Agents, Instructions, Plugins (turn each installed plugin on or off in place, with `Off, kept installed` when off, the result and Undo in the header, and **Its page** and **Uninstall…** beside the switch; marketplace and description on hover) and About, and you can manage that tool's items there directly. Only the tools you have are shown anywhere in the app.

**Manage**, a switch on each installed tool's card, says whether Central Knot manages that tool at all. Every installed tool is managed until you turn its switch off, a tool installed later too, whether Central Knot was open or closed: the Overview says so, with how many items were copied there until a sync first brought it into line (its Copied to entries in History), until you close that line, and says it again for a tool seen gone and back. A first setup, and a tool turned on by its switch, say nothing there. Turned off, the tool is left out: Central Knot writes nothing there (no skill, MCP server, agent, plugin, plugin update or instruction file), its copies stay as they are, every item keeps its On or Off, and the tool shows on no other page but History (the line under the Overview's tools table names it as left out); its card keeps its name and its switch, and says the switch asks before managing it again. An item you turn off meanwhile stays in that tool until it is back. Turned on again, the next sync brings it into line, as a tool managed again (below). Its switch asks first, in its card, in the order it happens: what that sync will do there, read when the switch is pressed with nothing saved or fetched (the tool's differing copies saved as versions, which History can restore, then Central Knot's version written there, copies of items that are off removed; the one item it changes by name; items taken in, and the other items it has, which stay its own and show under Found in the Library; what can't be read there said as not known), or that it changes no item there, and, while plugins update by themselves, that it gets each plugin that is on and not kept out of it, from a marketplace listed now; with Automatic sync off, that Sync once brings it into line, and a click on an item brings that item. **Manage <tool>** turns it on, unless what it would do changed since it was read (each item: its kind, name and what is done to it): then nothing is turned and it asks again with what it does now; **Cancel** or Escape closes it, and a read that failed says why, with **Close** and **Try again**. After it the band says what the sync did there, naming the one item it changed. Each flip is one History entry; a tool's newest Manage entry offers **Manage <tool>** (asking the same question in the row) or **Leave <tool> out again** while the tool is present and still in the state that entry made. A tool left out stays left out when it is uninstalled and installed again. In a home that is preview only, or whose record stops every write, the switches can't be turned, and the list says why. pi-gui, a third-party desktop app for Pi, counts as Pi's app (on macOS and Windows). Under the cards, **Also on this Mac** (**Also on this computer** on Windows and Linux) names T3 Code (on macOS and Windows) and VS Code (on macOS) when they are installed: they are no tool of their own, but T3 Code starts your tools, and VS Code's built-in Copilot lists skills from their folders.

### The Library

The **Library** lists every skill, MCP server and agent, one row per item with a small mark of its kind before its name, the kinds mixed under each heading in the chosen order (one name goes skill, then server, then agent). The **kind switch**, first in its toolbar, shows them all or one kind: each segment counts the rows of its kind that Find and the chip leave, with "?" where some of that kind couldn't be read; a kind no managed tool here can hold has none, and with one kind left there is no switch. It is on All at each launch, and the kind chosen stays while the app is open, across pages and homes. Find looks through every kind at once by word search (SQLite's own full-text search, in memory, built from what the Library holds): each row's name, description and file's text (a skill's SKILL.md and the names of its other files, an agent's prompt, a server's command or address), On or Off, and what installed plugins bring, with the last word read as its start and a word that finds nothing replaced by the nearest known words. While it has text the rows found are one list, best match first, Sort says Best match, and a row found only in its text shows the words around the first that matched where its description shows; a row clicked holds every row where it is until the text changes (a row a later answer brings goes below; one it no longer finds goes for good), and **Put in order** puts them back in best-match order; between a keystroke and the answer the list on screen stays where it was and acts on nothing, and the answer's list shows from its top; each chip counts what Find leaves; "Nothing matches" has **Clear Find**; clearing Find brings back the headings and the Sort chosen. After the Library's own results comes **In plugins you don't have**: the skills, agents and MCP servers of the listed marketplaces' plugins that no managed tool has installed (read in the background: see Plugin marketplaces), best match first, with their own count, ten at a time (**Show 10 more**), each with its kind's mark, its name, its plugin and marketplace and its description (or the words around a match in its text), and no switch: its name opens its plugin's page, where the plugin's own switch installs it, and the mouse's Back returns to the same text and rows. It shows also when the Library has nothing yet, follows the kind switch (not counted there), and shows with no chip on and From on Anywhere or Any plugin; a plugin installed and turned off counts as installed, and where a tool's record of its plugins can't be read none is offered. Its heading also says, while not every listed plugin is read, how many are ("still reading" while a read is going on), or that reading is off, with the way to Settings; with no hit anywhere, under "Nothing matches". Find never waits for that reading or downloads anything: it searches what has been read so far, taken in at most every five seconds while it changes. The chips are toggles, a second click letting go. A skill's **Files** opens its files beside the list of skills, and its back arrow leads to the list it was opened from as it was: the Library, or a tool's Skills tab, whose tool the arrow names. A tool's own page on Harnesses has a tab per kind with the same rows, that tool first, its Find matching each row's key (its folder or file name) and description.

Each row has one switch at its start (a found one has Add there instead). A click on a switch or Add draws its row in its new state at once and is carried out in turn, after the clicks before it (the Plugins page's switches wait in the same line): the page stays usable meanwhile, a second click on a row whose click still waits takes that click back, and every other action that writes (Refresh, Turn these off, an opened row's controls, History, Profiles, Library sources, Instructions, the Git repo, a tool's Manage switch, first setup's choices, Settings' Synchronize everything) waits until the clicks are done, and says so. The window's header says what the clicks did, beside the page's name, once for a run of clicks ("3 skills are off: …", each row as the clicks left it): a click joins the run there while one of its clicks waits or runs, or within 8 seconds after its last one ended, until its ×, its Undo, another action or another home ends it, or another page or tool's page once its clicks are done (a page opened while they are carried out leaves the run whole) (in the Library, clicks on a skill, a server and an agent are one run, whichever kind is shown); with one **Undo** for the clicks that did something; where anything wasn't done the sentence says so first ("1 of 3 didn’t go through in every tool: …") and the line under it is the first reason. After an addition or turn On (a row's click, a profile switch, a plugin installed or switched on, Synchronize everything's take-ins, Sync once, or History's Restore), the result's second line shows chips for each tool that needs to do something, tailored to how that tool is found here (its CLI, its desktop app, or both: copy buttons for commands such as `/reload`, `/skills reload`, `/reload-plugins`, `claude --continue`, `/new`, `codex resume --last`, and `opencode --continue`, or plain words when it needs a restart or new session; overflowing chips fold into `+N more`), and **Show all** lists each tool's full sentence and copy buttons in tool order (Central Knot sends nothing to any running session); an opened row's tool line shows that tool's sentence while the result is active. The result keeps to the header's own two lines, so nothing under it moves or is covered; **Show all** opens the whole of it, every reason once, as a card over the page, which Show less, ×, Escape or a click anywhere else folds; a result with nothing undone goes by itself 8 seconds after the last click is done (not while the pointer or the focus is on it), and its Undo stays in History. An Undo leaves each tool's folder or file as it was before the click (a tool's own copy that the click wrote over is given back). **Marks** at the row's end say what each tool has (on, off, no copy, kept out, switched off in the tool's own settings, has it another way, can't take it, something waiting for sync, or through a plugin), each with a mark of its own and the legend in the lines' words; they are status only. The opened row (its chevron) has each tool's line, with its own controls. A skill's file mark, after its name, opens its file in one click: its SKILL.md from its first line in a box that scrolls inside itself, its other files as tabs, a choice of copy where the copies differ, and its path with Show in folder and Copy path. An agent's mark (one on its own row, not yet on a plugin's agent or a marketplace hit) opens its whole file as a tool has it, front matter and prompt or Codex's TOML, with a choice of each tool that has a copy (the tool's own tab starts on its copy); an agent no tool has opens **Central Knot’s definition**, its description and prompt, stored in Central Knot with no path. An MCP server's mark (on its own row, not yet on a plugin's server) opens its entry exactly as a tool's settings file has it, its name as spelt there, comments and escapes in it, and nothing else of the file (in Codex's `config.toml`, the server's own tables, or its own lines where it is written inline or with dotted keys; where other lines of the file come between its parts, each part is a block of its own, with a band between them that is never selected or copied), with where in the file it is (**In mcpServers**, **In mcp_servers**) and the file's path, with a choice of each tool whose settings have an entry and, for a server in Central Knot, **Central Knot’s definition** last (alone where no tool has an entry), stored in Central Knot with no path. From a closed row the file opens alone under it. From an opened row it takes the place of the row's details, under the row or in the side panel, with **‹ Back to details** above it and no ✕ of its own: Back to details, its mark or Escape close the file and bring the details back. On a row asking which copy to use, the mark closes the question and opens the file alone.

**Sort**, beside the filters, puts your rows under each heading (**Only through a plugin** stays by name) by **Name** (as they first are), **Last updated** (newest first, each row saying when, "3 days ago"), **Last used** (newest use first), or **Most used** (most sessions in the last 30 days first; equal counts by the more recent use, then by name; rows with no sessions in the last 30 days, or nothing known, last by name). Last updated is the time the item's current version carries: a copy taken in (an edit in a tool, a found item added) keeps its file's time (an MCP entry, which has none, the time it was taken in), a source's update its commit's, and Replace, Merge or Make current the click's; On, Off and writes to other tools never change it. A found item goes by its newest copy's time; one with no time (an MCP entry has none of its own) goes last, and equal times go by name. One choice for the Library, remembered when the app opens again; a tool's own page on Harnesses keeps its rows by name.

**Usage statistics** are collected by themselves whenever a home opens (at launch, and when another home is opened; after a start at sign-in with no window, once the window first shows), in the background: Central Knot reads each tool's own session history on this computer for which skills, MCP servers and agents were used in the last 30 days, and when; nothing leaves the computer, nothing is changed, and nothing is kept (the figures go when the app closes). At the toolbar's end, **Collect usage statistics** (before any reading) or **Update usage statistics** (after one) collects again, and beside it says when it last did ("Collected 8:44 AM", "· no sessions yet" where no tool keeps any). A click on it opens a band under the toolbar that says what collecting does while it collects, then that it was collected, or that it couldn't be; a reading by itself that fails is said in the status bar instead, so no band opens above the list on its own. The band has a close button and stays closed until the next Update. Only a call counts, or a skill the person typed, never the list of what a session had available. A use counts in any tool read, managed here or not. Each row then says the one figure its Sort is about — under **Most used**, its sessions in 30 days, every tool's added up ("14 sessions"); under **Last used** (and under every Sort while the **No use seen in 30 days** chip is on), when it was last used ("2 days ago"); under **Name**, **Last updated** or **Best match**, nothing for a row that was used — while under every Sort an unused row says "no use seen" (with its 30-day window or "No use seen · records from Nov 7." on hover), or a faint "use unknown" when no tool that has it on can tell (a page where every row would say so shows no figure); hovering a cell with words keeps both figures (an empty cell has no hover), and its opened row says each tool's short figure (`used 2 days ago · 28 sessions`, `no use seen · records from Nov 7`), or `use unknown` with its `(?)` card holding why (unreadable session counts stay visible, and an absent plugin line with nothing observed and readable history is blank). A use dated after the reading takes its file's time. While a home's first reading runs, the figures' column and an opened row's lines hold their room. A reading that lands moves no row: under Sort by **Last used** or **Most used**, or with the **No use seen in 30 days** chip on, the rows on screen stay where they are (each row's figure fills in place) until the next Sort, chip, page or Refresh, or **Put in order**, which shows beside Sort whenever rows on the list are held where they were (a click on a row's own switch holds it too). The chip lists each item that is On, whose oldest version is at least 30 days old, that a tool which can tell has on, and of which no tool saw a use (a tool whose history is shorter counts as far back as it goes); an item no tool can tell about is never in it. The chip shows only when it holds something. Its band is one line (wrapping to a second line at narrow widths when a managed tool’s history was not read): how many, how many from a plugin are skipped (marked on their own rows while not selecting; when every row shown is a plugin's, they are marked from a plugin and the band says to turn each off on its own row), any managed tool whose history could not be read at all, a **What’s counted** disclosure (history read, what uses are not seen from here, and what new or found items were not counted), and **Turn N off everywhere** (each row's own Off in one click, kind by kind, with one Undo that turns them all back on; a kind whose record can't be written is skipped and named, and the others go on; any profile it ends is named in the result). When the kind on screen runs out while other kinds still have items with no use seen, the band names them with a button (**Show Agents** or **Show all N**) that switches to them with the chip kept on. Read: Claude Code (`projects/` in its folder), Codex (`sessions/` and `archived_sessions/`), Copilot CLI (`session-state/`), Pi (`sessions/`) and OpenCode (its database under `~/.local/share/opencode`, read from a copy). Not read: Antigravity (yet), Cowork, ChatGPT desktop, the web, another computer.

**Skills, MCP servers and agents live in Central Knot.** Central Knot holds each skill (its whole folder), each MCP server and each agent itself, with its versions; a tool is somewhere it is applied.

- **Found**: one a tool has that Central Knot doesn't. It has **Add** where an item in Central Knot has its switch. Add takes it in, turns it on and puts it in every tool Central Knot manages that can take it (its row names those that can't, or have it another way). Its Undo takes it out again: the copies it made go, each tool it was found in keeps its own, and it is found again. Where the tools' copies differ, Add asks which one to take in, quoting each (a skill's first line of text; **Read both copies** opens a skill's files); the others are kept as versions; the copy changed last is marked and its button is the main one (none where the dates can't tell: an MCP entry has no time of its own, and two copies changed less than a second apart are a tie). With **Synchronize everything** off, nothing else takes a found item in.
- **First setup**: a home whose Synchronize everything was never answered (a new one, or one from before this question) is asked once, at the top of the Overview, in one line: "Add 75 of the 84 items found in your tools to every tool that can take them, and new ones as they turn up?" ("the 84 items" where all are ready; found means new to Central Knot, a plugin's parts included), its (?) saying that each item goes to the tools that lack it and what the one Undo takes back (the items it added, but for any changed since; a copy you choose has its own Undo, said where copies differ). Its buttons are **Synchronize everything** and **No, I'll add items myself**, whose hover says what it leaves (what is on stays on, said only where something is), with "You can undo this." beside them. Under it is only what is true of the home: found kinds whose record stops them, and one line for the found items whose copies differ, which stay as they are until you choose, with **Show them**; Automatic sync off is the Overview's own line, with **Sync once**; the lead that says what Central Knot does waits until it is answered. It isn't asked where nothing can be written, or with no tool managed; in a home waiting for Resume, Resume comes first. Yes is Settings' switch: it turns the rule on and adds what it may, and its result stays on the Overview, "Synchronize everything is on: it added 75 items.", with the switch-on's own **Undo** (with Automatic sync off: "Synchronize everything is on. Nothing added yet: Automatic sync is off.", with **Sync once** beside Undo); the line under it leads into the **walkthrough** with **Choose copies**: one found item whose copies differ at a time, on its page, with its row's own question, the latest copy offered first, **Skip** (which changes no copy), and **Use the latest for the rest** (which skips the ones with no dates to go by and says how many). It can be left at any moment; what is left stays found, and the Overview and Settings lead back in with **Choose copies** (once the last item was skipped, it starts again at the first that waits). No stores the rule off and changes nothing; its band, "Synchronize everything is off.", offers **Turn on**, the same switch as Yes, with the same result. Either answer is kept in the home's record, and Settings is the way to change it.
- **Synchronize everything** (Settings › This home): a skill, MCP server or agent that turns up in a managed tool is taken in and turned on everywhere by itself, as Add would, at the next sync (with Automatic sync off, at Sync once). Turning it on takes in everything found then, and shows a result band on Settings with History's **Undo** right there (and its help on hover). Switching it on or off is an entry in History; the switch-on's **Undo** switches it off again and takes back everything it took in since, each by that item's own Undo (whichever sync took it in), and names what it leaves in: anything it was found in that no longer holds the copy it held then (an item changed since, an edit not taken in yet among them, turned off, deleted, kept out of or taken over in a tool, or found in a tool now left out), and a copy you chose (which has its own Undo). An item's own Undo goes by the same rule. A tool no longer managed that only got Central Knot's copy keeps it until it is managed again. That Undo's entry offers **Restore**, which puts back what it took out (passing over an item added, changed or deleted since) and puts the switch-on back in force, so its Undo takes them back again. Each item it took in also gets Add's History entry, saying Synchronize everything took it in and from which tool, with Add's Undo. One notice per sync, on its page and in Settings, says how many and where they were found. It leaves found, each opened row saying why: copies that differ (the row asks which, and Settings and the Found heading count them), an item deleted from Central Knot or whose take-in was undone (it is not added by itself again; Add, or Restore in History, brings it back), a plugin's part, an item every tool that has it has switched off in its own settings, and a copy that can't be read. An item that is Off, or kept out of a tool, whose copy turns up is not found at all. A copy a tool has another way is taken in from where it is; that place is not written (Take over stays a click).
- **On**: every managed tool has the current version, kept the same both ways: an edit made in any tool becomes the current version and reaches the others. When two tools were edited, the latest edit wins (by the folder's or file's time; an MCP entry has no time of its own, so the first tool's, in the order the page lists them) and the other is kept as a version. A skill's whole folder is the same everywhere: every file as it is, its scripts still runnable, and empty folders (not a nested `.git`, Finder's `.DS_Store` or an editor's swap and backup files). An agent's name, description and prompt are the same everywhere; each tool's other settings (Claude Code's `tools` and `model`, Codex's keys and tables, comments) stay in that tool's own file.
- **Off**: it leaves every tool. It stays in Central Knot, with a row under Off, and turning it on writes each tool's folder or file back exactly as it was (an MCP server's entry: the same values, name, place and own fields; see below). A copy deleted by hand in a tool turns it Off everywhere; Central Knot keeps it, so **Turn it on** puts it back. A copy that can't be read, a half-finished save, a tool uninstalled, or a folder that was moved, made again or removed is never taken for a deletion: a removed folder is written again after a short settle.
- **One tool's switch**, in the opened row, keeps it out of that tool alone; the row then says "in 2 of 3 tools · kept out of Codex" (it counts the tools that load it now) and its switch is drawn partial. On an Off row, a tool's switch turns the item on in that tool alone (kept out of every other tool); where another managed tool reads its skills folder, can load the skill, and has no copy or off-switch of its own (as OpenCode reads Claude Code's), that tool's line and switch label say so before the click ("If on, OpenCode reads it too"), and History records it when a switch turns the skill on in one tool alone and that write lands (even if its keep-outs did not change; turning the other tools off one by one records nothing). A tool kept out that still loads a copy there (one Central Knot doesn't write, as Use the plugin's leaves yours in the other tools; or one in another tool's folder it reads, as OpenCode reads Claude Code's) is counted as loading it: "in 5 of 5 tools · 3 run their own copies · OpenCode has it another way", and its switch, unticked as before and with the same click, reads "Its own copy" or "Another way", not Off. A tool that can't take it (a name or shape it won't load, a folder that can't be written) says why on its line; one that won't load an edit made elsewhere keeps the copy it has, and says why the same way.
- **Versions**, in the opened row: every version, the current one first, each with when it was made, where it came from and what changed. **Read** shows one, marking what differs from the current version; **Make current** puts an earlier one in every tool it is on in. Central Knot keeps every version while the item is in Central Knot.
- **Delete…** takes it out of every tool and off the page. History keeps it, with its versions, for History's days (Settings), and **Restore** there puts it back as it was.
- **Select**, on the Library's toolbar (Done ends it, as do Escape, another page or home and the Files view), puts a tick in each row's switch's place: a click on a row ticks it, Shift-click ticks the run to it, a heading's tick its rows; the chevron still opens a row. A tick stays while Find or a filter hides its row, and only the rows listed are counted or acted on. The bar under the toolbar counts the rows ticked and how many of them can't be deleted, a link that names each and why (not in Central Knot, only through a plugin, its kind's record stopped); a heading none of whose rows can be deleted has no tick. **Delete…** asks once, in the bar's place, what goes and for how many days History can restore it (Settings' days); the result names what was deleted, stays until closed, and has one **Undo**.
- **A tool managed again** (its Manage switch turned on again, or uninstalled and back): Central Knot's version wins there. A copy changed in that tool meanwhile is kept as a version first; a copy of an item turned off meanwhile is removed; a copy deleted there is written again. Nothing turns Off because a tool was away. A tool managed for the first time that has its own copy of an item that is on gets the current version, its own copy kept as a version first. History says each of these: a copy put where there was none, with no click of yours behind it, is an entry of its own, Copied to <tool>, with **Turn it off in** that tool.

Skills only:
- **Has it another way**: a tool that has a skill without a copy of Central Knot's in its own folder gets none: a plugin brings it, a link in its skills folder leads to a copy, it reads a copy in `~/.agents/skills` (Copilot CLI, Codex, Pi and OpenCode do; not one its own settings keep out while the copy in its own folder is let in, which stays), or it reads another managed tool's folder (OpenCode reads Claude Code's, while the skill is really there). Its line says which. Central Knot never writes through a link or into a folder that isn't its own; a copy it put there that is one too many is removed, and one it didn't put is left alone (the line says the tool has it both ways). **Take over…**, on that line, makes Central Knot's copy the tool's: a link is replaced at once (what it led to stays); a copy in `~/.agents/skills` is removed once confirmed (its armed line says which folder goes and which tools get Central Knot's copy), kept as a version first, with the links in the tools' folders that led to it, and each tool that read it gets Central Knot's copy, switched off where the tool had switched off the copy it read. Take over has no Undo, and says so. A copy in `~/.agents/skills` edited after the skill was taken in is said on the lines of the tools that read it. A copy there deleted by hand while the skill is on, and a tool had it only there (or through a link to it), is a deletion as in a tool's own folder: the skill turns Off everywhere, nothing is written, and the notice and History say it was deleted in the shared folder; **Turn it on** then gives each tool Central Knot's copy (OpenCode reads Claude Code's), in place of a link that leads nowhere, and says so (Central Knot never writes the shared folder). Only such a link deleted is a deletion in that tool, and the notice names the tools that still read the shared copy. While the shared folder can't be vouched for (unreadable, or missing or holding none of the skills tools had there or a link in a tool's folder leads to: a volume not mounted, another folder in its place), nothing is concluded from it, nothing is written because of it, and nothing in it is found or taken in: no skill turns off, no tool that may have had a skill there gets a copy (a new skill's first copy waits too, and a click's or a profile switch's result names the tools that wait), a copy of its own in a tool that reads the folder is left exactly as it is (it may stand beside one that is away), and a skill found with such a copy waits, Add saying why (one only ever in such a tool's own folder waits too, until the folder is back), as does History's Undo that would give such a copy back; the Library says so once, naming those skills. A person who removes every one of them sees that line, turns them off and removes the links to them. A home from an earlier build learns how each tool has a skill at its first sync; a copy deleted from the shared folder before that sync, or the shared folder away then in a home with no link into it, still writes a copy into each tool once, as before.
- **A tool's own switch** for a skill (Claude Code `skillOverrides`, Copilot `disabledSkills`, Codex `[[skills.config]]` by path, Pi's `settings.json` filter, OpenCode a `deny` rule for the skill's name, Antigravity the folder's name in `skills.json` `exclude`) is read at every look and never undone by a sync: the folder stays, the tool doesn't load it, the tool is not counted as on: its mark is its own, the row says "switched off in Codex" with a partial switch, and that tool's line says "Switched off". **Let Codex load it**, on that line, clears the switch; its Undo sets it again. An agent in Pi, which takes it as a skill, has Pi's the same way.

MCP servers only:
- A server's **version** is what it runs (its command, arguments, environment and working folder, or its URL and headers), the same in every tool; the rest of its entry stays that tool's own: its other fields (Copilot's `tools`, Codex's timeouts and tables, `enabled`), its name as that tool spells it, where OpenCode keeps it (`mcp` or `mcp.servers`), and the comment lines of a Codex table. That comes back with the entry after Off and On, which puts it after the file's other servers; a comment at the end of a shared value's line (`command = "npx" # pinned`) is not kept. A change to the tool's own part alone is no edit.
- Each tool's user-wide file: Claude Code `~/.claude.json`, Copilot `mcp-config.json`, Codex `config.toml`, Pi `mcp.json`, OpenCode `opencode.json` (or `opencode.jsonc` when there is one), Antigravity `~/.gemini/config/mcp_config.json` (a remote server at `serverUrl`, as its own command writes it; `url` is read too). Writes edit only that server's entry; the rest of the file stays byte for byte. OpenCode's servers are read from both places its settings keep them (`mcp` and `mcp.servers`); an entry is changed where it is, and a new one goes under `mcp`.
- **Claude Code's file is written in the same sync as every tool's**, while Claude Code, Claude desktop or its Code tab runs too: Central Knot holds Claude Code's own lock on the file for the whole of each write (the `.claude.json.lock` folder that `claude mcp add` takes), and a running Claude Code saves its own settings under the same lock, keeping what Central Knot wrote. Should Claude Code keep that lock for more than about two seconds, that write is left for the next sync. A Claude Code session that is already open keeps the servers it started with until it is started again, as with the other tools; a new session has the change.
- **Left alone, said why on its line, never taken in**: a server that belongs to an app (ChatGPT desktop's own), an entry in a form Central Knot doesn't edit (Codex servers written inline or with dotted keys, an OpenCode name in both places), two names in one file that differ only by case, and an entry Central Knot put in as a plugin's part (it is the plugin's). A tool that can't hold a server (SSE in Codex, Pi, OpenCode and Antigravity) says so. A settings file that can't be read leaves that tool alone; a missing one is written afresh after a short settle; one that reads and no longer has an entry (`codex mcp remove`, or a tool rewriting its file) is a deletion by hand: the server turns Off everywhere, and **Turn it on** puts it back.
- **A tool's own switch** for a server (Claude Code `deniedMcpServers` and Copilot `disabledMcpServers` in their `settings.json`, `enabled = false` in a Codex table, `"enabled": false` in a Pi or OpenCode entry, `"disabled": true` in one under OpenCode's `mcp.servers` or in an Antigravity entry) is read and left as it is: its mark and line say it. Where it lives inside the entry (Codex, Pi, OpenCode, Antigravity) it is that tool's own field, so it comes back with the entry after Off and On; Claude Code's and Copilot's stay in their settings either way.

Agents: Claude Code `~/.claude/agents`, Copilot `~/.copilot/agents`, Codex `~/.codex/agents`, OpenCode `~/.config/opencode/agents`; Antigravity's are not handled yet. An agent new to OpenCode is written with `mode: all`, so both of OpenCode's lines offer it to choose and to hand work to. Pi holds no agents of its own, so it takes each agent as a skill: `<name>.md` in `~/.pi/agent/skills`, the same Markdown as Claude Code's file, kept in step both ways like any tool's (deleting it there turns the agent off everywhere; Pi's switch in the opened row keeps it out of Pi alone). Such a skill has no isolated context of its own, no tool restrictions and no model selection, and it is invoked as a skill rather than picked as an agent; the opened row says so. A skill of the agent's name in Pi keeps the agent out of Pi until that skill is deleted or renamed, since Pi loads only one skill of a name: a folder or a link to one, in its skills folder or `~/.agents/skills`, or a `<name>.md` in its skills folder that Central Knot didn't put there. Such a file is the person's own skill, never read or replaced.

Skills: each tool's own skills folder. OpenCode 1.x leaves out a skill with no `name` in its frontmatter, so such a skill is marked as one OpenCode can't load. A skill whose folder can't be copied as it is (a link inside, a file Central Knot can't read) is a row that says why, and can't be taken in until it can. Skills synced by an earlier version are moved into Central Knot the first time this one opens the home: a synced skill is On with the same content, a tool left out is kept out, and one never synced, or kept different on purpose, is found (every folder untouched); `sync.json` as it was is kept beside it as `sync.v1.json`.

### Two-way sync

- **Automatic sync** (status bar switch, on by default): an item edited in one tool spreads to the others within seconds. A deletion is acted on after a 2 s settle. Competing edits: the latest edit wins, by the folders' or files' times (MCP entries, which have none: the first tool's, in the page's order), and the other is kept as a version. Each outcome is a notice in the window's header, never above a list, so nothing it brings moves a row: **Notices** counts them (filled with the app's own blue while one is unseen), the newest, said as an automatic change in that blue, is in the header's two lines while no result or background problem has them, coming on a stronger fill that settles once, and Notices, or a click on that line, opens a card with every one whole and its actions: See change, Undo or Turn it on, History, Dismiss and Dismiss all. Undo or Turn it on there says what it did in its notice's place, each until the card closes; one refused says why there, keeping its own action for another try. A notice counts as seen once drawn while the window has the focus. A result keeps the lines while a notice arrives; a notice of a later save of the same item takes the older one's place, whose save stays in History.
- With Automatic sync off, edits and deletions are noted as waiting, and **Sync once** spreads them once.
- A folder or file that can't be read or is half-written is held, never read as a deletion; a folder made again is written afresh. An MCP settings file that reads without a server's entry is that entry deleted by hand (see MCP servers). Every write checks the file first and never overwrites a save made meanwhile.
- Closing the window keeps Central Knot syncing, and updating plugins (see Plugin marketplaces). On a Mac it then leaves the Dock and runs from its menu bar icon alone, until the window is opened again; on Linux it runs from its system tray icon, and on a desktop with no system tray (GNOME without its AppIndicator extension) closing the window quits, and a start at sign-in shows the window once about ten seconds have passed with no tray (a panel still starting at sign-in is waited for). The menu bar icon has Open, Settings, the profile, Automatic sync, Sync once (while Automatic sync is off), Start at sign-in and Quit.

### MCP sign-in

**MCP sign-in**, beside the Library in the sidebar, has a row for each MCP server a tool here has (your own and installed plugins', as the Library lists them) and a column for each tool that has one, and says in each cell what that tool's own command reports of the server. Nothing runs when the page opens: the cells of a tool with a command that reports say **Not checked** until you press **Check** at the head of its column, which runs that command once (`claude mcp list`, `codex mcp list --json`, `pi mcp list --json`, `opencode mcp list`) from an empty folder made for it, stopping it after 70 seconds or when Central Knot quits; **Check all** runs the columns one after another, and while one runs every Check waits. A cell then says **No sign-in needed**, **Signed in**, **Connected**, **Needs sign-in**, **Couldn’t reach:** with the tool's own words, **Codex can’t tell if it needs a sign-in**, **Not reported by** the tool, or **Couldn’t read** the tool's **answer** with the line it couldn't read; a column whose tool didn't answer in 70 seconds, has no command line here, or answered in a shape Central Knot can't read says so in each of its cells. A cell says **Off in** the tool where the tool's own switch has the server off, whatever it answered, and **Not checked** again where the server was changed, removed or switched off since its column's check. Beside **Check all** are the time of the last whole Check all (a column shows its own time only before one, or where its time differs) and a line saying what a check does on this computer: which tools start their local servers (Claude Code, Pi and OpenCode, where they have one), or else which contact their remote ones, (a server switched off in a tool, or a tool whose command line isn't here, isn't counted), and that OpenCode leaves a service running (2.x) or adds `$schema` to its config files (1.x), or may do either where its version isn't known. The first **Connected** has a card saying that Claude Code, Pi and OpenCode don't tell a sign-in from none needed, so their Connected is only that the server answered. A server that runs on this computer (its transport is stdio) says **Local** under its name. When you come to the page, and on Refresh, the rows that need a sign-in or say what went wrong come first; a check moves no row while you are on the page. Copilot CLI and Antigravity have no command that reports this: their columns run nothing, Copilot CLI's head says `In a session: /mcp auth <name>` and Antigravity's `Sign in inside a session`, and a cell where the tool has the server shows a mark (•) whose hover says where its sign-in shows. A cell that needs a sign-in shows that tool's own command for it (`claude mcp login <name>`, `codex mcp login <name>`, `pi mcp login <name>`, `opencode mcp auth <name>`, with the server as that tool names it, a Claude Code plugin's as `plugin:<plugin>:<server>`, in single quotes where a shell needs them) with **Copy**; you run it in a terminal yourself, then Check again. A check of this computer's home runs with its environment; a check of the Practice copy or another folder runs with one made for it (its path, home, temporary folder, locale and terminal), so none of the tools' own settings reaches it. Central Knot reads only what the commands print: it doesn't read, keep or show a token, a credential file, a cache or a keychain entry, starts no sign-in, and stores nothing. What a check said stays on the page until Central Knot quits or another home is opened. The tools' own commands may write their own logs and caches in their own folders, as they do whenever they run.

### Instructions

Opens each tool's own instruction file to read and edit in place, one card a row (two on a wide window): a click on the text (or **Edit**) opens it with the caret there, a drag across it selects it to copy, and a card's buttons stay in its head while you edit, with **Undo save** after. **How these files are read**, at the top, says who reads each file and each tool's own notes, such as OpenCode 1.x reading Claude Code's `CLAUDE.md` while it has no `AGENTS.md`. Under a tool's card, **Also read with CLAUDE.md** (each tool's own file name) lists what the tool reads with its file, in its order: first **In every session**, then **Only for matching files**, each with the files it is read for. A line says where the file comes from and its size, and **Show** opens its text below, **Hide** closes it. The files: Claude Code's `@` imports (each resolved against the file that holds it, up to four hops, none in code or an HTML comment) and every `.md` under its `rules/` (linked folders followed), each with its imports, though a rule only for matching files is listed without its own; Copilot CLI's `instructions/*.instructions.md`; and the files OpenCode's config lists under `instructions`. A file the tool can't read (missing, a folder) is in the warning tone, beside the line that names it. A pattern, a relative path or a web address in OpenCode's list is named as written; nothing is fetched. These files are shown as they are. Writes go by destination: a tool's own file is written from its card and by the base instructions, even when a card lists it here too, and nothing else listed here is written. One that is another tool's own file (`CLAUDE.md` importing Codex's `AGENTS.md`) says so.

Last on a tool's card, **Hooks that can add text** (Pi's **Packages**, OpenCode's **Plugins**) names what else can add text to that tool's sessions, read from files only: nothing runs by itself. One sentence under the heading (and the **(?)** mark on the first hooks strip of a page) says what it lists: hooks that run a program when a session starts or when you send a prompt (Copilot CLI: when a session starts, as it ignores what prompt hooks print), whose output is known only when they run; other kinds of hook (one that calls a URL or an MCP tool) and a project's or an organisation's hooks are not listed. Each source is a group with its own colour dot and its name: your own hooks (**yours**, with the settings file that holds them), then each plugin that is on in that tool (with **Plugin's page: turn it off there**), each hook beneath it with when it runs (as its matcher narrows it: after compaction, on resume), its command as written, and **View source** (**Hide source** while open) to show in place the script its command names and where the hook is declared, read from disk on click. On macOS and Linux in this computer's own home, each of your own hooks also has **Run it** beside **View source** (and every strip with a runnable hook shows **Run it runs the command for real. It may change your files.** above its rows): a click runs that hook once as its tool would (**Running…** and **Stop** while it runs) and shows under its row what the tool would add (**Would add**, never **Added**, with when and where it ran and **Show all it printed** / **Standard error** where relevant, or why nothing would be added or why it was **Not run**). Nothing runs on opening a page, on Refresh, in another folder or Practice copy, on Windows, or on a plugin's hooks. A plugin's copy or a hooks file that can't be read is said in the warning tone, never shown as no hooks. Codex's note (on a runnable strip, that **Run it** runs a hook even if it isn't trusted in `/hooks`; otherwise that Codex runs a hook only after you trust it in `/hooks`) and Copilot CLI's come before the rows.

**Base instructions**: you write a base once and choose which tools get it. It is added after each tool's own instructions as one marked block; the tool's own text is never rewritten. Every write is reviewed first (**Review changes**), a copy edited outside the app is found, and each save can be undone. A typed draft is not lost when you switch homes: the app asks first.

**Draft with a tool**: instead of writing the base yourself, have one of your tools write a first draft from the instruction files you already have. The button opens a panel under the base's text and runs nothing yet: it says which tool's command line will run, takes the tool (any with a CLI on this computer, except OpenCode and Antigravity) and, if you want one, a model (passed as `--model`; empty is the tool's own default), and shows the whole prompt the tool will be sent. **Start** runs it once, sending exactly that prompt (if a file changed since it was shown, nothing is sent and the new prompt is shown instead); it sorts your files into a base for every tool and what stays only in each tool's file. You see the draft, including any line it did not carry over as written, and can change it; one **Save** then sets the base and updates every file, with **Undo**. Nothing is saved before that.

### Plugin marketplaces

- **Marketplaces**: add one by Git URL, `owner/repo` or folder, or from Library sources (**Add to Plugin marketplaces**, below). A Git address is checked (`git ls-remote`) before it is added, and a marketplace is read at its repository's root, from its default branch: a web link to a branch or a folder is refused here, with a pointer to Library sources, whose Look reads any link. Adding one already on the page (on Central Knot's list, or added in a tool) says so. Claude-format and Codex marketplaces (including `.agents/plugins/marketplace.json`) are read. Under the open add box, a line says that any other link (a folder of skills, agents or MCP servers, or one plugin) goes on Library sources, with a link to it.
- **Suggested**: a marketplace from the maker of each plugin tool you have is offered under the list, with **Add**: Anthropic's `claude-plugins-official` for Claude Code and Codex, GitHub's `copilot-plugins` for Copilot CLI. One is offered only where its tool is installed and nothing lists it yet; nothing is fetched until you add it, adding installs nothing, and the × beside one stops it being offered (with Undo). A custom build that carries its own marketplace suggests none.
- Each plugin shows its parts (skills, MCP servers, agents and more), what each tool gets from them, its skill text, and each tool's installed version next to the marketplace's.
- **What a plugin says to your sessions**: its page lists the instruction files it carries under **Instruction files (N), read by no tool** (a `CLAUDE.md`, `AGENTS.md` or `GEMINI.md` at its root, `.claude/CLAUDE.md`, `.github/copilot-instructions.md`, Copilot's `com.github.copilot/rules/*.md`), each opening to its text, with a `(?)` card explaining that the model sees one only when something tells it to read the file, such as one of the plugin's skills (measured: `docs/capability-data.md`, section 6). A plugin that holds nothing else that could be a part says, beside its tool boxes, that no tool reads these files by itself and to copy the text into your own instructions. What can add text to sessions is a start-of-session or prompt hook: these are a group of their own, before the other hooks, a row per command, with its arguments and **View source** to show the marketplace copy's script and declaring entry in place (labelled as the marketplace's copy; shown, never run), under a line naming each of your tools that takes text from none of them (Codex, for a plugin whose Codex manifest says `"hooks": {}`), and the **In each tool** fold (open at once only where some tool's outcome is limited or fails, closed otherwise; **Readme** is a fold closed at open too) says how much of it reaches each tool's sessions (Copilot CLI takes only a top-level `{"additionalContext": …}` from a start-of-session hook; Codex waits until you trust the hook in `/hooks`).
- **One switch per plugin**, on its row and on its page, acting at once, or after the switch clicks before it: clicks wait their turn on the page, and each row says what its click is waiting to do (Waiting to turn on, say), then what it is doing, then its result, or why it failed; its switch is free again as soon as its own click is done. Meanwhile every other plugin's switch and the rest of the app stay usable; the Plugin marketplaces page's other actions (Update, Undo, adding a marketplace) and the ways to another home are off until the clicks are done, and say so. A row's result stays until the next click after them, another plugin action or Refresh; the header's result goes by itself 8 seconds after the clicks are done when nothing failed, and its Undo with it (a plugin's switch has no History entry: the switch itself turns it back). **On** installs it in every managed tool that takes it and lacks it, through that tool's own plugin command (Claude Code, Copilot CLI, Codex), and in Pi, OpenCode and Antigravity turns its items on (below); **Off** turns it off in every managed tool by that tool's own switch (Claude Code's and Copilot CLI's `plugin disable`, Copilot CLI's `plugin uninstall` for a copy loaded live from a folder, Codex's `enabled = false`) and keeps it installed there, with its data, its saved options and the tool's switches for its single items; and it turns its items off in Pi, OpenCode and Antigravity. A copy kept off so says "Off, kept installed", is not updated by itself, and only the plugin's switch or its box turns it on again: not a profile, not an item's switch in the Library (that tool's line there offers Turn the plugin on, as its box does). An install, uninstall or switch counts only when that tool's own record shows it. A tool whose Manage switch is off is left alone, and so are Claude Code's copy from the Anthropic Directory, a copy whose files are not where its tool records them, and a tool that has a different marketplace under the same name: the result says so. The result names what happened in each tool, with **Undo**: what the click installed is uninstalled (or turned off, kept installed, for a live Copilot CLI copy), and what it turned off is turned on again (the same copy). On turns a copy kept off on again; it installs only where a tool lacks it.
- **Each tool's box** on the plugin's page is ticked while the plugin is in that tool. Untick it to turn it off there, kept installed (in Pi, OpenCode and Antigravity, to take its items out): it stays out ("Off, kept installed" where a copy is kept; "Not installed" where absent), and automatic updates and a tool installed later respect that; a plugin kept out of a tool that takes it shows its switch striped, as partial. Unticking the last tool that has it turns the plugin off, so its switch brings it back where it last was; on a plugin that is off, unticking a tool that still has it on only turns that copy off. Tick it to install it there, or to turn on the copy kept there; on a plugin that is off, a tick turns it on in that tool, and in any other tool that still has it on. A tool that lacks a plugin that is on (an install that didn't finish, or one taken out there with the tool's own command) has an empty box, and nothing puts it back by itself. A box that can't act (a tool that can't take the plugin or refused its marketplace, a record that can't be read now, a copy that can't be taken out here) is off and says why on its line. In Pi, OpenCode and Antigravity, where none of its items is on, each reason is said under the box, with the way to have the plugin's there instead. On the Plugins list each tool's mark only shows what it has.
- **Uninstall…**, under a tool's box on the plugin's page and on that tool's row of its Plugins tab, uninstalls it from that tool alone by the tool's own command, where a copy is installed there whole and its box can act (not for Copilot CLI's copy loaded live from a folder, whose Off already uninstalls it, nor in Pi, OpenCode and Antigravity, where an untick takes its items out). It asks first, in place, from a read of that tool's copy as it opens (until it lands only Cancel can be pressed): whether it can be installed again and as what (another version, or the marketplace's copy where this one was edited, or where a part of it couldn't be compared; a copy loaded from the marketplace's own folder is the marketplace's), or that it can't (no longer offered, its marketplace can't be read now, or a bundled build doesn't include its files), then what that tool deletes for good (in Claude Code the options saved for it, declared now or not, its data folder kept; in Codex its MCP servers' settings in its own file). Cancel or Escape asks nothing more. It keeps the tool out as an untick does (the last tool that had it leaves the plugin off), so nothing puts it back there by itself; a tick installs it again where it can be. Its **Undo** installs the marketplace's copy there again, turned off if it was off, and says it comes back without what the uninstall deleted; where that install fails, the tool stays kept out. A plugin that can't be installed again has no Undo.
- **Found**: a plugin a managed tool has that Central Knot has no record of (installed there with the tool's own command) shows **Add** in place of its switch: Add turns it on, and it goes into every other tool that takes it. Nothing takes it in by itself.
- **The first time a home is opened by this version**, each plugin some managed tool has is recorded as on; while some managed tool lacks it, it is kept out of every tool that lacks it, so it stays where it is. Nothing is uninstalled, and the only install is one the version before was waiting to make in a tool new here. What is recorded is `.central-knot/plugins.json` (each plugin on or off and the tools it is kept out of, and the managed tools that are not new here); what each tool has is read again at each look. While a tool's own record of its plugins can't be read (half written, say), nothing is recorded or switched until it can.
- **Its items in Pi, OpenCode and Antigravity**, which take no plugins: the plugin's skills, agents (in Pi, each as a skill; Antigravity takes none) and MCP servers are items of Central Knot's linked to it, read from the marketplace's copy, and its page lists them under **Its items**; each one's row says "from the plugin". On brings them in and turns every one of them On (one you had turned off by itself too); a name new to Central Knot arrives On but kept out of each tool the plugin isn't in and of each tool that has a copy of that name, which stays as it is. A name you already have stays yours, said under the box of each tool the plugin is on for, whatever else is so. The same content changes nothing: it counts as on where yours is, and its line says it is the same, so yours stays. Other content gets **Use the plugin's <name>** under its line, and a take happens only on that click, never by a tick, an Update or the automatic check: the plugin's goes into that one tool and no other, yours is kept as a version, and every other tool keeps your copy as its own, so the plugin's Off or an untick never removes it there. It is offered only where the plugin's can land: where that tool can't hold it, or reads yours from `~/.agents/skills` (Take it over on its Library row first), its line says why instead. Its Undo, in the header or in History, gives back exactly what the click changed, your own again in every tool as before, but a copy you changed since in another tool, which stays as you left it, kept out, and the Undo says so; after the plugin's update meanwhile History offers Go back before this, and both stay versions. Off turns them off (Central Knot keeps them); a tool's box changes that tool alone. **Update** reads the plugin again: what changed becomes the current version, a new item comes in, and one the plugin no longer has turns off, said once on its page; turning it on keeps it as yours. An item you change here (in a tool, or by making another version current) is let go, said once: it is yours from then on, the plugin's updates and its Off leave it, and the plugin's item of that name is not brought in beside it; Use the plugin's on its page takes it in place of yours. Making current again a version the plugin itself gave earlier (History's Undo or Go back before this on its update, or Make current under Versions) is no change: the item stays the plugin's, and while the plugin still gives the version you went back from, only Update on the plugin's page brings that back (it offers it); its switch, a tool's box, a profile or a tool managed again give each tool it goes to the version you went back to, and anything else the plugin gives comes as any update does. In Claude Code, Copilot CLI and Codex such an item comes only with the installed plugin. Push leaves these items out of the Git repo: each computer gets them from the plugin there. A plugin whose parts an earlier version (0.6.0-alpha.1 or before) put into a tool as separate copies has them moved to the library at the first look: each becomes one of its items, in the tools that had it and kept out of the others; one you left out stays out, one you edited is let go as your own (said once) where the plugin is on and Central Knot already knew that tool's folder, and elsewhere stays that tool's own copy, kept out of the item, with nothing said; and one in Claude Code, Copilot CLI or Codex stays that tool's own copy. A tool you left out is decided the same way, so managing it again later brings back nothing you removed and writes over nothing you edited there; a plugin's item none of your tools had (an agent, which Pi took no part of) stays out of every tool until you let one in. Nothing is written in a tool by the move. Until it can be made (first setup isn't answered yet, or a tool's record of its plugins can't be read, say), those copies wait, said on their rows, and nothing of their names is taken in; the plugin waits in Pi and OpenCode too, its line there saying why, and nothing of it changes there. In Claude Code, Copilot CLI and Codex its switch acts as any plugin's meanwhile, and its Off reaches Pi and OpenCode when its parts are moved, leaving a copy you edited there as it is. A copy an earlier version put into Claude Code, Copilot CLI or Codex as a part is that tool's own: the plugin reads as not installed there (its box puts it in where it can go), and Off leaves that copy.
- **One item, however a tool has it**: in the Library, a tool that has an item through the plugin itself is marked **Through a plugin** rather than "No copy", and sync never places a separate copy beside the plugin's. That tool's line in the opened row has the item's switch there (see **Switch one item of a plugin** below). This applies to an item Central Knot holds as that plugin's (one of its items in Pi, OpenCode and Antigravity) and to skills whose SKILL.md is the same; another item that only shares the name stays an ordinary item.
- **What plugins bring, in the Library**: the Library also lists every skill, server and agent an installed plugin brings, in an **Only through a plugin** section, each marked with the plugin's icon and "from <plugin>". They are read from each tool's own records, so a plugin installed with the tool's own command counts too. They are never synced there; their row's switch and each tool's line turn the item on or off.
- **Every tool's line acts, in the Library**: an item a plugin brings, or a library item from a plugin, opened in the Library has a line per tool, and none sends you to another page to act. Where a click changes only this item in that tool, the line has the item's switch. Where it does more, a button names the act and the line says only what the button and tool name don't (with the full sentence on hover): **Install `<plugin>`** in a tool that takes plugins and lacks it ("With 3 skills and 1 MCP server"; counted for Claude Code alone, as Copilot CLI and Codex may read other parts than its marketplace lists; blank elsewhere unless a same-name copy of yours stays; not offered for an agent in Codex, which loads no plugin's agents), **Put its `<kinds>` here** in Pi, OpenCode or Antigravity where none of its items is there (beside "Will follow `<plugin>`", again after its Undo, which leaves them in the Library, Off), naming a name there of yours that stays yours, and **Turn the plugin on** ("Off, kept installed") or **off** ("With …") where that tool has no switch for one item (an agent in Copilot CLI, a skill in Claude Code) or the plugin is off there. **In each tool (?)** explains whole-plugin switches and what item-taking tools get (following the plugin; hooks and commands can't). Install, Put its `<kinds>` here and Turn the plugin on (for a copy kept off) do exactly what that tool's box on the plugin's page does, with what the line says while it waits and runs ("Installing varo-risk in Copilot CLI… This can take a few minutes."), and its result on a line of its own and in the header with the plugin page's own Undo, which stays until you close it or act again (said when you come back to the Library, if it ended while you were elsewhere); a new act on a plugin ends the result and Undo before it; Turn the plugin on or off is the tool's own switch, with its Undo. A line that can do nothing says why, and a tool that gets an item only with its plugin is said so on the row ("not in Codex: it gets it with the plugin"), not as one that can't take it. A strip under the description names the plugin, its version and where it is installed, with **Its page** to look at it (or where it is handled when unlisted).
- **From**: a menu in the Library's toolbar shows only what came from where: your own, any plugin or one plugin, any library source or one. A row from several places (your skill that a plugin also brings) shows under each. A plugin's page and its row on Plugin marketplaces have **Its items in the Library**, and each library source with items there **Show in the Library**.
- **Switch one item of a plugin**: in the Library, the switch on a tool's line in the item's opened row turns that one item off or on in that tool, at once, with Undo; the row's own switch does it in every tool that has the item. Each uses the tool's own switch, the plugin's files are never touched, and what you turn off stays off through plugin updates and sync:
  - a **skill** in Copilot CLI and Codex (also on the plugin's own page);
  - an **MCP server** in Claude Code, Copilot CLI and Codex;
  - an **agent** in Claude Code (Claude is no longer offered it; a session you start as that agent yourself still runs).
  - Where a tool has no switch for one item (a skill in Claude Code, an agent in Copilot CLI), that line's switch and the row's own turn the **whole plugin** off or on in that tool instead, with everything it brings there, and say so before the click; the result names what went with it, and one Undo puts it all back.
  - Turning on one item of a plugin that is off as a whole turns the plugin on with its other switchable items held off. Whatever of the plugin has no switch of its own in that tool comes on with it (its skills in Claude Code, say), and the tooltip names those first.
- **Update**: where a tool has an older version than the marketplace, the list row and plugin page offer Update, which runs at once; **Update all**, for a marketplace with two or more behind, runs every update it names in one run, those the filter hides too. Each tool refreshes its copy of the marketplace and updates through its own command. An update can't be undone, and its tooltip and its result say so. A plugin turned off in a tool is still off after its update. The switches under **Skills** (a skill's in Copilot CLI and Codex) act at once too, with Undo.
- **Updates that arrive by themselves**: every four hours, with the window closed too, Central Knot reads your marketplaces again and makes the updates that Update all would offer, through each tool's own command. It only updates what a tool already has: a plugin turned off stays off, and one you uninstalled from a tool is not put back. A note on the Plugin marketplaces page says which plugins were updated in which tools and what couldn't be; a failed update is tried again, less often each time, and the log has each step. It is on unless you turn off **Update plugins automatically** in Settings, and it pauses while Automatic sync is off. **Check now** in Settings runs a check at once.
- **What plugins hold, read in the background**: once a home is open, Central Knot reads the names, descriptions and first lines of the skills, agents and MCP servers in the plugins of the marketplaces listed here, and keeps them in its own data folder (never in a home or a tool). A plugin kept in its marketplace is read from the marketplace's copy; one kept in another repository is fetched as text only, at its pinned commit, with this computer's git: the list of its files, then only the files that name and describe its items. Nothing is installed or run. The first reading downloads about 0.1 MB for each plugin kept elsewhere (about 30 MB for the two default marketplaces); after that only a plugin whose pin moved is read again, and one with no pin is looked at once a day. A repository that can't be read is tried again later, less often each time (Refresh on the Plugin marketplaces page tries it again at once); one whose server doesn't say it can send only part of it is not read. **Read what plugins hold** in Settings says how much is read and turns it off (it is on by default, whether or not Automatic sync is); turned off, nothing is downloaded and what was read is kept. The Library's Find shows what is read under **In plugins you don't have**.
- **A tool you install later**, or one whose Manage switch is turned on again, gets each plugin that is on and not kept out of it, at the next check (made at once when the tool turns up or is turned on): through its own command; in Pi, OpenCode and Antigravity, the plugin's items Central Knot doesn't have yet (the ones it has reach the tool as any item does). The note says so. It follows the same switch and pause as the updates: while either is off, nothing goes in by itself, and the tool's line on each plugin's page says it waits (a tick on its box puts it in at once). A plugin that is off in one of your tools' own settings is not brought to it by itself (its line says why; a tick puts it in). The tool is new for that one check: an install that fails is said in the note and on the plugin's page, where a tick puts it in, and is not tried again by itself; and one you take out of it later with the tool's own command stays out. Nothing is ever uninstalled by itself.
- **No longer offered**: a plugin its marketplace has dropped stays installed as it is, marked "No longer offered", until you uninstall it.
- **Cowork**: where Claude desktop is installed, Claude Code's card says Cowork uses the plugins in your Claude account and each plugin's page notes in its **Your tools** card where to add plugins for Cowork in Claude desktop, under Customize › Plugins (as Claude documents; not tried here). (When this was tried on Claude desktop 5.1231.0, a plugin put into Cowork's folder on the computer was listed by Claude desktop, but the new Cowork session, which ran in the cloud, didn't load it: `docs/capability-data.md`, section 7.)
- **Desktop apps without a CLI**: Claude desktop (its Code tab), the GitHub Copilot app and ChatGPT desktop each carry their own copy of the tool. With no CLI installed, Central Knot runs the plugin commands through that copy, and the tool’s line on the plugin’s page says which route it uses. A CLI is used when one is installed. If the app's copy isn't on disk yet (for example, the Code tab has never been opened), the plugin can't go into that tool, and its line says why. macOS app locations only.

### Profiles

A profile is a named set of skills, MCP servers and agents to have on, such as *Incident* or *Development*. Switching to one, from the Profiles page, the status bar or the menu bar icon's **Profile** menu, turns what it has On and everything else of yours in Central Knot Off: each item's own On and Off, so what goes Off leaves the tools and Central Knot keeps it, and a tool an item is kept out of stays so (and, for a profile that switches plugin items, each plugin's item copy by copy as below).

- The Profiles page shows a short header line ("In use · 60 on, 16 off", "Switching turns 1 on, 14 off", or "Can’t switch · issue-tracker is off in Codex" when held, with **Turn on issue-tracker in Codex** in Switch's place where one press turns the plugin on there, as the Library's line does, what it does in its **(?)**, its result and Undo on the page and the header worked out again; a row held in another plugin or tool has its own; after Undo switch the result says the plugin stays on there) with a **(?)** mark wherever the full sentence (also shown in both menus) says more than the plain line, including how many of the items a switch turns off still load in a tool from a copy Central Knot doesn't write ("Switching turns 10 items off; 4 still load from the shared skills folder, in Copilot CLI, Codex, Pi or OpenCode"), saying how where every one of them loads the same way (from the shared skills folder, through a link, from a copy of yours there, from another tool's folder, which OpenCode reads in Claude Code's, through a plugin that brings the same item and that the switch leaves as it is), else "another way"; and apart, a plugin's items that stay on in a tool ("1 stays on in Claude Code, through its plugin"), counting a copy the switch itself turns on ("1 is on in Copilot CLI, through its plugin"). Where the switch turns the plugin's item too, the plugin's copy is counted only on the plugin's line (or among what the switch turns on), not as one of yours; a separate copy of your own, such as your folder in another tool, can still count. Each such row the profile leaves out says it under its name ("Copilot CLI, Codex, Pi and OpenCode still load it from the shared skills folder.", "Claude Code still loads it through a plugin.", or for a plugin's agent "Stays on in Copilot CLI."). Unchanged rows leave their state cell blank (hovering any row's box keeps its live state, and a row's description sits on its name's hover); while previewing, **Changes N** narrows the list to the changing rows grouped **Turns on** then **Turns off** (showing kind icons with kind tooltips, naming the kind after rows that share a name, keeping per-tool words without repeating the heading, hiding the **Switching** column head when no cell under it has words, and keeping the pinned rows and counts until closed), and under 880 px of page width the profile list folds to a one-line picker beside **New profile** (marking the profile in use with "· in use"). After the switch, its result says what a read of the tools made after it finds, which can show a copy the preview couldn't see (a plugin's copy in a tool that also had Central Knot's copy of the item, until the switch removed it; or a copy a tool loads once the switch turns a plugin's part off there); History's entry counts what it turned, as before. A tool's copy the read can't tell about (one it can't see for sure, or two copies of which Central Knot wrote one, but for the copy a tool reads in another tool's folder) is not counted. Ticking only changes the profile (noted in the **(?)** beside the **In profile** column head).
- The profile in use is worked out, never stored: the one a switch to which would change nothing and hold nothing back. It shows on the page, in the status bar and beside the menu bar icon, and follows by itself: turn something on or off by hand, take an item in, Pull one, or delete a copy by hand, and the name follows (No profile when none matches; both names when two profiles have the same items). Before a click in the Library that would end the profile in use, the control says so: an opened row says "If on, only this item changes: Everyday stays saved but stops being the profile in use." at its head, Turn these off and Select's Turn on or Turn off show "Would leave Everyday" right after them ("Either would …" after both), and a switch's hover and description say it too ("may" while an earlier click is still being carried out); Undo, or switching to it again, puts it back in use.
- An item a profile names that is not in Central Knot now (deleted, or only found in a tool) is skipped, and stays in the profile. A profile with nothing in it is not offered to switch to.
- For a profile that switches plugin items, a plugin's skills, MCP servers and agents are rows too, each under its kind, "from" its plugin, whichever tools have it (installed there, or placed in Pi, OpenCode and Antigravity). A switch turns each on or off one tool at a time by that one item's own switch: Codex's and Copilot CLI's for a skill, each tool's for a server, Claude Code's for an agent, and in Pi, OpenCode and Antigravity its copy there. In Claude Code, which has no switch for one skill of a plugin, a plugin goes on or off whole: on while the profile ticks any item it brings there, off while it ticks none (one that brings nothing a profile can tick, only hooks or commands, is left as it is), its MCP servers' and agents' own switches set toward their ticks before it comes on, so nothing the profile leaves out loads meanwhile. It never installs a plugin. Each row's column says what a switch does to it, naming the tools where they differ ("Turns off in Codex and Pi"), and stays blank when unchanged. Where a tool can't switch one item (an agent in Copilot CLI) it stays on: the head of Agents says so once, and a row the profile leaves out says so under its name ("Stays on in Copilot CLI."). While Claude Code has a plugin the profile lists, a line under Find says the rule once ("Claude Code takes a plugin whole: it is on there while any of its items is ticked, and off while none is.") and, under "Switching turns, in Claude Code:", names each plugin the switch turns on or off there with what goes with it ("writing-kit on, with brainstorm and outline too", "solo off, with its 1 skill and everything else it brings there": its commands and hooks stop too), the one-skill and skill-less ones as well; the header's **(?)** and both menus count them, a sentence for each direction ("Turns 2 plugins off in Claude Code"). A skill the profile leaves out that comes on with a ticked item of its plugin says so ("Comes on in Claude Code too, with write.", set in beneath that item's row, its own box adding it to the profile; in use, the header counts such skills apart: "2 with plugin" and in its **(?)** "1 more on in Claude Code with its plugin", and its state column reads "Off · on in Claude Code" where another tool has it off), and the ticked row names what it brings on ("Brings brainstorm and outline on in Claude Code."); the switch's result says it after, in the Library's words ("write is on in Claude Code. Its whole plugin writing-kit was turned on there, with its 2 other skills."). A plugin goes on there only once its servers' and agents' own switches went through, and if it doesn't come on every switch made for it is put back. History keeps the steps a switch ran on such a plugin; its Undo turns them back while the plugin is as the switch left it, and otherwise leaves it and says it changed since. In Copilot CLI a plugin's MCP server and another server of the exact same name (yours, or another plugin's) are one switch (while both yours and a plugin's are configured, Copilot CLI runs the plugin's): the off-switch for that name is cleared whenever the profile wants either one — even after the plugin is turned off whole, uninstalled or drops that server — never written over a server of yours only found in Copilot CLI, and written in one switch when the profile leaves every managed server of that name out; where the profile names yours and not the plugin's, the plugin's row says so ("Stays on in Copilot CLI, which runs the plugin’s “issues” instead of yours (same name)."), its state column reads "Off · on in Copilot CLI" when off elsewhere, and that standing fact does not block "In use". An Undo never puts a Copilot CLI off-switch back when a server of yours (found or On) uses that name now, and says so. Where the whole plugin is off in a tool other than Claude Code, nothing is turned on there, and the row says so; where a tool's own switch can't be written or its copy can't be read, the row and the switch's result say so, and the other tools are switched all the same. "In use" covers what can be switched: two profiles that differ only by an agent Copilot CLI alone has are both in use, as are two that tick different skills of a plugin Claude Code has on while neither leaves out a server or agent of it that is on there; while a tool's copy of a plugin can't be read, no profile that switches plugin items is in use (an older profile that leaves plugin items alone still qualifies by your own items). A profile that differs only where a switch can't reach says why in its header ("Can’t switch · issue-tracker is off in Codex", with the press below or, where it can't be pressed, the reason in view, such as "Can’t switch · issue-tracker’s marketplace isn’t added here", with Open issue-tracker), and choosing it from a menu is refused in the same words.
- A plugin's item a profile names that no tool has now (the plugin uninstalled, the item gone in an update, or its Pi copy changed so it is your own item now) is skipped, and stays in the profile. The Git repo carries neither profiles nor a plugin's items, so Push and Pull change no profile; a profiles file brought to another computer by hand names the same items there, skipped until a tool there has them.
- **Profiles saved before plugin items could be ticked** (format 2) keep the reach they had: switching to one changes your own items as before and leaves every plugin copy as it stands — except clearing a Copilot CLI off-switch that blocks a server of yours the profile names (said in the preview and the switch's result, since the plugin's server of that exact name comes on there too), "In use" goes by your own items (and any such blocked server), and the page and both menus say "Plugin items stay as they are." beside the count (naming any Copilot CLI shared-name exception). On its page, plugin rows stay hidden behind **Choose plugin items for this profile**; renaming it, ticking your own items or using **Start from what's on now** keeps it leaving plugin items alone. Choosing plugin items changes only the profile (starting with none ticked, no tool written), and from then on it works like a new profile: from the next switch ticked ones turn on and unticked ones turn off wherever they can be switched, and there is no way back to leaving plugin items alone. New profiles switch plugin items from the start; a plugin installed later joins no profile, so older profiles leave its items alone while profiles that switch plugin items turn them off at the next switch. A format 2 file is read as-is and never rewritten until you change a profile, which writes format 3; an older Central Knot refuses a format 3 file ("saved by a newer Central Knot") rather than dropping plugin items from it.
- The Profiles page lists every item of yours (and, for a profile that switches plugin items, every plugin's item) except those only found in a tool; a short line under Find says how many in your tools aren't in Central Knot, with a **(?)** card noting they are under Found in the Library, with Add on each that can be taken in.
- A switch is one History row. **Undo switch** turns back each item still On or Off as the switch left it, each with a History row of its own; an item whose On or Off differs now stays as it is. A plugin's item is put back by its own switch in each tool the switch turned it in and where it is still as the switch left it and still the plugin's, all in one History row of the Undo's own, which marks the switch's row Undone; a copy placed in Pi or OpenCode goes only from the tools the switch put it in (kept out of those, where another tool has it since). Each copy it leaves is named with why: changed since, edited by hand since (so it is your own now), or deleted by hand since.
- Profiles are kept in `.central-knot/profiles.json`. One from before profiles were sets of items (0.6.0-alpha.1 and earlier) is moved the first time this version syncs the home, and kept beside it as `profiles.v1.json`: each tool switch the earlier profiles set is released, also where the item's copy is not there now, an item they held off in every tool that has it is turned Off (one History row says which, with Undo), every agent that is on joins every profile, and nothing else changes: an item that stays on is left to sync as ever. (A home an earlier build moved may still list a Claude Code switch for a server that is Off, which that build kept until the server's entry left Claude Code; it is released once the server is on there again.)

### History

Lists what Central Knot and sync did, with **Undo** or **Restore**. Every replaced or removed version is kept first in `.central-knot/`, as a version of its item. Undo says what it could not put back. A skill's, server's or agent's entries offer what would still change something: **Undo** makes the version from before an edit current again, **Turn it on** or **Turn it off** (or **Turn it on in** and **Turn it off in** one tool, as a copy sync put in a tool with no click of yours offers: Copied to <tool>; offered while that tool is managed, and the entry says when it isn't) is its switch, **Restore** brings back a deleted agent. A tool's Manage entry offers **Manage <tool>** (asking in the row the question its card's switch asks) or **Leave <tool> out again** while the tool is still here in that state, disabled with the same reason on a locked home. In a row’s sentence, a list of three or more tools (that is not all of them) folds to `<N> of <M> tools` (or `<N> tools` if a tool has since left) and opens to their names below the sentence. History keeps things for 30 days by default; **Keep** on History (and **Keep history for** in Settings) offers 7, 30 or 90 days, with a warning before shortening.

### Sessions

One day's sessions in Claude Code and Codex, **Today** or **Yesterday**, read from each tool's own session history on this computer (Claude Code's `projects/`, Codex's `sessions/` and `archived_sessions/`) each time the page opens, a day is pressed or **Refresh** is pressed. At the top, the day's dollars, then each tool's, and the tools not counted (Copilot CLI, Pi, OpenCode and Antigravity, where they are here); then a row a session: when, the tool, the project folder's name and its dollars, an agent's sessions included. Opened, a row shows each model's cost and its input, cached, cache-written and output tokens, then the sessions its agents ran, each marked Agent; the day's models are under **By model**. The dollars are what those tokens would cost at each model's API price, on a subscription or not (a subscription's bill is its plan's price), from a price list shipped with the app (Pydantic's genai-prices, MIT): "≈ $1.20", or "≈ $21.40 or more" where one-hour cache writes are priced at the shorter cache's rate or, for a tool's figure and the day's, where some of that tool's session history could not be read. A request with no matching rate in the list (for its provider, its model, or its speed or tier) is left out of the dollars and counted beside them ("2 unpriced"); why, whose prices they are and the price list's date are on hover. Claude Code's own figure for a session, where it saved one and the whole session lies in the day, is shown in its opened row and added to no total. Nothing is kept until you click **Start keeping session costs** beside Today/Yesterday (or turn **Keep session costs** on in Settings › This home): consent is stored per home in Central Knot's own settings, and while it is on Central Knot sweeps Claude Code's and Codex's session files into `.central-knot/sessions/` (request times, models, token counts and estimated prices without message text) after the home opens and every 15 minutes while the app runs (independently of Automatic sync). Turning it off with **Stop keeping** on Sessions or in Settings stops further sweeps without removing what was kept. Today and Yesterday still read live from the tools' own files; a home that keeps session costs is also offered **7 days**, today and the six days before, read from what was kept (a session whose file the tool has since deleted included): the period's dollars, then a line for each day with sessions, with its dollars and how many sessions, newest first and today's open where it has ten sessions or fewer, each opened to its rows. Choosing it shows what was kept at once and asks for a sweep; while it is shown, the figures are read again whenever a sweep ends, the 15-minute ones too; each request keeps the price it was given, and the price list dates are on the total's hover.

### Library sources

A GitHub or GitLab link that skills, agents and MCP servers are read from, never written to. Paste a link to a repository, a branch, a folder or a file in one (`owner/repo`, `github.com/owner/repo`, or any address git clones, works too; a link that names no branch reads the default branch, by its name) and click **Look**: Central Knot fetches it with this computer's git and its sign-in, one commit deep, and says what it found, item by item, before anything is kept. A skill is its whole folder (its SKILL.md and every file beside it), named as its SKILL.md names it. An agent is a file in an agents folder at the link (`agents/`, `agent/`, `.claude/agents/`, `.github/agents/` with `*.agent.md`, `.opencode/agent(s)/`, `.codex/agents/` with `*.toml`, or the link's folder itself when it is named `agents` or `agent`), or loose in the link's folder, a `*.agent.md` or a `.md` whose front matter names both `name` and `description`; never a README, CHANGELOG, LICENSE, CONTRIBUTING, CLAUDE or AGENTS file, a SKILL.md, a file inside a skill's folder, or a file in any other folder. It is named after its file (`reviewer.md` is the agent reviewer, whatever its front matter's `name` says), and a `.md` with no front matter is a page, not an agent. The same agent in two tools' forms is one agent; two files of one name that differ, or two in one tool's form, are both said on the row and not brought in. Some miss: a link straight to a commands or prompts folder brings each file there that names `name` and `description` as an agent (Off, and deleting one keeps it out); agents in a subfolder of an agents folder are read only from a link to that subfolder; and a loose `.md` whose front matter doesn't parse is an agent that can't be read, so while it is there the source turns no agent off. An MCP server is an entry of the `.mcp.json` in the link's folder (Claude Code's project file: `{"mcpServers": {…}}`, or the servers bare), read as Claude Code reads it; never a tool's or editor's own settings (`.vscode/mcp.json`, `.cursor/mcp.json`, `.claude/settings.json`), an `mcp.json` without the dot, a `.mcp.json` in a folder inside (a link to that folder reads it), or Central Knot's own repo layout (`mcp/<name>.json`), and a `.mcp.json` in a skill's folder is that skill's file. A server that would not run once copied (it runs files from the repository, such as `./server.js`, a relative `cwd` or `${CLAUDE_PLUGIN_ROOT}`, or runs from inside an app), one that has both a command's fields and a URL's, and two whose names differ only by case are said on the row and not brought in (a known miss: it stays out for as long as it is there), and the source still turns its other servers off. A `.mcp.json` that can't be read, or an entry with no command or no URL, is said on the row too, and while it is there the source turns no MCP server off. Likewise two skills or agents of one name, or a skill whose name no tool can store or that can't be copied as it is (a link inside, say), are said and not brought in, and hold back nothing else. **Add** brings each one into Central Knot **Off**: in no tool until you turn it on. A name Central Knot already has is linked when it is the same, or when it is still as this same link gave it before (a source removed and added again), and otherwise not brought in; one deleted from Central Knot stays deleted, and **Add** on the source's row brings it back. **Sync this source** reads the link again, as Central Knot does by itself once a day while Automatic sync is on (and at launch when a day has passed): what changed there becomes the current version, On or Off as it is, unless you changed it here. An item you changed here is never written over by its source: your version stays current, in Central Knot and in every tool, and its row on its page and on Library sources says the source has an update. **Merge** on the source's row puts the source's changes into yours, file by file for a skill, for an agent part by part (its name, description and prompt), and for an MCP server part by part (its command, arguments, working folder, URL, and each environment variable and header by its name): a file or part only one side changed takes that side's, and one both changed is merged line by line (by this computer's git), or for a server, whose parts have no lines, clashes; the merged version becomes current in every tool it is on in, and yours and the source's are kept as versions. Where both changed the same lines, or one side deleted a file the other changed, Merge changes nothing and names the files or parts. **Replace mine** makes the source's version current and keeps yours as a version. **Keep mine** keeps yours current and writes nothing: the source's version is kept as a version and no longer waits, and the source's next change is compared with it (a Merge whose result is exactly yours ends the same way); after a clash, make the source's change in yours by hand, then Keep mine. History's Undo of Merge or Replace mine puts yours back, and where you had changed it, the update waits again; Keep mine's Undo takes it back; or leave it as long as you like. After a Merge it still differs from the source, so the source's next change waits for you too. Making an older version current counts as a change here; turning it off and on, or a tool managed for the first time, doesn't; edit it back to exactly what it took from the source and it follows the source again. An item the source no longer has is turned off and is no longer from it, so later checks leave it as you set it. While it stays off, the source's row and its row on its page say so, worked out each time from what is kept (so after a restart, and after History's days, too); turning it on, there or anywhere, is the way back. If it comes back there while you haven't changed it here, it is from the source again (the source's version current), and going again turns it off again; if you changed it, it stays as you have it, and the source's row says why it isn't brought in. An item there that can't be read (an agent whose front matter doesn't parse, say) is said on the source's row, and while one of a kind can't be (or nothing can), nothing of that kind is taken to be gone. An agent's own fields (`tools`, `model`), and a server's other fields in the `.mcp.json` (`timeout`, say, which are Claude Code's own), come from the source only for a tool where Central Knot keeps none of its own for it, so a first turn-on there writes the source's file or entry exactly and nothing you set in a tool is written over; the cost, until this is decided otherwise, is that a change at the source to those fields alone never arrives (Sync this source says nothing came in), and a change to the prompt (or a server's command, say) and those fields together brings the prompt only. A server's update or drop reaches every tool at once, Claude Code included. Each change is in History. **Remove** forgets the source and leaves what it brought as it is.

Any GitHub or GitLab link goes in the one field. **A plugin's own folder** (a `.claude-plugin` or `.codex-plugin` folder, no marketplace file) is a source like any other: it is read as any link's folder is, and then for what its own files hold elsewhere, as Claude Code finds a plugin's (the folders its `plugin.json` names, `skills/`, `agents/`, `.mcp.json` and servers inside `plugin.json`, or one skill at its root), each name once, so a source never loses an item because its repository gained a `plugin.json`. Its skills, agents and MCP servers come in Off, each with its own switch, and follow the link as any source's do (Merge, Replace mine and Keep mine for an edit here). A skill is named as its SKILL.md names it, as at any link, so one read from the plugin's folder and one read from a link to its `skills/` folder are one item. Its commands, hooks, LSP servers and `bin` folder don't come, and Look and the source's row say which (Central Knot installs plugins only from a marketplace). A `plugin.json` that can't be read holds back every kind's drops while it is there, and a folder of its skills or agents that can't be listed holds back that kind's. **A marketplace** (a `marketplace.json`), or a plugin its repository's marketplace lists, is no source: Look says what it is and, for a marketplace at its repository's root on its default branch (`…/tree/<default>` too), offers **Add to Plugin marketplaces**, which opens that page and adds it there as that page's own add does (nothing installed, no plugin turned on, nothing kept on Library sources); the look and the field clear only when the add worked. On another branch or in a folder, Look says why it can't be handed over, and that a clone's folder can be added on Plugin marketplaces with **Folder…**. A source whose link later holds a marketplace turns nothing off, and its row says to remove the source, then look at its link again. An agent, a server or a skill that comes both from a source and through a plugin installed in Claude Code or Copilot CLI is placed once, the plugin's, while it is the same (a skill's SKILL.md, an agent's or server's shared part), whether the plugin or that item is turned off there or not: the row's Through a plugin box is its switch in that tool. Central Knot's copy is placed there again once the plugin is uninstalled there, or no longer brings that item. Known misses: a plugin whose own repository another marketplace lists, and a link to another folder inside a marketplace's repository (its `skills/`, say), are read as items, so where one of them differs from the plugin's of that name both are placed; a plugin with only `.codex-plugin/plugin.json` is read at the default places, not at the paths that manifest names; and after Sync this source updates such an item, the plugin's version stays alone in that tool until the next pass places the new one beside it.

### Git repo

Keeps the Managed set (skills, MCP servers, agents and base instructions) in a git repo on GitHub, GitLab or any git remote. Connect with a repo address and an optional branch; Central Knot uses this computer's own git sign-in. Nothing moves until you click **Pull** or **Push**. Push leaves out an item a plugin brought (Plugin marketplaces: its items in Pi, OpenCode and Antigravity), which each computer gets from the plugin there. Pull brings the repo's changes into your tools through the normal sync, so each one is in History with Undo. For agents the repo and Central Knot exchange versions: Pull makes the repo's content the agent's current version, marked as pulled from the Git repo, and puts it in every tool where the agent is On (an agent Off here stays Off; one new here comes in On); Claude Code takes the repo's file as written, its own settings included. One removed in the repo is deleted from Central Knot, with Restore in History. Push sends every agent in Central Knot, On or Off, at its current version: only Delete from Central Knot takes one out of the repo. Skills and MCP servers go the same way (a server's file in the repo carries Claude Code's own fields for it; only servers in Central Knot are sent, not ones only found in a tool). Push makes one commit of the Managed set. The page lists what would come in and what would go out, and the sidebar shows the counts. The repo layout is `skills/<folder>/`, `mcp/<name>.json`, `agents/<name>.md` and `instructions/base.md`; other files in the repo are left alone. A skill from a source is sent like any other, without its link.

### Settings

Start at sign-in, Appearance (System, Light or Dark), Updates (build version, Check now, Update and what the last check found), Synchronize everything and Keep session costs for the open home (Synchronize everything is kept in the home's `.central-knot/sync.json`, unanswered until first setup asks or it is switched here; while off, its row says how many found items it would add now, and either way how many wait for a choice of copy, with **Choose copies**; turning it on shows a result band with History's **Undo** right there (and its help on hover); Keep session costs is kept per home in `app-settings.json`, off until enabled, and sweeps session costs into `.central-knot/sessions/` at open and every 15 minutes), Update plugins automatically (always noting **Updates can’t be undone.**, with Check now and what the last check came to), Read what plugins hold (with the first-download estimate when plugins live outside their marketplace and how many are read), Keep history for (7, 30 or 90 days, with a warning before shortening), and the log: **Show log** shows its last 200 lines under its row, newest in view, times in UTC as in the file (with **Show 200 earlier lines** back to its start; at its foot, where the page lands, **Refresh log**, **Hide log** and **Open log folder** again), and **Open log folder** opens its folder. Standing explanations for switches and the log sit behind each row's **(?)** mark.

On Linux, Start at sign-in is the file `~/.config/autostart/<bundle id>.desktop` (`$XDG_CONFIG_HOME/autostart` where that is set), which opens the AppImage with `--hidden`; turning it off removes the file, and the switch reads the file back each time (a desktop's settings that remove it, or mark it `Hidden=true`, turn it off). The launcher entry is `~/.local/share/applications/<bundle id>.desktop` (`$XDG_DATA_HOME/applications`) and its icon `~/.local/share/icons/hicolor/512x512/apps/<bundle id>.png`; the window takes the entry's name as its app id, so a Wayland taskbar shows its icon. The bundle id is `com.centralknot.firstlook`, or `com.centralknot.alpha` for the alpha. Both entries carry the line `X-Central-Knot=true`: an entry of that name without it, or a link there (wherever it leads), is never written over or removed (for Start at sign-in, the row says so and names it). At each start the launcher entry is written where there is none, and the icon where nothing is at its path (one you removed comes back; your own picture there stays); nothing removes either. When the AppImage has moved (an entry's `Exec` runs another file ending `.AppImage`), only that program's path changes (the autostart file's too, while it is on): other arguments you added, such as `--no-sandbox`, and every other line stay as you have them. An `Exec` that runs anything else, such as `env VAR=x …` or a script of your own, is yours and is left whole. Only the AppImage writes them: a development run, or the app run from anywhere else, says only the AppImage can start at sign-in.

### Updates

The Mac app updates itself from this project's [GitHub releases](https://github.com/njfife/central-knot/releases). It asks GitHub's public API for the releases (one page: the 100 newest, previews and alphas together) shortly after it opens, every 15 minutes while it runs (window closed too), and when you come back to its window after five minutes or more; nothing about you is sent. The end of the sidebar, at the bottom left, always has the update control: **Check for updates** (circular arrows; a click checks now, and they spin while it checks). When there is a newer release it becomes a filled **Update available** button: one click downloads it, shows progress (a ring round the arrow), and restarts into it. If an instructions draft isn't saved or a plugin change is under way on the Plugin marketplaces page, it waits: the control becomes an outlined **Restart to update…** with a warning mark, and a click opens Settings › Updates, which says what restarting would lose beside its own Restart button. A download that fails offers **Try the update again**. It never restarts during a write. In the folded sidebar the control is its icon alone, with its name as the tooltip. The status bar shows the version, and after an update it says once which version is now running, with its release notes.

A build made from a preview is offered newer previews and finals; one made from a final release, finals only. **Central Knot Alpha** is a line of its own, for trying work that is still moving: an alpha is a separate app, with its own settings and log (`~/Library/Application Support/com.centralknot.alpha/` on a Mac, `~/.config/com.centralknot.alpha/` on Linux), that replaces Central Knot when installed, and Central Knot replaces it (see One build on a Mac); it updates itself the same way, but only to newer alphas, and a preview or final build is never offered an alpha. The new app must be signed by the same developer before it replaces the old one (Electron's Squirrel.Mac checks this), and a failed or interrupted update leaves the installed app as it was. Settings › **Updates** shows the version and release tag in use, **Update**, **Check now** and the last result. An app outside the Applications folder (or `~/Applications`), an unsigned or untagged build and a development build don't update themselves; Settings says why and links the release page, and the sidebar's control opens it (a newer release such a copy can't install shows there as an outlined **Update available**; a build that never checks has a faint **Updates**). **Check for Updates…** is in the app menu.

On Linux the AppImage doesn't update itself yet. It checks the same way, and a newer release in its line that carries an AppImage shows as the outlined **Update available**, which opens the release's page in your browser to download the new AppImage; a release with only Mac files is no update there. Settings › Updates says this copy doesn't install updates itself yet, with that page. Windows has no releases yet, so nothing is shown there.

**An earlier version on a home this one has written.** Updates only go forward. Once this version syncs or writes to a home that has a sync record (one it only opened to look at, such as a backup waiting for Resume: from Resume or its first write), an earlier version (0.7.0 alpha 5 and before) stops syncing it: its Overview says the sync record was written by a newer Central Knot, and it copies no item of the Library there. It still saves instruction files, and installs, removes and updates plugins in each tool's own way, when clicked or on its schedule. Installing this version again carries on where it was, with nothing lost.

**One build on a Mac.** Only one build of Central Knot is installed at a time, and a new one replaces the other. A build is its bundle id: any starting `com.centralknot.` (the standard app, the alpha, a custom build) other than this one's. Each build looks before it does anything (at launch, before the window's first view, the first sync, its login item and a bundled build's marketplace or feed), then again first in each view; a background sync reads the home without looking, so a build installed meanwhile is noticed at the next view. It stores nothing. It looks for a bundle at the top of `~/Applications` or `/Applications` whose XML `Info.plist` names such an id (called by the name it gives there), and any running copy of the builds found, of the standard app, of the alpha and of the build the open home's record names, by bundle id, wherever it runs from (Downloads, a translocated copy, the Trash). A build in a subfolder of Applications, or a custom build running from elsewhere that the home's record doesn't name, isn't found. It looks only in the installed app on a Mac; where an Applications folder can't be read it carries on, and its log says so.

While another build is found, this one is held: it writes nothing in the home or your tools (each write is refused in one sentence naming the other build), adds no login item (one it had stays), its menus' Automatic sync, Sync once, Profile and sign-in items can't be used, and its window shows one screen instead of the pages, even when it started at sign-in; closing that window quits it. The screen says which build it found and where, what is going on and what its buttons do: **Replace** the other build, or **Quit** this one; for a build that only runs, from outside an Applications folder, **Quit** that build in place of Replace. Under the buttons: what stays (the skills, MCP servers and agents, which of them are kept in step, and History: they live in the home), what becomes of the other build's settings, what the button does step by step, and how to keep the other build instead. The update control stays. Replace is offered only by a copy running at the top of an Applications folder: one opened from a disk image or Downloads says to move it there first, and one running from the Trash offers only Quit.

Replace asks every running copy of the other build to quit (a signal to stop, so macOS asks nothing) and waits up to 20 seconds (a build finishing a plugin step holds its quit for up to 15), checks the bundle again and moves it to the Trash, where it stays until the Trash is emptied. One still running, one whose state macOS can't say, or a bundle that changed meanwhile is left where it is; where macOS refuses the Trash, nothing else is tried and **Show in Finder** is offered, then Refresh clears the screen once it is gone; either way this build stays held, and the screen says why. The other build's own settings folder stays. Nothing happens by itself.

A home's record (`.central-knot/sync.json`) names the build that made it or last took it over. At each look that leaves this build free (at launch, in each view and switch of home, and once the build that held it is gone, however it went: Replace, Quit, or moved to the Trash by hand, then Refresh), a record naming another build is taken over by itself, and names this build from then on; a look that couldn't answer takes nothing over. Where that build's settings folder is found, History's days become the longer of the two, so no take-over shortens History. Where that build is the one that held this build, or the home is this Mac's own, its other choices that decide what is written come too (whether Automatic sync is on and whether plugins update by themselves), so your tools see no change, and this build remembers the record, so nothing asks to Resume; the page says so, and where its settings folder isn't found, it says this build's own settings stay. Anywhere else (another folder, the Practice copy) nothing else is copied, and a home this build has no memory of waits for **Resume**. A home folder that two Macs open is synced by each Mac's build once resumed there, and its record names whichever build looked at it last (two Macs on different builds rewrite it at each view). A record that can't be written is left as it is, and the log says why. A Central Knot from before this version stops syncing a home whose record names another build. Each build adds itself to start at sign-in at its first open that finds no other build, and can't turn another's entry off: if a removed build still starts at sign-in, turn it off in System Settings › General › Login Items (started from the Trash, it is found running and offered Quit).

## Custom builds

A custom build is Central Knot made by someone for their own group, under its own name. It replaces the standard app when installed, as any build replaces another (see One build on a Mac), and keeps its own settings (`~/Library/Application Support/com.centralknot.custom.<its id>/` on a Mac), so the two never share or overwrite each other's settings, and it never takes the standard app's updates. Settings › **This build** says what it is.

A **bundled build** also carries a marketplace, with every plugin's files inside the app. Whoever opens it needs no access to where the marketplace came from:

- **Plugins** lists that marketplace first, marked **Built in**, under the name and picture the build gave it. Its About tab says which release of the marketplace this is. It can't be removed from the list.
- At the first open the build unpacks the marketplace into its own data folder (`bundled/marketplace` there). That folder is an ordinary folder marketplace from then on: its plugins are browsed, installed, updated and turned off (kept installed; Copilot CLI's live copy uninstalled) the same way as any other's.
- A plugin the marketplace lists but the build could not pack (an npm package, say, or a repository that could not be fetched) is still listed, says that it can't be installed from this app and why (About has the reason, and who to ask).
- **In your tools' own plugin lists.** The first time it opens this Mac's home, the build adds its marketplace to the own plugin list of each tool found here that takes plugins (Claude Code, Copilot CLI, Codex), with that tool's own command, so the plugins also show there. It installs nothing, and the status bar says so and which tools. This is the one thing a bundled build changes without being asked. Each tool is given it once: take it out in a tool and it stays out, until **List in …** on the marketplace's About tab puts it back. A tool installed later gets it the next time the home is read. A tool that already has a different marketplace under the same name is left alone, and so is a folder opened as a home. The About tab says which tools list it, and that the app added it.
- **Newer plugins without a new app.** A build made with a feed (`--feed`) looks at that address shortly after it opens and every few hours while it runs, window closed too. When a newer release of the marketplace is published there, the app downloads it, checks it against its manifest and puts it in use, and the status bar says so. Claude Code and Copilot CLI load a folder marketplace's plugins from the folder, so they have the new ones at their next session; a tool that keeps its own copy (Codex) shows **Update** on the Plugin marketplaces page, as for any marketplace. The marketplace's About tab says when the feed was last looked at and has **Check now**.
- A release that can't be read, downloaded whole or unpacked changes nothing: the plugins in use stay, About says why, and the app looks again in a quarter of an hour. A release that names a newer app than this one waits until the app is that new.
- A plugin a release no longer offers stays, files and entry, while a tool on this Mac has it installed: its row says **No longer offered**, its page says it stays in the tools that have it, and it can be turned off (kept installed; uninstalled for Copilot CLI's live copy) but not installed anywhere else. (Without that, Claude Code stops loading an installed plugin the moment its marketplace no longer lists it.) The first release after it is uninstalled leaves it out.
- A later build that carries a newer release of the marketplace replaces the unpacked one at its first open, keeping such plugins the same way. An older one never does. A release that can't be unpacked leaves the last working one in place, and the log says why.

Not there yet: a custom build's own updates (it says so in Settings).

## State

Central Knot's state lives in one folder, `.central-knot/` inside the selected home: `sync.json` (the build that made it or last took it over, the tools whose Manage switch is off, and Synchronize everything), `skills.json`, `mcp.json`, `agents.json`, kept contents under `items/`, History (`history.json`), profiles (`profiles.json`), base instructions (`instructions/`), `sources.json` with each source's last read under `sources/`, Claude Code's skill overrides as they were before a switch was set (`skill-overrides.json`), Claude Code's MCP denies the move of profiles kept (`claude-denies.json`), plugins (`plugins.json`), plugin parts an earlier version wrote (`plugin-parts.json`, kept aside as `plugin-parts.v1.json` once they are moved to the library, and `plugin-parts-runs/`, no longer read), the Git repo's clone and state (`repo/`, `repo.json`), kept session costs once turned on for that home (`sessions/`), and `staging/`, where a skill's copy waits to be put in place when the folder beside its tool's skills folder can't be written. Central Knot is the truth for skills, MCP servers and agents: `skills.json`, `mcp.json` and `agents.json` hold each item (On or Off, its current version, its versions, the tools it is kept out of, what was applied where, and for a skill from a source, which one and what it last had); `items/skills/<name>/versions/<hash>/` holds each version of a skill's whole folder, `items/agents/<name>/versions/` each version of an agent's name, description and prompt, and `items/agents/<name>/own/` each tool's whole agent file as Central Knot last saw or wrote it; `items/mcp/<name>/versions/` each version of a server, and `items/mcp/<name>/own/` each tool's own part of its entry. A deleted skill's versions go once its deletion is older than History's days. A home last used by a version from before this model is migrated the first time it is opened: no tool's folder or file changes (but an MCP settings file missing at the earlier version's last look, which gets its servers afresh, and what the move of profiles clears and turns Off: see Profiles), and the earlier record stays beside the new one (`sync.v1.json`, `mcp.v1.json`, `agents.v2.json`, `profiles.v1.json`). A damaged, missing, newer or replaced record stops writes and deletes nothing. A kind's own record (`skills.json`, `mcp.json`, `agents.json`) that is damaged, can't be read or was written by a newer Central Knot stops that kind's writes alone: its rows' switches and Add are off, and so are the controls of its opened rows (each tool's switch, Use a copy, Delete, Make current, a skill's Let it load and Take over), while History offers no action on its entries, since its record can't be read; a plugin's own rows, which turn the plugin's switches, are aside, and the other kinds still work. App settings (home, appearance, history length, whether session costs are kept per home, and for each home the tools a sync last saw managed and the Overview's lines for the tools that came under management) and the log are in the normal Electron app data folder (`~/Library/Application Support/central-knot/` on a Mac; Central Knot Alpha's in `com.centralknot.alpha/` beside it). A settings file there that can't be read (`app-settings.json`) is kept beside it as `app-settings.unreadable-<time>.json`, as unreadable History is (`history.unreadable-<time>.json`); every setting starts at its default, the Overview and Settings say so this launch, until closed on Settings, and this computer's home, opened in place of the one the file may have named, waits for Resume: its sync passes and take-in, and plugin work of Central Knot's own accord, start only after a Resume there. A file that couldn't be moved stays in place, and no settings change is saved until it can be.

## For developers

Node 24.9 or newer.

```sh
npm ci
npm start            # dev build, opens the Practice copy
npm test             # TypeScript check and unit tests (tests/*.test.ts)
```

- **Where things are:** `MAP.md`, at the repository's root: every source file and script by area, where to start reading, the paths that cross areas and where the recipes for common changes are (`tests/map.test.ts` keeps it true). `LEDGER.md` is history up to 2026-11-13, frozen: how the code works now is in `MAP.md` and each module's header; a change's story is in its pull request.
- **End to end:** `npm run e2e` (`scripts/e2e.mjs`) drives the app over its debug port in a throwaway HOME, with a stand-in for `/Applications`, the running apps and the Trash (`CK_TEST_APPS`, `tests/macstandins.ts`): no test or tour looks at or removes the real ones, and with it a development run looks for another build too. Off a Mac only the flows about another build name one, so every other flow runs as a Linux user's app does, which never looks. `--electron` runs the dev build instead of the packaged app; on Linux add `--no-sandbox` and run it under `xvfb-run`. A run starts the script once per group of flows (`groups` in it), each copy with a throwaway home of its own, `CK_E2E_GROUPS_AT_ONCE` copies at a time (1 unless set; the Mac run sets 4); each group's output prints when it ends, then the total and every failure again, each named with its flow. A copy that dies (no total line, or an exit its total doesn't explain), or whose total counts more failures than its `FAIL` lines, is one failure more; the passes of one with no total line are left out of the total, which says so. `--flows openCodeFlow,…` runs only the named flows, in this one process with no copies, while working on one; `--group <n>/<total>` runs group `n` of `groups` as one supervised copy through `runGroups` (refusing when `total` is not `groups.length`).
- **UI tour:** `node scripts/ui-tour.mjs <outDir> [--electron]` is the light tour: the app opens on the Practice copy and each page is opened once, one picture each, in a few seconds. `--only shell,skills,…` takes the pictures of the named features; `--full` takes every feature at 860×560 up to 2560×1440, dark and light (about ten minutes, for a new release).
- **Harness tests:** `npm run test:harness` installs, updates and uninstalls a marker plugin with the real `claude`, `copilot` and `codex` CLIs in disposable homes (a missing one is skipped), checks that a plugin turned off stays off through an update and that one its marketplace dropped keeps its copy, and takes a bundled build's marketplace through being packed, unpacked, added to each tool's own list, installed and uninstalled. `CK_HARNESS_APPS=1` runs the same tests through the copy each desktop app carries.
- **Smoke:** `npm run smoke:mac` opens a hidden window on fixture data only; on Linux, the AppImage with `--smoke-test` does the same.
- **CI:** `.github/workflows/mac.yml` runs `scripts/mac-run.mjs`, in two phases: first the unit tests, and beside them the packaging, then the light tour (its pictures are the run's `light-tour` download), the bundled check and the alpha check; then the end-to-end checks against the packaged app, by themselves. Each part's output prints when it ends, then each part's result and time, and for a part that failed the line in its output that says what failed, when there is one; how a run waits for room on the Mac and cleans up after itself is in `AGENTS.md`. It runs on every push to `next`, unless a green run of the workflow has already tested that tree, and on any pushed branch with `gh workflow run mac.yml --ref <branch>`. `.github/workflows/mac-hosted.yml` runs the same script on one of GitHub's own Macs, a fresh machine each run, by hand with `gh workflow run mac-hosted.yml --ref <branch>`; it is not yet the run that counts. `.github/workflows/linux.yml` runs on GitHub's Ubuntu against the AppImage in jobs side by side (`npm test`, and four end-to-end jobs each packaging its AppImage and running one group of `scripts/e2e.mjs` with `--group <n>/<total>`, with one leg also running the smoke test and the light tour, followed by a `linux` job green only if all passed), on pushes to `next`, `ci/**` branches, and `workflow_dispatch`, for the Linux plan's steps; it is no required check for a Mac change.

### Packaging and release

`npm run package:mac` (`scripts/package-mac.mjs`) builds the app on an Apple silicon Mac and puts it in two downloads under `release/`: `Central-Knot-<version>-mac-arm64.dmg`, a disk image whose window shows the app beside a shortcut to Applications, and `Central-Knot-<version>-mac-arm64.zip`. It signs with the Mac's Developer ID Application certificate and notarizes through the `central-knot-notary` keychain profile when both are there; otherwise, or with `CK_SIGN=0`, it signs ad hoc. The disk image is signed, notarized and stapled the same way, in its own right. `npm run package:mac:release` never falls back to ad hoc. The version comes from `package.json`. The release tag is recorded in the app (`build-info.json`) from the highest version tag on the commit being built (`v0.5.0-preview.5`), or `CK_RELEASE_TAG`; a release build refuses to package without one, and an untagged build never offers updates. Each release must carry both downloads: the disk image is for people, and the zip, named `Central-Knot-<version>-mac-arm64.zip`, is what the app's own updater downloads. `node scripts/update-proof.mjs` proves an update between two signed test builds of one line in throwaway folders (instructions at its top).

`npm run package:linux` (`scripts/package-linux.mjs`) builds the Linux app on an x86_64 Linux machine with `mksquashfs` (squashfs-tools) and FUSE: `release/Central-Knot-<version>-linux-x86_64.AppImage`, from the same version, release tag and line as the Mac package (`scripts/package-app.mjs`, so an alpha tag makes `Central-Knot-Alpha-…`). It is the packaged app with a start script, a launcher file and the icon, squashed onto the AppImage project's static runtime, whose release and SHA-256 are pinned at the top of the script (with how to move to a newer one). It is not signed, nothing uploads it, and a custom build is refused there for now.

**An alpha is cut the same way, from its tag.** The release line is the tag's (`src/updates.ts releaseLine`), named by its pre-release part exactly: `v0.6.0-alpha.1` is an alpha, `v0.5.0-preview.9` a preview, no pre-release part a final. Packaging stops, saying so, at any other pre-release part (`v0.6.0-alpha1`, `v0.6.0-Alpha.1`, `v1.0.0-rc.1`): built, it would be the standard app and offered to every installed preview. Tag the commit `v<version>-alpha.<n>` (or set `CK_RELEASE_TAG`), with `package.json`'s version the tag's (`0.6.0` for `v0.6.0-alpha.1`), and run the same `npm run package:mac:release`. An alpha tag makes the app "Central Knot Alpha" (`src/updates.ts lineApp`): its name wherever the app shows it (the window, the menu bar icon's menu, About, the Dock), its own bundle id `com.centralknot.alpha`, and its own downloads, `Central-Knot-Alpha-<version>-mac-arm64.dmg` (its disk image says "Central Knot Alpha" too) and `Central-Knot-Alpha-<version>-mac-arm64.zip`. Its version reads "0.6.0 alpha 1". An alpha's release carries those two files and nothing else: installed previews up to preview 9 tell an alpha release apart only by its zip's name, so a `Central-Knot-<version>-mac-arm64.zip` on it would be offered to them. Packaging the standard app or an alpha first removes every other Mac download from `release/` (another line's, an earlier version's, a custom build's), names what it removed, and ends with "Upload exactly these:" and its two files. Publish them as a pre-release. `node scripts/alpha-check.mjs` packages an alpha from a test tag beside the standard app and opens the two on one throwaway home (the Mac run does this).

The disk image is made by `scripts/mac-dmg.mjs`. Each app's window is its own folder, `assets/dmg/Central-Knot/` and `assets/dmg/Central-Knot-Alpha/`: the picture, `background.svg` (it names the app), kept as PNGs at both sizes, and the window's size and icon places in `DS_Store`, which `scripts/mac-dmg-layout.sh "<app name>"` makes again on a Mac after a layout change. Releases are published on GitHub with their checks in the release notes.

**Model rates table.** `assets/model-rates.json` holds the dated per-million-token API rates for session cost estimates, built from Pydantic's `genai-prices` public list (`prices/new_data/v2/data_slim.json`, MIT licence) with its licence notice and source revision; the table's `date` is the date that revision's data file was last changed in Git (with `built` recording when the file was generated). Refresh it by hand before cutting a release and commit the updated file:

```sh
node scripts/build-rates.ts
```

That script is the only place that touches the network for rates (fetching the public list's `main` commit hash, the data file's last-changed commit date, `prices/new_data/v2/data_slim.json` and `LICENSE`, sending nothing about this project or computer). Packaging and the app read the checked-in `assets/model-rates.json` offline.

### Building a custom build

The same packaging command takes optional inputs. With none it builds the standard app; with any, a custom build, which must be given its name (`--app-name`):

```sh
npm run package:mac -- --marketplace acme/plugins --app-name "Acme Knot" \
  --app-icon acme.png --marketplace-name "Acme plugins" --marketplace-logo acme-plugins.svg
```

| Input | What it sets |
|---|---|
| `--marketplace <owner/repo, Git URL or folder>` | The marketplace to carry. A Git source is fetched with this computer's own Git sign-in; a folder is carried as it is on disk, uncommitted changes included. Every plugin's files are packed, including plugins the marketplace keeps in other Git repositories. |
| `--app-name "<name>"` | The app's name, everywhere the app says it. Required, and never "Central Knot": under its own name the app sits beside the standard one in Applications, where a second "Central Knot" would take the standard app's place. |
| `--app-id <id>` | Its identity: its bundle id is `com.centralknot.custom.<id>`, which also names its settings folder. Made from the app's name when left out ("Acme Knot" is `acme-knot`). |
| `--app-icon <file.png or file.icns>` | The app's icon (a 1024 by 1024 .png, or a Mac .icns), also shown in the sidebar. |
| `--marketplace-name "<name>"` | The marketplace's name in the app. The tools still know it by the name in its `marketplace.json`. |
| `--marketplace-logo <file.png, .svg or .jpg>` | Its picture in the app. |
| `--feed <http or https address>` | Where newer releases of the marketplace will be published: the address of a folder (below). Needs `--marketplace`, the release the build starts with. Without it the marketplace changes only with a new build. |
| `--sequence <number>` | The release's place in the order of releases. Left out, it is the time of the build (seconds since 1970, about 1.8 billion now), so a later build is a later release. A number given by hand must be higher than every earlier build's, that default included: an installed copy keeps the content it has when the build it opens carries a lower number, and its log says so. |

The result is `release/<Name>-darwin-arm64/<Name>.app`, its zip `release/<Name>-<version>-mac-arm64.zip`, and `release/<Name>-build-report.txt`. The report lists the identity, the marketplace release (what it was made from, with the commit when there is one), each plugin packed, each plugin that could **not** be packed with the reason, a note when one entry makes Copilot CLI refuse the whole marketplace (an npm, pip or archive plugin does), the feed's address or that there is none, and that the build has no update location. A plugin that can't be packed doesn't stop the build. A missing `--app-name`, marketplace branding without `--marketplace`, or an input that can't be read stops it before anything is fetched. Signing is as for the standard app: your own Developer ID when one is in the keychain, otherwise (or with `CK_SIGN=0`) ad hoc. A custom build has no disk image yet.

What is packed is the marketplace as it is, without the fetch's own `.git` folders. A plugin kept in another repository is copied into `_bundled/<plugin>/` and its entry in `marketplace.json` pointed there; that file is then written again as JSON with every other value as it was, and a marketplace with no such plugin is carried byte for byte. What Central Knot writes outside the app (the markers around base instructions in a tool's file, a Git repo commit's author and message) says "Central Knot" in every build, so a custom build and the standard app read each other's. Inside the app the release is two files, `dist/bundle/release.json` (the manifest: marketplace, sequence, date, source, plugins, the archive's size and SHA-256) and one `.tgz` archive (`src/bundle.ts`, `src/bundlepack.ts`).

### Publishing newer plugins to a feed

A feed is a folder served over http or https that holds two files: `release.json` (the manifest) and the archive it names. Any static web server, bucket or file share behind a web address does; the app signs in to nothing, so who can reach the address is for whoever hosts it. To publish a new release of the marketplace:

```sh
node scripts/publish-bundle.mjs --marketplace acme/plugins --out ./feed
```

It packs the marketplace exactly as the build does and writes the archive, then `release.json`, into `--out`. Serve that folder at the build's `--feed` address; when copying it to a server, copy the archive before `release.json`. The earlier archive is no longer needed. `--sequence <number>` sets the release's place in the order (default: the time it is made) and `--min-app <version>` the oldest app that can use it.

- Nothing is published, and the command exits 1, when the marketplace can't be read, when a plugin's files couldn't be fetched this time (try again: a release never loses a plugin to a network hiccup), when the sequence isn't higher than the one already in `--out`, or when `--out` holds another marketplace's releases.
- A plugin that can never be packed (an npm or pip package) doesn't stop it: it is left out and named in what the command prints, and copies of it that people have installed stay as they are.
- What it prints also names each plugin the release no longer lists.

- **Try one without packaging:** `node scripts/custom-build.mjs <inputs> --out build/custom` stages the build on any system, then `CK_CUSTOM_BUILD=build/custom npm start` runs it. A plain `npm run build` makes `dist/` the standard app again.
- **Check:** `node scripts/bundled-check.mjs` builds a bundled build from the fixture marketplace with the documented command, deletes the marketplace, opens the packaged app in a throwaway home and checks its name, its own settings folder, the marketplace added to each tool's own list (stand-ins for the tools' CLIs record what they were asked), the Plugin marketplaces page at four window sizes, Settings, and the feed: a release published to a folder served on this computer is taken, a plugin it no longer offers stays while a tool has it, and a broken publish changes nothing (`--electron` does the same as a development run; adding to the tools is checked where the home can be written, on macOS and Linux). The Mac run has it in its first phase, after the light tour (`scripts/mac-run.mjs`).

### Logo

The logo files are in `assets/`: `logo.svg` (the sidebar mark, copied into `dist/` by `scripts/build.mjs`), `icon.icns` (the Mac app icon, used by `scripts/package-mac.mjs`), `icon.png` (the window and tray icon on Windows and Linux) and `icon.svg` (the app icon drawing). A custom build takes its app icon and sidebar mark from `--app-icon` (above). The Mac's menu bar icon is the same logo in one colour: its drawing is `assets/tray.svg`, and the 32-pixel PNG made from it is kept as text in `src/trayicon.ts`; a custom build keeps the standard menu bar icon for now.

The product boundary is in `AGENTS.md`. `docs/SPEC.md` is the requirements as written before the library, history now and not kept true. The per-tool evidence is in `docs/capability-data.md`. `LEDGER.md` records what was run and every check round up to 2026-11-13 (frozen history; a change since has its story in its pull request).
