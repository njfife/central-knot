# Central Knot

Central Knot is a desktop app that shows the skills, MCP servers, agents, instructions and plugins each AI coding tool on your computer has, and keeps the ones you choose the same across those tools. It works with Claude Code, GitHub Copilot CLI, Codex, Pi and OpenCode, through their CLIs or their desktop apps (Claude desktop, the GitHub Copilot app, ChatGPT desktop, OpenCode desktop), and it only reads and writes each tool's own user-wide files.

## Getting it

Download the Mac disk image (Apple silicon), `Central-Knot-<version>-mac-arm64.dmg`, from the [GitHub releases](https://github.com/njfife/central-knot/releases). Open it, drag **Central Knot** onto the **Applications** folder beside it, then open Central Knot from Applications. It is signed with a Developer ID and notarized. Each release also has the same app as a zip.

A released build opens on **This Mac's home**: your real tools. Nothing is changed until you choose it. The sidebar's **Home** list also has **Another folder…**, for a backup or another account's home; Central Knot writes only inside that folder, and one that is or links into your real tool folders is read-only. The **Practice copy** (sample data in a throwaway folder, removed at Quit) is only in development builds: run `npm start` from the source to try things on sample files first.

Real-home writes happen only on macOS. If something looks wrong, Settings → **Show log file** opens Central Knot's own log: each plugin change with what it came to and why, and each item a change couldn't reach.

## The pages

### Overview

One card each for skills, MCP servers and agents, with counts and anything that needs a choice. A card opens its page. Where another build of Central Knot is on this Mac (Central Knot Alpha beside Central Knot, say) and doesn't sync this home, a band says where it is and what removing it does, with **Remove** and **Keep both** (see Updates); Keep both hides the band, and Settings keeps its row.

### Harnesses

One card per tool found on this computer, with its skills, MCP servers, agents, instruction file, plugins and config folder. A tool counts as found when its CLI or its desktop app is there; when both are, their versions are shown separately. A settings folder with no CLI or app beside it (left behind by an uninstall, say) doesn't count, and a CLI is looked for wherever your terminal finds it, including folders that nvm, bun and the like add to your PATH. Each harness has its own page with tabs for Skills, MCP servers, Agents, Instructions, Plugins and About, and you can manage that tool's items there directly. Only the tools you have are shown anywhere in the app.

**Manage**, a switch on each installed tool's card, says whether Central Knot manages that tool at all. Every installed tool is managed until you turn its switch off, a tool installed later too (the status bar says so when one turns up while the app is open). Turned off, the tool is left out: Central Knot writes nothing there (no skill, MCP server, agent, plugin, plugin update or instruction file), its copies stay as they are, every item keeps its On or Off, and the tool shows on no other page but History; its card keeps its name, its switch and a line saying what turning it on would do. An item you turn off meanwhile stays in that tool until it is back. Turned on again, the next sync brings it into line, as a tool managed again (below): before the click its line counts what that sync will do there (Central Knot's version written there, the tool's differing copies kept as versions first, copies of items that are off removed, found items), or says nothing in that tool would change, and after it the band says what the sync did there and says it gets the plugins your other tools have; with Automatic sync off, Sync once brings it into line, and a click on an item brings that item. Each flip is one History entry with no Undo: the switch is the way back. A tool left out stays left out when it is uninstalled and installed again. In a home another build syncs, or that is preview only, the switches can't be turned, and the list says why. pi-gui, a third-party desktop app for Pi, counts as Pi's app. Under the cards, **Also on this Mac** names T3 Code and VS Code when they are installed: they are no tool of their own, but T3 Code starts your tools, and VS Code's built-in Copilot lists skills from their folders.

### Skills, MCP servers and Agents

Each of these pages lists one row per item, with one switch at its start (a found one has Add there instead). Every click applies at once; the strip at the top says what it did, with **Undo** where it has one, and an Undo leaves each tool's folder or file as it was before the click (a tool's own copy that the click wrote over is given back). **Marks** at the row's end say what each tool has (on, off, no copy, kept out, switched off in the tool's own settings, has it another way, can't take it, something waiting for sync, or through a plugin), each with a mark of its own and the legend in the lines' words; they are status only. The opened row (its chevron) has each tool's line, with its own controls.

**Skills, MCP servers and agents live in Central Knot.** Central Knot holds each skill (its whole folder), each MCP server and each agent itself, with its versions; a tool is somewhere it is applied.

- **Found**: one a tool has that Central Knot doesn't. It has **Add** where an item in Central Knot has its switch. Add takes it in, turns it on and puts it in every tool Central Knot manages that can take it (its row names those that can't, or have it another way). Its Undo takes it out again: the copies it made go, each tool it was found in keeps its own, and it is found again. Where the tools' copies differ, Add asks which one to take in, quoting each (a skill's first line of text; **Read both copies** opens a skill's files); the others are kept as versions. With **Synchronize everything** off (as it is until you choose it), nothing else takes a found item in.
- **Synchronize everything** (Settings › This home): a skill, MCP server or agent that turns up in a managed tool is taken in and turned on everywhere by itself, as Add would, at the next sync (with Automatic sync off, at Sync once); an MCP server reaches Claude Code when you click Write to Claude Code. Turning it on takes in everything found then. Each one gets Add's History entry, saying Synchronize everything took it in and from which tool, with Add's Undo, except an MCP server found in Claude Code: its entry says why it has none and what to do instead. One notice per sync, on its page and in Settings, says how many and where they were found. It leaves found, each opened row saying why: copies that differ (the row asks which, and Settings and the Found heading count them), an item deleted from Central Knot or whose take-in was undone (it is not added by itself again; Add, or Restore in History, brings it back), a plugin's part, a skill Convert to skill made, an item every tool that has it has switched off in its own settings, and a copy that can't be read. An item that is Off, or kept out of a tool, whose copy turns up is not found at all. A copy a tool has another way is taken in from where it is; that place is not written (Take over stays a click).
- **On**: every managed tool has the current version, kept the same both ways: an edit made in any tool becomes the current version and reaches the others. When two tools were edited, the latest edit wins (by the folder's or file's time; an MCP entry has no time of its own, so the first tool's, in the order the page lists them) and the other is kept as a version. A skill's whole folder is the same everywhere: every file as it is, its scripts still runnable, and empty folders (not a nested `.git` or `.DS_Store`). An agent's name, description and prompt are the same everywhere; each tool's other settings (Claude Code's `tools` and `model`, Codex's keys and tables, comments) stay in that tool's own file.
- **Off**: it leaves every tool. It stays in Central Knot, with a row under Off, and turning it on writes each tool's folder or file back exactly as it was (an MCP server's entry: the same values, name, place and own fields; see below). A copy deleted by hand in a tool turns it Off everywhere; Central Knot keeps it, so **Turn on** puts it back. A copy that can't be read, a half-finished save, a tool uninstalled, or a folder that was moved, made again or removed is never taken for a deletion: a removed folder is written again after a short settle.
- **One tool's switch**, in the opened row, keeps it out of that tool alone; the row then says "in 2 of 3 tools · kept out of Codex" and its switch is drawn partial. A tool that can't take it (a name or shape it won't load, a folder that can't be written) says why on its line; one that won't load an edit made elsewhere keeps the copy it has, and says why the same way.
- **Versions**, in the opened row: every version, the current one first, each with when it was made, where it came from and what changed. **Read** shows one, marking what differs from the current version; **Make current** puts an earlier one in every tool it is on in. Central Knot keeps every version while the item is in Central Knot.
- **Delete from Central Knot…** takes it out of every tool and off the page. History keeps it, with its versions, for History's days (Settings), and **Restore** there puts it back as it was.
- **A tool managed again** (its Manage switch turned on again, or uninstalled and back): Central Knot's version wins there. A copy changed in that tool meanwhile is kept as a version first; a copy of an item turned off meanwhile is removed; a copy deleted there is written again. Nothing turns Off because a tool was away. A tool managed for the first time that has its own copy of an item that is on gets the current version, its own copy kept as a version first. History says each of these.

Skills only:
- **Has it another way**: a tool that has a skill without a copy of Central Knot's in its own folder gets none: a plugin brings it, a link in its skills folder leads to a copy, it reads a copy in `~/.agents/skills` (Copilot CLI, Codex, Pi and OpenCode do), or it reads another managed tool's folder (OpenCode reads Claude Code's, while the skill is really there). Its line says which. Central Knot never writes through a link or into a folder that isn't its own; a copy it put there that is one too many is removed, and one it didn't put is left alone (the line says the tool has it both ways). **Take over…**, on that line, makes Central Knot's copy the tool's: a link is replaced at once (what it led to stays); a copy in `~/.agents/skills` is removed once confirmed (its armed line says which folder goes and which tools get Central Knot's copy), kept as a version first, and each tool that read it gets Central Knot's copy, switched off where the tool had switched off the copy it read. Take over has no Undo, and says so. A copy in `~/.agents/skills` edited after the skill was taken in is said on the lines of the tools that read it.
- **A tool's own switch** for a skill (Claude Code `skillOverrides`, Copilot `disabledSkills`, Codex `[[skills.config]]` by path, Pi's `settings.json` filter, OpenCode a `deny` rule for the skill's name) is read at every look and never undone: the folder stays, the tool doesn't load it, the tool is not counted as on: its mark is its own, the row says "switched off in Codex" with a partial switch, and that tool's line says "Switched off". **Let Codex load it**, on that line, clears the switch; its Undo sets it again.

MCP servers only:
- A server's **version** is what it runs (its command, arguments, environment and working folder, or its URL and headers), the same in every tool; the rest of its entry stays that tool's own: its other fields (Copilot's `tools`, Codex's timeouts and tables, `enabled`), its name as that tool spells it, where OpenCode keeps it (`mcp` or `mcp.servers`), and the comment lines of a Codex table. That comes back with the entry after Off and On, which puts it after the file's other servers; a comment at the end of a shared value's line (`command = "npx" # pinned`) is not kept. A change to the tool's own part alone is no edit.
- Each tool's user-wide file: Claude Code `~/.claude.json`, Copilot `mcp-config.json`, Codex `config.toml`, Pi `mcp.json`, OpenCode `opencode.json` (or `opencode.jsonc` when there is one). Writes edit only that server's entry; the rest of the file stays byte for byte. OpenCode's servers are read from both places its settings keep them (`mcp` and `mcp.servers`); an entry is changed where it is, and a new one goes under `mcp`.
- **Claude Code's file is written only by Write to Claude Code**, which waits while Claude Code, Claude desktop or its Code tab is open. Until then a row whose entry there is behind, still to be added or still to be removed says so on its mark and Claude Code's line, and one band above the table offers the write for all of them (with Automatic sync off too). Its way back is Make current an earlier version, then Write again.
- **Left alone, said why on its line, never taken in**: a server that belongs to an app (ChatGPT desktop's own), an entry in a form Central Knot doesn't edit (Codex servers written inline or with dotted keys, an OpenCode name in both places), two names in one file that differ only by case, and an entry Central Knot put in as a plugin's part (it is the plugin's). A tool that can't hold a server (SSE in Codex, Pi and OpenCode) says so. A settings file that can't be read leaves that tool alone; a missing one is written afresh after a short settle; one that reads and no longer has an entry (`codex mcp remove`, or a tool rewriting its file) is a deletion by hand: the server turns Off everywhere, and **Turn on** puts it back.
- **A tool's own switch** for a server (Claude Code `deniedMcpServers` and Copilot `disabledMcpServers` in their `settings.json`, `enabled = false` in a Codex table, `"enabled": false` in a Pi or OpenCode entry, `"disabled": true` in one under OpenCode's `mcp.servers`) is read and left as it is: its mark and line say it. Where it lives inside the entry (Codex, Pi, OpenCode) it is that tool's own field, so it comes back with the entry after Off and On; Claude Code's and Copilot's stay in their settings either way.

Agents: Claude Code `~/.claude/agents`, Copilot `~/.copilot/agents`, Codex `~/.codex/agents`, OpenCode `~/.config/opencode/agents`. An agent new to OpenCode is written with `mode: all`, so both of OpenCode's lines offer it to choose and to hand work to. Pi has no agents; **Convert to skill** writes one as a Pi skill, once.

Skills: each tool's own skills folder. OpenCode 1.x leaves out a skill with no `name` in its frontmatter, so such a skill is marked as one OpenCode can't load. A skill whose folder can't be copied as it is (a link inside, a file Central Knot can't read) is a row that says why, and can't be taken in until it can. Skills synced by an earlier version are moved into Central Knot the first time this one opens the home: a synced skill is On with the same content, a tool left out is kept out, and one never synced, or kept different on purpose, is found (every folder untouched); `sync.json` as it was is kept beside it as `sync.v1.json`.

### Two-way sync

- **Automatic sync** (status bar switch, on by default): an item edited in one tool spreads to the others within seconds. A deletion is acted on after a 2 s settle. Competing edits: the latest edit wins, by the folders' or files' times (MCP entries, which have none: the first tool's, in the page's order), and the other is kept as a version. Each outcome shows a notice with Undo or Turn on.
- With Automatic sync off, edits and deletions are noted as waiting, and **Sync once** spreads them once.
- A folder or file that can't be read or is half-written is held, never read as a deletion; a folder made again is written afresh. An MCP settings file that reads without a server's entry is that entry deleted by hand (see MCP servers). Every write checks the file first and never overwrites a save made meanwhile.
- Closing the window keeps Central Knot syncing, and updating plugins (see Plugins). On a Mac it then leaves the Dock and runs from its menu bar icon alone, until the window is opened again. The menu bar icon has Open, Settings, the profile, Automatic sync, Sync once (while Automatic sync is off), Start at sign-in and Quit.

### Instructions

Opens each tool's own instruction file to read and edit in place, with **Undo save**. OpenCode's card says when OpenCode 1.x is reading Claude Code's `CLAUDE.md` because it has no `AGENTS.md` yet.

**Base instructions**: you write a base once and choose which tools get it. It is added after each tool's own instructions as one marked block; the tool's own text is never rewritten. Every write is reviewed first (**Review changes**), a copy edited outside the app is found, and each save can be undone. A typed draft is not lost when you switch homes: the app asks first.

**Draft with a tool**: instead of writing the base yourself, have one of your tools write a first draft from the instruction files you already have. Choose the tool (any with a CLI on this computer, except OpenCode); it runs once and sorts your files into a base for every tool and what stays only in each tool's file. You see the draft, including any line it did not carry over as written, and can change it; one **Save** then sets the base and updates every file, with **Undo**. Nothing is saved before that.

### Plugins

- **Marketplaces**: add one by Git URL, `owner/repo` or folder. A Git address is checked (`git ls-remote`) before it is added. Claude-format and Codex marketplaces (including `.agents/plugins/marketplace.json`) are read.
- **Suggested**: a marketplace from the maker of each plugin tool you have is offered under the list, with **Add**: Anthropic's `claude-plugins-official` for Claude Code and Codex, GitHub's `copilot-plugins` for Copilot CLI. One is offered only where its tool is installed and nothing lists it yet; nothing is fetched until you add it, adding installs nothing, and the × beside one stops it being offered (with Undo). A custom build that carries its own marketplace suggests none.
- Each plugin shows its parts (skills, MCP servers, agents and more), what each tool gets from them, its skill text, and each tool's installed version next to the marketplace's.
- **Install and uninstall** run through each tool's own plugin commands, and count only when that tool's own record shows the result. Nothing runs until **Apply all**.
- **Parts** for a tool that can't take the whole plugin (Pi and OpenCode always): the plugin's skills, MCP servers and agents go in as ordinary items. They are removed together, can be undone, and show **Update parts** when the plugin changes. Under **What it holds**, each part has a switch per such tool, so you can put in only the ones you want; a part turned off stays out when the parts are updated. Claude Code has no switch for one skill of a plugin, so with the plugin not installed there, the same switches put single skills into Claude Code as separate items.
- **One item, however a tool has it**: on Skills, MCP servers and Agents, a tool that has an item through the plugin itself is marked **Through a plugin** rather than "No copy", and sync never places a separate copy beside the plugin's. That tool's line in the opened row has the item's switch there (see **Switch one item of a plugin** below), with a link to the plugin's page. This applies to items Central Knot installed elsewhere as that plugin's parts and to skills whose SKILL.md is the same; another item that only shares the name stays an ordinary item.
- **What plugins bring, on the pages**: Skills, MCP servers and Agents also list every skill, server and agent an installed plugin brings, in a **From plugins** section, each marked with the plugin's icon and "from <plugin>". They are read from each tool's own records, so a plugin installed with the tool's own command counts too. They are never synced there; their row says where they are handled, and its switch and each tool's line turn the item on or off. A **From plugins** filter shows only these.
- **Switch one item of a plugin**: on Skills, MCP servers and Agents, the switch on a tool's line in the item's opened row turns that one item off or on in that tool, at once, with Undo; the row's own switch does it in every tool with such a switch, and never turns a whole plugin off. Each uses the tool's own switch, the plugin's files are never touched, and what you turn off stays off through plugin updates and sync:
  - a **skill** in Copilot CLI and Codex (also on the plugin's own page);
  - an **MCP server** in Claude Code, Copilot CLI and Codex;
  - an **agent** in Claude Code (Claude is no longer offered it; a session you start as that agent yourself still runs).
  - Where a tool has no switch for one item (a skill in Claude Code, an agent in Copilot CLI), that line's switch turns the **whole plugin** off or on in that tool instead, and says so before the click. After the row's switch, the result offers it beside Undo.
  - Turning on one item of a plugin that is off as a whole turns the plugin on with its other switchable items held off. Whatever of the plugin has no switch of its own in that tool comes on with it (its skills in Claude Code, say), and the tooltip names those first.
- **Update**: where a tool has an older version than the marketplace, the plugin box, list row and plugin page offer Update (**Update all** for a marketplace with two or more behind). Each tool refreshes its copy of the marketplace and updates through its own command. An update can't be undone, and the result says so. A plugin turned off in a tool is still off after its update.
- **Updates that arrive by themselves**: every four hours, with the window closed too, Central Knot reads your marketplaces again and makes the updates that Update all would offer, through each tool's own command. It only updates what a tool already has: a plugin turned off stays off, one you uninstalled from a tool is not put back, and parts in a tool that can't take the whole plugin are updated with the parts you turned off left out. A note on the Plugins page says which plugins were updated in which tools and what couldn't be; a failed update is tried again, less often each time, and the log has each step. It is on unless you turn off **Update plugins automatically** in Settings, and it pauses while Automatic sync is off. **Check now** in Settings runs a check at once.
- **A tool you install later**, or one whose Manage switch is turned on again: when a managed tool that plugins go into is first seen in a home, the plugins every other managed tool there has go into it too, once, at the next check (which comes soon after the tool is found): through its own command, or as parts where it takes parts. The note says so. It follows the same switch and pause as the updates. The tools already there when this first runs get nothing, nor does a tool installed while the switch or Automatic sync was off; a plugin turned off in one of your tools is not passed on; a plugin you then take out of the new tool stays out; an install that keeps failing (a tool not signed in yet) is tried three times, quietly, and its box on Plugins still installs it.
- **No longer offered**: a plugin its marketplace has dropped stays installed as it is, marked "No longer offered", until you uninstall it.
- **Cowork**: where Claude desktop is installed, Claude Code's card and each plugin's page say that Cowork uses the plugins in your Claude account, so Central Knot doesn't install there; plugins for Cowork are added in Claude desktop, under Customize › Plugins (as Claude documents; not tried here). (When this was tried on Claude desktop 5.1231.0, a plugin put into Cowork's folder on the computer was listed by Claude desktop, but the new Cowork session, which ran in the cloud, didn't load it: `docs/capability-data.md`, section 7.)
- **Desktop apps without a CLI**: Claude desktop (its Code tab), the GitHub Copilot app and ChatGPT desktop each carry their own copy of the tool. With no CLI installed, Central Knot runs the plugin commands through that copy, and the plugin box says which route it uses. A CLI is used when one is installed. If the app's copy isn't on disk yet (for example, the Code tab has never been opened), the plugin's parts are offered instead. macOS app locations only.

### Profiles

A profile is a named set of skills, MCP servers and agents to have on, such as *Incident* or *Development*. Switching to one, from the Profiles page, the status bar or the menu bar icon's **Profile** menu, turns what it has On and everything else in Central Knot Off: each item's own On and Off, so what goes Off leaves the tools and Central Knot keeps it, and a tool an item is kept out of stays so. An MCP server's change in Claude Code waits for Write to Claude Code, as always; the switch's result offers it.

- The Profiles page says what a switch will turn On and Off before it is clicked. Ticking only changes the profile.
- The profile in use is worked out, never stored: the one whose items are exactly the items that are On. It shows on the page, in the status bar and beside the menu bar icon, and follows by itself: turn something on or off by hand, take an item in, Pull one, or delete a copy by hand, and the name follows (No profile when none matches; both names when two profiles have the same items).
- An item a profile names that is not in Central Knot now (deleted, or only found in a tool) is skipped, and stays in the profile. A profile with nothing in it is not offered to switch to.
- A switch is one History row. **Undo switch** turns back each item still On or Off as the switch left it, each with a History row of its own; an item whose On or Off differs now stays as it is.
- Profiles are kept in `.central-knot/profiles.json`. One from before profiles were sets of items (0.6.0-alpha.1 and earlier) is moved the first time this version syncs the home, and kept beside it as `profiles.v1.json`: each tool switch the earlier profiles set is released, also where the item's copy is not there now, an item they held off in every tool that has it is turned Off (one History row says which, with Undo), every agent that is on joins every profile, and nothing else changes: an item that stays on is left to sync as ever. Claude Code's switch for a server that is Off then stays until the server is on there again, so it doesn't start before Write to Claude Code takes its entry out.

### History

Lists what Central Knot and sync did, with **Undo** or **Restore**. Every replaced or removed version is kept first in `.central-knot/`, as a version of its item. Undo says what it could not put back. A skill's, server's or agent's entries offer what would still change something: **Undo** makes the version from before an edit current again, **Turn on** or **Turn off** is its switch, **Restore** brings back a deleted agent. History keeps things for 30 days by default; Settings offers 7, 30 or 90.

### Git repo

Keeps the Managed set (skills, MCP servers, agents and base instructions) in a git repo on GitHub, GitLab or any git remote. Connect with a repo address and an optional branch; Central Knot uses this computer's own git sign-in. Nothing moves until you click **Pull** or **Push**. Pull brings the repo's changes into your tools through the normal sync, so each one is in History with Undo. For agents the repo and Central Knot exchange versions: Pull makes the repo's content the agent's current version, marked as pulled from the Git repo, and puts it in every tool where the agent is On (an agent Off here stays Off; one new here comes in On); Claude Code takes the repo's file as written, its own settings included. One removed in the repo is deleted from Central Knot, with Restore in History. Push sends every agent in Central Knot, On or Off, at its current version: only Delete from Central Knot takes one out of the repo. Skills and MCP servers go the same way (a server's file in the repo carries Claude Code's own fields for it; only servers in Central Knot are sent, not ones only found in a tool). Push makes one commit of the Managed set. The page lists what would come in and what would go out, and the sidebar shows the counts. The repo layout is `skills/<folder>/`, `mcp/<name>.json`, `agents/<name>.md` and `instructions/base.md`; other files in the repo are left alone.

### Settings

Start at sign-in, Appearance (System, Light or Dark), Updates, Synchronize everything for the open home (kept in the home's `.central-knot/sync.json`, off until chosen; while off, its row says how many found items it would add now), Other builds of Central Knot (a row for each found on this Mac, while it is there, with Remove or Quit: see Updates), Update plugins automatically (with Check now and what the last check came to), Keep history for (7, 30 or 90 days) and Show log file.

### Updates

The Mac app updates itself from this project's [GitHub releases](https://github.com/njfife/central-knot/releases). It asks GitHub's public API for the releases (one page: the 100 newest, previews and alphas together) shortly after it opens, every 15 minutes while it runs (window closed too), and when you come back to its window after five minutes or more; nothing about you is sent. The end of the sidebar, at the bottom left, always has the update control: **Check for updates** (circular arrows; a click checks now, and they spin while it checks). When there is a newer release it becomes a filled **Update available** button: one click downloads it, shows progress (a ring round the arrow), and restarts into it. If an instructions draft isn't saved or changes wait for Apply all, it waits: the control becomes an outlined **Restart to update…** with a warning mark, and a click opens Settings › Updates, which says what restarting would lose beside its own Restart button. A download that fails offers **Try the update again**. It never restarts during a write. In the folded sidebar the control is its icon alone, with its name as the tooltip. The status bar shows the version, and after an update it says once which version is now running, with its release notes.

A build made from a preview is offered newer previews and finals; one made from a final release, finals only. **Central Knot Alpha** is a line of its own, for trying work that is still moving: an alpha is a separate app, installed beside Central Knot with its own settings and log (`~/Library/Application Support/com.centralknot.alpha/`), and updates itself the same way, but only to newer alphas; a preview or final build is never offered an alpha. Opened on the same home, the two are two builds: one syncs it at a time, and each names the other ("Central Knot", "Central Knot Alpha") and offers **Take over syncing** (see Custom builds). The new app must be signed by the same developer before it replaces the old one (Electron's Squirrel.Mac checks this), and a failed or interrupted update leaves the installed app as it was. Settings › **Updates** shows the version and release tag in use, **Update**, **Check now** and the last result. An app outside the Applications folder (or `~/Applications`), an unsigned or untagged build and a development build don't update themselves; Settings says why and links the release page, and the sidebar's control opens it (a newer release such a copy can't install shows there as an outlined **Update available**; a build that never checks has a faint **Updates**). Windows and Linux have no releases yet, so nothing is shown there. **Check for Updates…** is in the app menu.

**One build on a Mac.** So that two builds don't sit side by side, one of them stopped, the app offers to remove the other: Central Knot Alpha offers to remove Central Knot, and Central Knot offers to remove the alpha; no other app is ever offered (a home a custom build syncs gets Take over syncing as before). It looks at each read of the home, and stores nothing: a bundle at the top of `~/Applications` or `/Applications` named Central Knot… whose `Info.plist` names one of those builds, and any copy of them that is running, by bundle id, wherever it runs from (Downloads, a translocated copy, the Trash). It looks only in the installed app on a Mac. Where the other build syncs the open home, **Take over syncing** is two choices, on the item pages, the Overview and its Settings row: **Take over and remove** it, or **Take over, keep both** (it stays installed, stopped there). Where it doesn't, the Overview has a band and Settings a row, with **Remove**, or **Quit** for a build that only runs from somewhere else. Before the click the words name the bundle that goes, the copies that stay and what else stays. Nothing happens by itself. Remove refuses anything but another build's bundle in an Applications folder (checked at the look, at the click and again just before the Trash; never this app itself), asks every running copy of it to quit (a signal to stop, so macOS asks nothing) and waits a few seconds: one still running (it may be asking about unsaved work), or one whose state macOS can't say, leaves it where it is, and the words say so. Then the bundle goes to the Trash, where it stays until the Trash is emptied; where macOS refuses that, nothing else is tried, and **Show in Finder** is offered. A take-over that is part of the click comes first and is said first; one refused removes nothing, and a remove that fails after it leaves the take-over done. What stays: the skills, MCP servers and agents, Central Knot's record of them and History (they live in the home) and the other build's own settings folder. Each build adds itself to start at sign-in at its first open and can't turn another's entry off: if a removed build still starts at sign-in, turn it off in System Settings › General › Login Items (started from the Trash, it is found running and offered Quit).

## Custom builds

A custom build is Central Knot made by someone for their own group, under its own name. It installs beside the standard app and keeps its own settings (`~/Library/Application Support/com.centralknot.custom.<its id>/` on a Mac), so the two never share or overwrite each other's settings, and it never takes the standard app's updates. Settings › **This build** says what it is.

A **bundled build** also carries a marketplace, with every plugin's files inside the app. Whoever opens it needs no access to where the marketplace came from:

- **Plugins** lists that marketplace first, marked **Built in**, under the name and picture the build gave it. Its About tab says which release of the marketplace this is. It can't be removed from the list.
- At the first open the build unpacks the marketplace into its own data folder (`bundled/marketplace` there). That folder is an ordinary folder marketplace from then on: its plugins are browsed, installed, updated and uninstalled the same way as any other's.
- A plugin the marketplace lists but the build could not pack (an npm package, say, or a repository that could not be fetched) is still listed, says that it can't be installed from this app and why (About has the reason, and who to ask).
- **In your tools' own plugin lists.** The first time it opens this Mac's home, the build adds its marketplace to the own plugin list of each tool found here that takes plugins (Claude Code, Copilot CLI, Codex), with that tool's own command, so the plugins also show there. It installs nothing, and the status bar says so and which tools. This is the one thing a bundled build changes without being asked. Each tool is given it once: take it out in a tool and it stays out, until **List in …** on the marketplace's About tab puts it back. A tool installed later gets it the next time the home is read. A tool that already has a different marketplace under the same name is left alone, and so is a folder opened as a home. The About tab says which tools list it, and that the app added it.
- **Newer plugins without a new app.** A build made with a feed (`--feed`) looks at that address shortly after it opens and every few hours while it runs, window closed too. When a newer release of the marketplace is published there, the app downloads it, checks it against its manifest and puts it in use, and the status bar says so. Claude Code and Copilot CLI load a folder marketplace's plugins from the folder, so they have the new ones at their next session; a tool that keeps its own copy (Codex) shows **Update** on the Plugins page, as for any marketplace. The marketplace's About tab says when the feed was last looked at and has **Check now**.
- A release that can't be read, downloaded whole or unpacked changes nothing: the plugins in use stay, About says why, and the app looks again in a quarter of an hour. A release that names a newer app than this one waits until the app is that new.
- A plugin a release no longer offers stays, files and entry, while a tool on this Mac has it installed: its row says **No longer offered**, its page says it stays in the tools that have it, and it can be uninstalled but not installed anywhere else. (Without that, Claude Code stops loading an installed plugin the moment its marketplace no longer lists it.) The first release after it is uninstalled leaves it out.
- A later build that carries a newer release of the marketplace replaces the unpacked one at its first open, keeping such plugins the same way. An older one never does. A release that can't be unpacked leaves the last working one in place, and the log says why.

**One build syncs a home at a time.** A custom build and the standard app can both be on one Mac and open one home, but skills, MCP servers and agents are kept in sync by one of them: the one that managed something there first, until another is told to take over. The other one names it on Overview, Skills, MCP servers and Agents (and whether it is open now), changes nothing there, and offers **Take over syncing**. Taking over starts nothing again: the record of what is managed, every choice and History live in the home (`.central-knot/`), so the new owner carries on from exactly where the other left it, and the other stops at its next look and offers the same button. Syncing never changes hands by itself. Where that other build is installed on this Mac, the button is two choices: take over and remove it, or take over and keep both (see Updates). Plugins are each build's own business either way: both install, update and list their marketplaces as before, and an instruction file can still be saved from either.

Not there yet: a custom build's own updates (it says so in Settings).

## State

Central Knot's state lives in one folder, `.central-knot/` inside the selected home: `sync.json` (who syncs this home, and the tools whose Manage switch is off), `skills.json`, `mcp.json`, `agents.json`, kept contents under `items/`, History, profiles and base instructions. Central Knot is the truth for skills, MCP servers and agents: `skills.json`, `mcp.json` and `agents.json` hold each item (On or Off, its current version, its versions, the tools it is kept out of and what was applied where); `items/skills/<name>/versions/<hash>/` holds each version of a skill's whole folder, `items/agents/<name>/versions/` each version of an agent's name, description and prompt, and `items/agents/<name>/own/` each tool's whole agent file as Central Knot last saw or wrote it; `items/mcp/<name>/versions/` each version of a server, and `items/mcp/<name>/own/` each tool's own part of its entry. A deleted skill's versions go once its deletion is older than History's days. A home last used by a version from before this model is migrated the first time it is opened: no tool's folder or file changes (but an MCP settings file missing at the earlier version's last look, which gets its servers afresh, and what the move of profiles clears and turns Off: see Profiles), and the earlier record stays beside the new one (`sync.v1.json`, `mcp.v1.json`, `agents.v2.json`, `profiles.v1.json`). A damaged, missing, newer, replaced or differently owned record stops writes and deletes nothing. App settings (home, appearance, history length) and the log are in the normal Electron app data folder (`~/Library/Application Support/central-knot/` on a Mac; Central Knot Alpha's in `com.centralknot.alpha/` beside it).

## Not here yet

## For developers

Node 24.9 or newer.

```sh
npm ci
npm start            # dev build, opens the Practice copy
npm test             # TypeScript check and unit tests (tests/*.test.ts)
```

- **Where things are:** `MAP.md`, at the repository's root: every source file and script by area, where to start reading, the paths that cross areas and where the recipes for common changes are (`tests/map.test.ts` keeps it true). `LEDGER.md` is history up to 2026-11-13, frozen: how the code works now is in `MAP.md` and each module's header; a change's story is in its pull request.
- **End to end:** `npm run e2e` (`scripts/e2e.mjs`) drives the app over its debug port in a throwaway HOME, with a stand-in for `/Applications`, the running apps and the Trash (`CK_TEST_APPS`, `tests/macstandins.ts`): no test or tour looks at or removes the real ones, and with it a development run looks for another build too. `--electron` runs the dev build instead of the packaged app; on Linux add `--no-sandbox` and run it under `xvfb-run`. `--flows openCodeFlow,…` runs only the named flows while working on one.
- **UI tour:** `node scripts/ui-tour.mjs <outDir> [--electron]` is the light tour: the app opens on the Practice copy and each page is opened once, one picture each, in a few seconds. `--only shell,skills,…` takes the pictures of the named features; `--full` takes every feature at 860×560 up to 2560×1440, dark and light (about ten minutes, for a new release).
- **Harness tests:** `npm run test:harness` installs, updates and uninstalls a marker plugin with the real `claude`, `copilot` and `codex` CLIs in disposable homes (a missing one is skipped), checks that a plugin turned off stays off through an update and that one its marketplace dropped keeps its copy, and takes a bundled build's marketplace through being packed, unpacked, added to each tool's own list, installed and uninstalled. `CK_HARNESS_APPS=1` runs the same tests through the copy each desktop app carries.
- **Smoke:** `npm run smoke:mac` opens a hidden window on fixture data only.
- **CI:** `.github/workflows/mac.yml` runs the unit tests, packages the app, then runs the light tour (its pictures are the run's `light-tour` download) and the end-to-end checks against the packaged app. It runs on every push to `next`, and on any pushed branch with `gh workflow run mac.yml --ref <branch>`.

### Packaging and release

`npm run package:mac` (`scripts/package-mac.mjs`) builds the app on an Apple silicon Mac and puts it in two downloads under `release/`: `Central-Knot-<version>-mac-arm64.dmg`, a disk image whose window shows the app beside a shortcut to Applications, and `Central-Knot-<version>-mac-arm64.zip`. It signs with the Mac's Developer ID Application certificate and notarizes through the `central-knot-notary` keychain profile when both are there; otherwise, or with `CK_SIGN=0`, it signs ad hoc. The disk image is signed, notarized and stapled the same way, in its own right. `npm run package:mac:release` never falls back to ad hoc. The version comes from `package.json`. The release tag is recorded in the app (`build-info.json`) from the highest version tag on the commit being built (`v0.5.0-preview.5`), or `CK_RELEASE_TAG`; a release build refuses to package without one, and an untagged build never offers updates. Each release must carry both downloads: the disk image is for people, and the zip, named `Central-Knot-<version>-mac-arm64.zip`, is what the app's own updater downloads. `node scripts/update-proof.mjs` proves an update between two signed test builds of one line in throwaway folders (instructions at its top).

**An alpha is cut the same way, from its tag.** The release line is the tag's (`src/updates.ts releaseLine`), named by its pre-release part exactly: `v0.6.0-alpha.1` is an alpha, `v0.5.0-preview.9` a preview, no pre-release part a final. Packaging stops, saying so, at any other pre-release part (`v0.6.0-alpha1`, `v0.6.0-Alpha.1`, `v1.0.0-rc.1`): built, it would be the standard app and offered to every installed preview. Tag the commit `v<version>-alpha.<n>` (or set `CK_RELEASE_TAG`), with `package.json`'s version the tag's (`0.6.0` for `v0.6.0-alpha.1`), and run the same `npm run package:mac:release`. An alpha tag makes the app "Central Knot Alpha" (`src/updates.ts lineApp`): its name wherever the app shows it (the window, the menu bar icon's menu, About, the Dock), its own bundle id `com.centralknot.alpha`, and its own downloads, `Central-Knot-Alpha-<version>-mac-arm64.dmg` (its disk image says "Central Knot Alpha" too) and `Central-Knot-Alpha-<version>-mac-arm64.zip`. Its version reads "0.6.0 alpha 1". An alpha's release carries those two files and nothing else: installed previews up to preview 9 tell an alpha release apart only by its zip's name, so a `Central-Knot-<version>-mac-arm64.zip` on it would be offered to them. Packaging the standard app or an alpha first removes every other Mac download from `release/` (another line's, an earlier version's, a custom build's), names what it removed, and ends with "Upload exactly these:" and its two files. Publish them as a pre-release. `node scripts/alpha-check.mjs` packages an alpha from a test tag beside the standard app and opens the two on one throwaway home (the Mac run does this).

The disk image is made by `scripts/mac-dmg.mjs`. Each app's window is its own folder, `assets/dmg/Central-Knot/` and `assets/dmg/Central-Knot-Alpha/`: the picture, `background.svg` (it names the app), kept as PNGs at both sizes, and the window's size and icon places in `DS_Store`, which `scripts/mac-dmg-layout.sh "<app name>"` makes again on a Mac after a layout change. Releases are published on GitHub with their checks in the release notes.

### Building a custom build

The same packaging command takes optional inputs. With none it builds the standard app; with any, a custom build, which must be given its name (`--app-name`):

```sh
npm run package:mac -- --marketplace acme/plugins --app-name "Acme Knot" \
  --app-icon acme.png --marketplace-name "Acme plugins" --marketplace-logo acme-plugins.svg
```

| Input | What it sets |
|---|---|
| `--marketplace <owner/repo, Git URL or folder>` | The marketplace to carry. A Git source is fetched with this computer's own Git sign-in; a folder is carried as it is on disk, uncommitted changes included. Every plugin's files are packed, including plugins the marketplace keeps in other Git repositories. |
| `--app-name "<name>"` | The app's name, everywhere the app says it. Required, and never "Central Knot": under its own name the app sits beside the standard one in Applications, where a second "Central Knot" would take the standard app's place. |
| `--app-id <id>` | Its identity: its bundle id is `com.centralknot.custom.<id>`, which also names its settings folder. Made from the app's name when left out ("Acme Knot" is `acme-knot`). |
| `--app-icon <file.png or file.icns>` | The app's icon (a 1024 by 1024 .png, or a Mac .icns), also shown in the sidebar. |
| `--marketplace-name "<name>"` | The marketplace's name in the app. The tools still know it by the name in its `marketplace.json`. |
| `--marketplace-logo <file.png, .svg or .jpg>` | Its picture in the app. |
| `--feed <http or https address>` | Where newer releases of the marketplace will be published: the address of a folder (below). Needs `--marketplace`, the release the build starts with. Without it the marketplace changes only with a new build. |
| `--sequence <number>` | The release's place in the order of releases. Left out, it is the time of the build (seconds since 1970, about 1.8 billion now), so a later build is a later release. A number given by hand must be higher than every earlier build's, that default included: an installed copy keeps the content it has when the build it opens carries a lower number, and its log says so. |

The result is `release/<Name>-darwin-arm64/<Name>.app`, its zip `release/<Name>-<version>-mac-arm64.zip`, and `release/<Name>-build-report.txt`. The report lists the identity, the marketplace release (what it was made from, with the commit when there is one), each plugin packed, each plugin that could **not** be packed with the reason, a note when one entry makes Copilot CLI refuse the whole marketplace (an npm, pip or archive plugin does), the feed's address or that there is none, and that the build has no update location. A plugin that can't be packed doesn't stop the build. A missing `--app-name`, marketplace branding without `--marketplace`, or an input that can't be read stops it before anything is fetched. Signing is as for the standard app: your own Developer ID when one is in the keychain, otherwise (or with `CK_SIGN=0`) ad hoc. A custom build has no disk image yet.

What is packed is the marketplace as it is, without the fetch's own `.git` folders. A plugin kept in another repository is copied into `_bundled/<plugin>/` and its entry in `marketplace.json` pointed there; that file is then written again as JSON with every other value as it was, and a marketplace with no such plugin is carried byte for byte. What Central Knot writes outside the app (the markers around base instructions in a tool's file, a Git repo commit's author and message) says "Central Knot" in every build, so a custom build and the standard app read each other's. Inside the app the release is two files, `dist/bundle/release.json` (the manifest: marketplace, sequence, date, source, plugins, the archive's size and SHA-256) and one `.tgz` archive (`src/bundle.ts`, `src/bundlepack.ts`).

### Publishing newer plugins to a feed

A feed is a folder served over http or https that holds two files: `release.json` (the manifest) and the archive it names. Any static web server, bucket or file share behind a web address does; the app signs in to nothing, so who can reach the address is for whoever hosts it. To publish a new release of the marketplace:

```sh
node scripts/publish-bundle.mjs --marketplace acme/plugins --out ./feed
```

It packs the marketplace exactly as the build does and writes the archive, then `release.json`, into `--out`. Serve that folder at the build's `--feed` address; when copying it to a server, copy the archive before `release.json`. The earlier archive is no longer needed. `--sequence <number>` sets the release's place in the order (default: the time it is made) and `--min-app <version>` the oldest app that can use it.

- Nothing is published, and the command exits 1, when the marketplace can't be read, when a plugin's files couldn't be fetched this time (try again: a release never loses a plugin to a network hiccup), when the sequence isn't higher than the one already in `--out`, or when `--out` holds another marketplace's releases.
- A plugin that can never be packed (an npm or pip package) doesn't stop it: it is left out and named in what the command prints, and copies of it that people have installed stay as they are.
- What it prints also names each plugin the release no longer lists.

- **Try one without packaging:** `node scripts/custom-build.mjs <inputs> --out build/custom` stages the build on any system, then `CK_CUSTOM_BUILD=build/custom npm start` runs it. A plain `npm run build` makes `dist/` the standard app again.
- **Check:** `node scripts/bundled-check.mjs` builds a bundled build from the fixture marketplace with the documented command, deletes the marketplace, opens the packaged app in a throwaway home and checks its name, its own settings folder, the marketplace added to each tool's own list (stand-ins for the tools' CLIs record what they were asked), the Plugins page at four window sizes, Settings, and the feed: a release published to a folder served on this computer is taken, a plugin it no longer offers stays while a tool has it, and a broken publish changes nothing (`--electron` does the same as a development run; adding to the tools is checked on a Mac only, where the home can be written). The Mac CI runs it after the end-to-end checks.

### Logo

The logo files are in `assets/`: `logo.svg` (the sidebar mark, copied into `dist/` by `scripts/build.mjs`), `icon.icns` (the Mac app icon, used by `scripts/package-mac.mjs`), `icon.png` (the window icon on Windows and Linux) and `icon.svg` (the app icon drawing). A custom build takes its app icon and sidebar mark from `--app-icon` (above). The menu bar icon is the same logo in one colour: its drawing is `assets/tray.svg`, and the 32-pixel PNG made from it is kept as text in `src/trayicon.ts`; a custom build keeps the standard menu bar icon for now.

The product boundary is in `AGENTS.md`. The requirements are in `docs/SPEC.md` and the per-tool evidence in `docs/capability-data.md`. `LEDGER.md` records what was run and every check round up to 2026-11-13 (frozen history; a change since has its story in its pull request).
